## 1 任务概述

ACANX：**#153 并没有真的修好** —— 实际是这些区域（日志区、对话输入框）的**背景颜色在切换主题前后
未能调整**；**重启则不会出现**，只有涉及主题切换时才暴露。要求**先确定根因再修**。

## 2 排查（不猜，按证据走）

| 步 | 动作 | 结论 |
|---|---|---|
| 1 | 读主题机制 | 颜色有两条路：**内联 + 属性 API**（`ThemePaint.themed`，靠 `restylers` / `themeListeners` 重刷）与**补丁样式表**（整份替换）|
| 2 | 列所有上色点 | `setStyle` 27 处、`setBackground`/`setTextFill` 只出现在 `ThemePaint` 内部；主窗口与对话框的登记是齐的 |
| 3 | 对比两份表 | 选择器集合**完全对称**（0 差异）⇒ 不是「某一份漏规则」|
| 4 | 找「一次性上色且没登记」 | 找到一批（ProviderDialog ×12、OutputDialog ×1、ApprovalDialog ×5 等），但都是**文字色**，与「背景」不符 |
| 5 | 查皮肤内部节点 | **`grep -rn 'lookup(".content")\|.viewport\|skinProperty' view/*.java` ⇒ 0 处** —— 内部基面从来没被程序化上色过 |
| 6 | 看两张表 | 它们**确实**在给内部节点上色：`.text-area > .content`、`.scroll-pane > .viewport` / `.corner` |
| 7 | 读 `TS-2610-038` | 结尾写着「下一步是给输入类控件补一条**皮肤内部的兜底**（属新工作）」—— 与本轮定位一致 |
| 8 | 看冒烟测试 | 断言只看**控件本体**的 `getStyle()` ⇒ 内部节点画出来的颜色看不见 ⇒「绿而仍错」|

## 3 根因（确定）

**输入类控件的可见底色不是控件本体画的，而是皮肤内部节点画的**（`TextArea` 的 `.content`、
`ScrollPane` 的 `.viewport` / `.corner`）；而代码的上色只落在**控件本体**上，内部基面此前**只依赖
补丁样式表**。于是：

- **启动**：样式表按当时主题装载、本体色按当时色表求值 ⇒ 两边一致 ⇒ 看着正常；
- **切换**：本体被重刷（新色）✓，内部基面只能等样式表重算 —— 在 CSS 传导不可靠的环境
  （原生镜像；`TS-2610-028` 与 `ThemePaint` 类注释都记过）下它不重算 ⇒ **基面停在旧色** ✗；
- **重启**：整棵按新色表重建 ⇒ 本体与基面同时拿到新值 ⇒ 又正常 ✓。

⇒ 这正好解释「**重启正常、只有切换时暴露**」，也解释了为什么「只看控件本体样式」的断言抓不住它。

## 4 修法

1. `ThemePaint` 新增 `SKIN_SURFACE_SELECTORS`（`.content` / `.viewport` / `.corner`）与
   `applySkinSurfaces()`：每次上色时把**同一份底色**用属性 API 再写到内部基面上
   —— 延后一帧 + 先 `applyCss()`（皮肤那时才建好；`lookup` 也只在 CSS 处理之后有效），
   单个节点失败只记日志、不拖累整屏。
2. `install()` 的样式表清理：从「按 `external(stale)` 的 URL 字符串删另一份」改为**按文件名**
   删掉任何非当前主题的补丁表 —— URL 形式不一致（不同加载方式 / 原生镜像）时原先删不掉，
   两份同时在场上，切回旧主题时获胜的是**旧那份**，症状同样是「某些区域停在切换前的颜色」。
3. **回归断言**（这才是能抓住它的那条）：冒烟测试在切亮 / 暗之后，直接读 `#aha.composer` 的
   `.content` **实际背景色**并与 `Palette.CONTROL_INNER` 比对（暗 `#1E1E1E` ↔ 亮 `#FFFFFF`，
   两值不同 ⇒ 有判别力）。
4. **防漂移守卫**：`bin/CheckTheme.py` 新增 `check_skin_surface_fallback()` —— 代码清单里的每个
   基面类名都必须在**两份表**里以「后代选择器 + 设了 `-fx-background-color`」出现；
   方向是单向的（表里另有大量非基面的内部节点，不该被要求兜底）。

## 5 为什么不在内部节点上写文字色

`TextArea` / `TextField` 的 `.text` 是**皮肤把它绑定到控件 `textFill`** 上的，用属性 API 直写 `fill`
会打断那条绑定，反而让文字色从此不跟主题 ⇒ 文字侧继续走 `<控件>.setTextFill`（`apply()` 已经在做），
内部只兜底**基面**。
