## 1. 背景

PR #15 上出现两件事：

1. `Build` 的第一次 Maven 调用直接失败：
   `Plugin org.jacoco:jacoco-maven-plugin:0.8.15 ... Could not find artifact ... in central`；
2. `DesktopNative` 四条腿**全红**。用户追问：「这个不是说了作为可选项了吗？」

第 2 件是**观感事故**：它确实不是必需检查、也确实没挡住合并，但满屏红叉会被读成「流程挂了」。
第 1 件则是被怀疑成「版本号写错」，实际不是。

## 2. 排障过程与修复链

### 2.1 jacoco：不是版本问题，是「伪重试」

取证顺序（先证伪最容易的假设）：

| 核对 | 结果 |
|---|---|
| Central 上有没有 `jacoco-maven-plugin:0.8.15` | **有**：`maven-metadata.xml` 里列着，`…/0.8.15/…pom` 返回 **HTTP 200** |
| 本地仓库有没有 | 有（0.8.15 与 0.8.13）——这正是本地一直能过的原因 |
| CI 那条命令本地复跑 | `./mvnw -B clean test -Djacoco.skip=true` → **BUILD SUCCESS** |

真因在自建的 `maven-run` action：它**只在重试循环之前**清一次 `*.lastUpdated`。
而 Maven 的负缓存是「**首次失败时写入**」的——于是：

```
第 1 次：真的去 Central 取 → 失败 → 写下 *.lastUpdated
第 2 次：命中负缓存 → 立刻失败（日志与第 1 次一模一样）
第 3 次：同上
```

结果是「重试了 3 次」却**等于没重试**。修法：把清理抽成 `clear_failure_cache()`，
在**每一轮开跑前**调用；失败提示按「先 `curl -sI` 看 Central 是否有该 artifact →
再查 runner 网络/代理 → 最后才怀疑坐标」的顺序重写（因为每轮已清缓存，
「存在却取不到」基本只能是仓库侧问题）。

### 2.2 原生镜像：作业级容错 ≠ 非阻塞

第一次真跑的数据（run 37710184662）：

| 作业/腿 | 结论 | 失败步骤 |
|---|---|---|
| native-version | success | — |
| native-build (linux-x64, jdk25) | failure | **构建原生镜像 ✓ 成功**；产物自证 ✗ |
| native-build (macos-arm64, jdk25) | failure | **构建原生镜像 ✓ 成功**；产物自证 ✗ |
| native-build (windows-x64, jdk25) | failure | 工具链自证 ✗ |
| native-build (windows-x64, jdk27) | failure | 安装 GraalVM ✗ |
| native-publish | failure | 整理资产 ✗ |

**最重要的结论是那条好消息**：linux-x64 与 macos-arm64 的**原生编译本身成功了** ——
说明整条链路（GraalVM 安装 → argfile → classpath → `-H:Path/-H:Name` → assembly）是通的，
问题全在「编译之外」的四个地方。

**观感的根因**：容错放在了**作业级**。

- 作业级 `continue-on-error: true` 只保证「**整次运行**不变红」；
- **作业本身仍显示失败（红叉）**——PR 检查列表里就是一排红。

而整次运行最终也确实红了，因为 `native-publish` 的「整理资产」在**一个制品都没有**时
`exit 1`（它没有容错），把运行结论拖成了 failure。

四个修复：

1. 容错**下沉到步骤级**：安装 GraalVM / 工具链自证 / 构建 / 产物自证 / 改名 / 上传 / 下载 /
   整理资产，全部 `continue-on-error: true`，并让每个作业把真实结论写进 Job Summary。
2. **产物自证改成「诊断式」**：判据只留真不变式（存在、≥5 MB、平台魔法数、
   OpenJFX 三件套齐全且无 0 KB 空壳），失败时先把现场打全（`ls -la`、`find`、classpath 清单），
   结论写摘要而**不变红叉**，并用 `produced` 输出决定后续要不要改名/上传。
   顺带删掉一个会**误导**的判据与写法：
   - 「恰好 3 个 OpenJFX jar」会随传递依赖漂移 → 改成「≥3 且无 0 KB 空壳」；
   - `jfx=$(ls dir/*.jar | wc -l)` 在 `set -e` 下 glob 不匹配时 `ls` 退 2，
     **赋值语句直接让整步失败**，报错只有一行 `No such file or directory`。
3. **Windows 上 `.cmd` 不能由 bash 直接执行**：工具链自证那一步就是这样红的 →
   改为 `cmd //c "native-image.cmd --version"`。
4. **GraalVM 的 JDK 27 还没发布**（上游节奏）→ 安装步骤容错 + 后续步骤以
   `steps.graal.outcome == 'success'` 为前提，摘要里如实写「工具链未就绪」。
5. **无产物不发版**：发布作业在零制品时既不发布也不失败，只写摘要。

取舍写进文档：**原生编译真坏了，CI 不会红**——只表现为摘要里少一版、发布页少一个包。
这是刻意的：它是数据点，不是交付物。

### 2.3 顺带收紧

`Release.yml` 桌面端文件名 glob 由 `dist/aha-desktop-*.zip` 收紧为
`dist/aha-desktop-[0-9]*.zip`，避免把 `aha-desktop-native-*.zip` 误当成桌面端 jar 包
（自证步骤断言「恰好 1 个桌面端包」，误匹配会在有残留时假失败）。

## 4. 关键教训

1. **「重试」必须重建前置条件**：只清一次缓存的重试，本质上是一次重试加两次读缓存。
   凡是「失败会留下痕迹」的重试，清理动作都要放进循环体。
2. **作业级容错 ≠ 非阻塞**：`continue-on-error` 放错层级，等于把「可选」做成了
   「看着像挂了」。要让作业绿，必须落到步骤级。反过来也要配套「摘要留真相」，
   否则从「吓人」滑向「没人知道坏了」。
3. **判据只留不变式**：「恰好 N 个」这类判据一定会漂，而漂不代表坏。
   门禁的判据应当是「坏了才不满足」的条件。
4. **自证脚本先打现场**：失败时最需要的是「到底有什么」（目录、候选文件、清单），
   而不是一句 `error`。这也是「门禁必须自证」的落地方式。
5. **不要把「环境问题」和「代码问题」混在一个颜色里**：Windows `.cmd` 不能执行、
   GraalVM 某 JDK 未发布，都属于前者；它们的正确表现是「记录 + 摘要」，不是红叉。
6. **先证伪最容易的假设**：这次「jacoco 版本写错」的假设用三条命令就排除了
   （Central 200 / 本地有 / 本地复跑成功），避免了去改一个本来正确的版本号。
7. **顺序不能反**：本轮先改代码、后补技能，违反了技能自己写的「踩坑三步：
   先写技能 → 再改代码 → 记来源」。已在技能迭代日志里如实记下。
