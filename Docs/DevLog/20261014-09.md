## 🔍 先看清再动手：A 方案的原写法被仓库自己的证据否掉

正文 A 方案写的是「CSS 用集中定义的变量 / looked-up color 而非手抄色号」。动手前翻到
`Palette.buildThemeStyle()` 的注释与两份 CSS 的头部，记着同一条结论：

> **原生镜像下这种查表不可靠**——声明里一旦查不到值，CSS 会**丢掉整条声明**，
> 文字色回落到 modena 默认黑（暗色下就是一片黑字，issue **#49 第四轮**）。
> 结论：这份表里不允许出现任何变量查表 / `derive()` / `linear-gradient()` / `ladder()`。

⇒ 字面量**必须保留**（这是真机 + 原生镜像换来的教训），「唯一色源」只能从别处落地。

| 环节 | 落点 |

与 `bin/GenLogoPng.py` 同一模式：**生成器入库、产物入库**。

### 2. 58 处色号按**语义角色**命名（不是按色值）

每个字面色号都换成了角色占位符（`%CONTROL_INNER%` / `%SCROLL_THUMB%` / `%ON_ACCENT%` …）。
好处不只是「不手抄」：**读 CSS 就能看出意图**——`-fx-background-color: %ON_ACCENT%` 比
`-fx-background-color: #FFFFFF` 明确得多。判角色时按选择器与属性逐条定，并当场校验
「角色在该主题下的值 == 原字面量」，任一不符即报错。

### 3. 新增跨主题不变量：两份模板的角色序列必须**完全一致**

这是「同族控件在两种主题下逐项一致」的**机器证明**：同一控件在两个主题下必须用同一个
**角色**上色（值当然不同）。它能挡住「暗色下用前景色、亮色下却用边框色」这类错位——
而两份表各写各的字面量时，这种错位**肉眼看不出来**。

### 4. 四道静态门禁挂到 `Build.yml`

`CheckDocs` / `CheckSkills` / `CheckScripts` / `CheckTheme` 此前只在 `Gate.yml` 里跑，
而 Gate **不覆盖对 `dev` 的 PR**（只在 PR→main/release、每周一、手动时跑）⇒
面向 dev 的改动要等到发版前才被检查。新增 `static-guards` 作业（纯 Python，秒级），
问题在提 PR 时就暴露——**"写入规范而无人执行等于没写"**在 dev 分支上重演了一次，本轮补上。
