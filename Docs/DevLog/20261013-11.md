## 📋 任务概述

把桌面端界面骨架迁移到 **FXML**（界面与控制器分离），并保证原生包能正常启动。

参考：姊妹项目 LegionFanControl 的 `TS-2610-003-FXML-UI-Refactor-And-Native-Image-Reflection-Pitfalls.md`
——那份档案记录了「FXML 重构后原生包启动即崩」的两层踩坑：**反射登记的单元是「声明类」**，
以及**宽匹配资源规则会把 `.class` 也当资源编进镜像**（后者触发 JavaFX 运行期 `defineClass`）。

## ✅ 完成内容

### 1. 骨架迁到 `desktop-shell.fxml`

| 项 | 前 | 后 |
|---|---|---|
| 新建控件 | `DesktopShell` 里约 840 行（`buildMenuBar` / `buildMiddleRow` / `buildLeftContent` / `buildLeftColumn` / `buildRightColumn` / `buildCenterColumn` / `buildComposerBox` / `buildStatusBar`） | `desktop-shell.fxml`（结构 + `fx:id` + `id`），`DesktopShell#wireView()` 只负责样式 / 事件 / 监听 |
| 控制器 | 无 | `DesktopShell` 自身（`FXMLLoader#setController(this)`）——**公开方法一个没改** |
| 动态内容 | 消息流 / 工具卡片 / 会话单元格 / 空态标志 | 不变，仍在 Java（它们随数据生成） |

**为什么用「本类作控制器」**：`DesktopShell` 有大量被冒烟测试与真机自证依赖的公开方法
（`toggleLeft` / `toolCardCount` / `sessionRows` …）。换控制器类就要先搬一遍这些方法，
而换成自己作控制器后，**测试与宿主代码一行都不用改**，风险面小得多。

**为什么 FXML 里几乎没有属性**：每个 FXML 属性在原生镜像下都是一次反射调用，而反射调用的
成员**声明在哪个类上就得登记哪个类**。把属性降到最少，需要登记的类就收敛到可枚举的一小组
（各容器构造器 + `Pane#getChildren` + `Node#setId` + `@FXML` 字段注入）；样式与行为本来就在
Java 里（内联样式串 + 主题重刷），搬进 FXML 反而会把那套机制拆成两半。

### 2. 依赖

- 父 POM 的 `dependencyManagement` 新增 `javafx-fxml`（`version = ${javafx.version}` +
  `classifier = ${javafx.platform}`，与其余四个 OpenJFX 工件同款）；

  （`javafx-base` / `javafx-graphics` 的无分类器版本）。

### 3. 原生镜像侧（这里才是真正的坑）

| 项 | 改动 | 为什么 |
|---|---|---|
| 资源白名单 | `native-image-args.txt` 的扩展名清单加 `fxml` | 漏了就是「构建全绿、启动即崩（`IOException: Location is not set`）」，与 `.yaml` / `.obj` 那两次同类 |
| **刻意不做**的事 | 不写 `com/sun/javafx/.*` 这类宽匹配路径规则 | 它会把 `com/sun/javafx/reflect/Trampoline.class` 一并当资源编进镜像 → JavaFX 私有加载器读到字节 → **运行期 `defineClass`** → native-image 默认禁止 → 崩（TS-2610-003 的结构性根因）。AHA 用的是**扩展名白名单**，本来就不含 `.class`，保持这个形态即可 |
| 反射元数据 | 新增 20 条：`DesktopShell`、`javafx.fxml.FXMLLoader` / `FXML`、骨架里出现的各控件与布局（`BorderPane` / `HBox` / `VBox` / `Button` / `Label` / `TextField` / `TextArea` / `ScrollPane` / `ListView` / `MenuBar` / `Menu` / `MenuItem` / `CheckMenuItem` / `SeparatorMenuItem`）、`ObservableList` / `EventHandler`、StAX 的 `XMLInputFactoryImpl` | `FXMLLoader` 在 `<clinit>` 里**按名字**强初始化自己（封闭世界看不到）；控件按类名实例化；StAX 实现由 `FactoryFinder` 按名字找 |
| **声明类升级** | `javafx.scene.Node` / `Parent` / `layout.Region` / `layout.Pane` / `control.Control` / `control.Labeled` 由「只有类名」升为 `allDeclared*` | 反射访问成员按**声明类**解析：`getId` 在 `Node`、`getChildren` 在 `Pane`、`setOnAction` 在 `ButtonBase`……**子类条目不会覆盖父类成员**（TS-2610-003 第 ② 条） |

## ⚠️ 遗留与边界

| 项 | 说明 |
|---|---|
| GUI 冒烟在 CI 上是关闭的 | `AhaDesktopSmokeTest` 要 `-Daha.ui.tests=true` 才跑，所以**本次改造的界面行为未在 CI 的单测阶段被执行**；能执行它的只有原生 GUI 冒烟（`DesktopNative.yml`，Windows 腿真启 exe）与真机 |
| `DesktopNative.yml` 不在 PR 上触发 | 只有 `push: dev` 与 `workflow_dispatch`。要「合并前拿到原生包证据」，需手动 dispatch 到本分支 |
| 其余视图仍是 Java 构造 | 7 个对话框 + `LogPanel` + `CompletionPopup` 本轮未动；它们不是「骨架」的一部分 |
| 真机对照 | 布局 / 观感是否与改前一致，只能由 ACANX 真机比对（CI 只能证明「能起不崩」） |
