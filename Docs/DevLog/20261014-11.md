## 📋 任务概述

切主题后，**输入框（`aha.composer`）的底色仍是切换前那个主题的**，其它如供应商 / 日志 / 工具
对话框里的部分组件也一样。初始渲染是对的 ⇒ 问题只在「切换」这一步。

## 🔍 排查：不是一类原因，是四类并存

颜色是**内联在样式串里**的（`Palette` → `ThemePaint.themed` → `setStyle`），
所以换色表**不会**自动影响已建节点；主窗口有一张登记表 `DesktopShell.restylers`，
每个 `themed(...)` 的节点都留了「怎么重刷」。逐个核对「谁没被刷到」：

| # | 漏洞 | 关键取证 |
|---|---|---|
| A | `static final String` 样式常量：常量在**类加载时**求值，颜色被冻死 | `ProviderDialog.SECTION_TITLE_STYLE`、`SettingsDialog.MUTED_STYLE` / `NOTE_STYLE`、`ApprovalDialog.SECTION_STYLE` |
| B | 对话框内容用**已求值字符串**一次性上色：`themed(root, Palette.dialogTheme())` | `ProviderDialog` 的 root / content / scroll 三处 |
| C | 打开中的对话框**场景**不换样式表（`install` 只装在主窗口） | 对话框有独立 `Scene` |
| D | `ThemePaint.apply()` 缺 `-fx-control-inner-background` 的 API 兜底 | 输入类控件的底色来源就是它（modena 的 `.text-input` 亦然） |

**A 与 C 的区分办法**（记下来）：**重开一次对话框**——重开还是旧色 ⇒ A（值被冻住）；
重开正常、开着切不对 ⇒ C（时机缺失）。本次两类同时存在，只看现象会误判成同一个 bug。

## ✅ 完成内容

### 1. `ThemePaint`：通用重刷机制

| 新增 | 作用 |
|---|---|
| `onThemeChange(listener)` | 登记「换主题后怎么重刷」 |
| `refreshAll()` | 重刷还开着的对话框面板 + 跑一遍登记过的重刷（逐个隔离，一个失败不拖累其余） |
| `DIALOG_PANES` | 对话框面板登记表，**弱引用**（窗口关掉自动消失） |
| `themedForever(node, supplier)` | 立即上色 + 登记重刷，语义与 `DesktopShell.themed` 一致 |

### 2. 接上调用点

- `DesktopShell.applyTheme`：重刷自己的 `restylers` 之后调 `ThemePaint.refreshAll()`；
- `ApprovalDialog` / `ProviderDialog` / `SettingsDialog` / `LogPanel`：静态常量 → **按需求值**
  （方法 / lambda）+ `themedForever` 登记；
- `ThemePaint.apply`：没有 `-fx-background-color` 时也读 `-fx-control-inner-background`，
  落到 `Region#setBackground`。

### 3. 机器守卫（第 6 项，`bin/CheckTheme.py`）

**禁止 `static final String` 里出现 `Palette.`** ——「主题色」与「类加载时求值」在语义上互斥。
守卫逐文件解析初始化文本（跳过普通字符串与文本块），命中即报错并说明改法。

2. **原生镜像下输入框内层**（`.content` / `.viewport`）由 CSS 补丁表覆盖，本轮 API 兜底设在
   控件自身 ⇒ 二者是否一致需真机确认（记入 `TS-2610-038` 的 Q2）；
