| 事件 | 归组 |
|---|---|
| `pull_request` 的 `labeled` / `unlabeled`、`issue_comment`、`workflow_dispatch` | `explicit`（用户显式动作）|

## 🔧 技术要点

### 关键决策

- **显式请求的优先级必须落在并发组上**：GitHub Actions 的 `concurrency` 无法表达「显式请求可取消自动事件、
  但反向不行」；区分事件类别、让两者互不取消，是最简单且可静态守卫的形态。代价是显式请求与自动事件
  可能并发跑（原生构建可能多烧一条），换取「请求不被静默吞掉」；
- **`plan` 的 `push` 跳过与注释对齐**：注释早已写明「dev/push 时它被跳过」，实现却与注释不符；
  这类偏差只在 run 变红时才暴露，故配守卫时以「实现在不在」为准；
- **GitHub Actions 表达式没有三元运算符**：初版用 `? :` 选择 `explicit` / `auto`，让三条工作流在
  GitHub **校验阶段**直接失效（「workflow file issue」、无日志、无 job）⇒ 改用 `cond && 'explicit' || 'auto'`。
  本地 `CheckScripts` / PyYAML 都发现不了，**工作流改动应过一遍 `actionlint`**。

### 验证方式

- `python3 bin/CheckScripts.py` 通过；
- **`actionlint`（v1.7.12）静态校验**：三条工作流无输出（通过）；
- **守卫反向验证**：把 `DesktopNative.yml` 的 group 改回 `${{ github.ref }}` ⇒ 第 ⑥ 条如实点名并退出码 1，还原后复绿；
- **解析器自证**：三条线的 `concurrency.group` 都能被 `concurrency_group()` 正确抽出（含折叠多行）；
- 真机复验（合并后）：新开只改文档的 PR，**先同步 base** 再打触发标签 ⇒ 原生线启动并出包（本轮未做）。
