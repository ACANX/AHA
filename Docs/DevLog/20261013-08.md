## 📋 任务概述

落地 issue #44 里「原生 GUI 字体发虚 / 与 JVM 模式不一致」的**临时缓解**。

issue #48 已在真机截图的逐像素分析中把根因锁定为「**原生镜像丢失 LCD 次像素抗锯齿、退化为灰度**」
（彩色边缘像素 JVM 165,783 / native 9,025，18.4 倍；native 暗像素反而多 67%），
成因指向 DirectWrite 渲染参数在 closed-world 编译下读不到（与 #60 同源）。
根治要么补上渲染参数读取、要么等上游修复——**都不在本轮范围**。

本轮参照姊妹项目 LegionFanControl 已验证的做法（`NativeImageRenderDefaults`）：
**原生镜像内默认关闭 LCD 次像素合成、改走灰度抗锯齿**（灰度路径在原生与 JVM 两个构建下表现一致），
并保留**不改代码即可回退**的开关。

## 🔧 技术要点

### 关键决策

- **为什么现在可以改渲染行为**：TS-202610-NativeFontRenderingDiff 当初明确「拿到真机数据之前
  不改渲染参数」。真机数据已到手（#48 的像素对照），且做法在 LegionFanControl 上已经验证，
  属于「先证伪、再改」的正常推进，不是猜测。
- **为什么定性为临时措施**：它**没有修好根因**，只是绕开退化的合成路径。原生的灰度与 JVM 的
  次像素仍不是同一观感——它消除的是「发虚、发糊」，不是「与 JVM 逐像素一致」。
  因此类注释、指南与风险清单里都写死了「上游修复或补上渲染参数读取后删除本类与调用点」。
- **为什么默认关而不是默认不管**：不管的话原生包呈现的是**退化产物**（比正常灰度还糊），
  用户侧无法自助解决；默认关则给出一个稳定、可预期、可一键退回的结果。
- **开关命名**：`aha.desktop.nativeTextGreyscale`（沿用 AHA 的 `aha.` 前缀习惯），
  与 JavaFX 自己的 `prism.lcdtext` 分属两层——前者是「本缓解措施的开关」，后者是「渲染属性本身」。
