## 1. 背景

`DesktopNative` 首次真跑（run 37710184662，`dev@192a10d`）四条腿**全红**，
用户追问：「这个不是说了作为可选项了吗？」

先取证，事实是两句话：

- 它**确实**不是必需检查（分支保护里只有 `build (…)` / `Gate` / `Compat`），
  **也确实没有挡住合并**——PR #15 只是把 `dev` head 的**全部**检查都列了出来；
- 但四条腿全红（✗），观感上就是「流程挂了」。

## 2. 排障过程与修复链

### 2.1 先读结论：好消息在里面

拉 `/actions/runs` 与 `/actions/runs/<id>/jobs`，逐步骤看结论：

| 腿 | 结论 | 失败步骤 |
|---|---|---|
| `native-version` | success | — |
| `native-build (linux-x64, jdk25)` | failure | **「构建原生镜像」✓ 成功**；「产物自证」✗ |
| `native-build (macos-arm64, jdk25)` | failure | **「构建原生镜像」✓ 成功**；「产物自证」✗ |
| `native-build (windows-x64, jdk25)` | failure | 「工具链自证」✗ |
| `native-build (windows-x64, jdk27)` | failure | 「安装 GraalVM」✗ |
| `native-publish` | failure | 「整理资产」✗ |

**最重要的结论**：Linux 与 macOS 上**原生编译本身成功了**——整条链路
（GraalVM 安装 → `@argfile` → `-cp` classpath → `-H:Path` / `-H:Name` → assembly）
**是通的**，四个红叉**全在「编译之外」**。

### 2.2 观感根因：容错放错了层级

`continue-on-error` 在**作业级**时的语义被误解了：

| 放法 | 效果 |
|---|---|
| 作业级 `continue-on-error: true` | 只保证**整次运行**不变红；**作业本身仍显示失败（红叉）** |
| **步骤级** `continue-on-error: true` | 作业也绿（红叉消失），运行自然绿 |

而整次运行最后**也真的红了**：`native-publish` 的「整理资产」在**一个制品都没有**时
`exit 1`，而它偏偏没有加容错——它把运行结论拖成了 failure。

### 2.3 四个具体缺陷与修法

1. **容错下沉到步骤级**：安装 GraalVM / 工具链自证 / 构建 / 产物自证 / 改名 / 上传 /
   下载 / 整理资产，全部 `continue-on-error: true`，并让每个作业把真实结论写进
   Job Summary（编了没有 / 产物在哪 / 多大 / 为什么没成）。
2. **产物自证改成「诊断式」**：判据只留真正的不变式（存在、≥5 MB、平台魔法数、
   OpenJFX 三件套齐全且无 0 KB 空壳），失败时**先把现场打全**
   （`ls -la`、`find`、classpath 清单），结论写摘要而**不再变红叉**，
   并用 `produced` 输出决定后续要不要改名/上传。
   同时删掉两个会**误导**的判据与写法：
   - 「恰好 3 个 OpenJFX jar」：这个数会随传递依赖漂移，而漂移**不代表坏了**
     → 改成「≥3 且无 0 KB 空壳」；
   - `jfx=$(ls dir/*.jar | wc -l)` 放在 `set -e` 下：glob 不匹配时 `ls` 退 2，
     **赋值语句直接让整步失败**，报错只有一行 `No such file or directory`
     → 用 `set -uo pipefail`。
3. **Windows 上 `.cmd` 不能由 bash 直接执行**：`native-image.cmd` 就是这样让
   「工具链自证」红的 → 改走 `cmd //c "native-image.cmd --version"`。
4. **GraalVM 的 JDK 27 还没发布**（上游发布节奏，不是本项目问题）→
   安装步骤容错，后续步骤以 `steps.graal.outcome == 'success'` 为前提，
   摘要里如实写「工具链未就绪」。
5. **无产物不发版**：发布作业在零制品时**既不发布也不失败**，只写摘要——
   空 release 比不发更糟。

### 2.4 顺带收紧

`Release.yml` 桌面端文件名 glob 由 `Dist/aha-desktop-*.zip` 收紧为
`Dist/aha-desktop-[0-9]*.zip`：否则 `aha-desktop-native-<版本>-<jdk>.zip` 会被误当成
桌面端 jar 包，而自证步骤断言「恰好 1 个桌面端包」，在有残留时会**假失败**。

### 2.5 顺带确认的另一件事：默认构建的契约

同一轮里顺手把「默认构建只保证能编译、能打 jar」的契约也钉死了（与本次同属构建可靠性）：

- **两层保障**：① 模块只在 profile 的 `<modules>` 里（默认反应堆没有它）；
  ② 内层开关给安全默认值：`native.skip` 默认 `true`，由 `-Pdesktop-native` 置 `false`——
  这样「模块误入反应堆」与「真的去编原生镜像」是两件事，误入也不要求环境装好 GraalVM；
- 理由是**可诊断性**：默认路径一旦依赖平台工具链，构建失败就从「代码问题」变成
  「环境问题」，而后者极难在别人的机器上复现。

## 4. 关键教训

1. **作业级容错 ≠ 非阻塞**：`continue-on-error` 放错层级，等于把「可选」做成
   「看着像挂了」。要让**作业**绿，必须落到**步骤级**。
2. **但从「吓人」到「没人知道坏了」只有一步之遥**：步骤级容错**必须**配
   「摘要留真相」（Job Summary 逐腿写结论），否则信息随红叉一起消失。
3. **判据只留不变式**：「恰好 N 个」这类判据一定会漂，而漂不代表坏。
   门禁的判据应当是「坏了才不满足」的条件。
4. **自证脚本先打现场**：失败时最需要的是「到底有什么」（目录、候选文件、清单），
   而不是一句 `error`。这也是「门禁必须自证」的落地方式。
5. **不要把「环境问题」和「代码问题」混进同一个颜色**：Windows `.cmd` 不能执行、
   GraalVM 某 JDK 未发布，都属于前者，正确表现是「记录 + 摘要」，不是红叉。
6. **红叉之外先看步骤结论**：`/actions/runs/<id>/jobs` 的逐步骤结论能在没有日志权限时
   直接指出「哪一步红、哪一步绿」——本次正是靠它发现「编译成功、自证失败」。
7. **顺序不能反**：本轮先改代码、后补技能，违反了技能自己写的「踩坑三步：
   先写技能 → 再改代码 → 记来源」。已在技能迭代日志里如实记下，下一轮先落条目。
