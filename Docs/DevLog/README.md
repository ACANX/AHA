## 0. 本目录的定位

记录**已完成的事项**：做了什么、为什么这样做、改到哪些文件、如何验证、还剩什么。
**不记录排查过程**——排查与事故复盘进 [`Docs/Troubleshooting/`](../Troubleshooting/)，
需要时在日志里引用其文件名或 Issue 编号。

| 目录 / 载体 | 记什么 |
|---|---|
| `Docs/DevLog/`（本目录） | **已完成事项的开发记录** |
| `Docs/Troubleshooting/` | 问题排查 / 缺陷定位 / 事故复盘（`TS-yyyyMM-PascalCaseTitle.md`） |
| `Docs/TODO/` | 待办清单（`TD-PPPPP-*.md`）与进度看板 |
| GitHub Issue | 需要长期跟踪的遗留问题（含验收标准） |

## 1. 命名规范

```
yyyyMMdd-HH.md
```

| 部分 | 说明 | 示例 |
|---|---|---|
| `yyyyMMdd` | 日期（年月日） | `20261009` |
| `HH` | 小时（24 小时制，取事件处理时点） | `09` |

完整示例：`20261009-09.md` 表示 2026-10-09 09:00 开始的那件事。

**为什么用小时而不是日期范围**：一天可能开始多个独立任务，用小时可区分不同时段的工作。

> 同一小时内若确有第二件独立事项，**把 `HH` 顺延一位**（21 时的第二件记为 `...-22.md`），
> **不得加 `-2` 之类的后缀**——同一目录里只保留一种文件名形态，纯字符串排序即时间线顺序。

## 2. 记录规范

### 何时记录

- 完成一个独立功能模块后；
- 完成一次重要改造 / 迁移后；
- 每日开发任务结束时。

### 记录原则

- **简洁明了**：避免长篇大论，重点记关键决策与变更；
- **可追溯**：文件路径、类名 / 方法名必须准确；
- **可复用**：关键结论写清楚，方便后人少走弯路。

### 必须包含

- 完成了哪些功能；
- 修改了哪些文件（新增 / 修改 / 删除）;
- 如何验证（**CI 运行编号**，按项目约定不在本地跑 Maven）；
- 后续待办（属长期跟踪的 → 登记 `Docs/TODO/` 并开 Issue）。

### 可选内容

- 工时统计、接口清单、测试统计、截图或图表、参考文档链接。
