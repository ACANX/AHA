## 🔧 技术要点

### 关键决策

- **只动清单内文件**：两份清单都没有的路径一律不碰 —— 这是「`Dist/` 既有脚本又有产物」双重身份的命门；
- **动作列表单点产出、执行侧不做判断**：判断与执行分离，helper 只按计划执行，可审计、可复现；
- **备份先于替换**（删除也走备份）：否则「落完再备份」等于把新文件备份了；
- **门接在所有入口、且在下载之前**：界面拦住了、CLI 绕过去 ⇒ 用户的应用「换装成功但没人拉回来」；
- **形态判定用最窄特征**（`.jar`）而不是「是不是普通文件」，并用 GraalVM 运行期属性双保险；
- **不做形态切换**（JVM ↔ 原生）：原生自更新是**同一形态内**的升级，不是换形态；
- **能力门的顺序按「具体程度」**：原生 > 平台 > 安装形态（否则 Linux 上的原生包只会被告知「只在 Windows 实现」）；
- **一次性验证不常驻化**（ACANX 判定）：`HelperSelfTest` 一类「跑一次就够」的验证从每次构建的门禁里撤掉；
  只有**必然复发且复发时静默**的缺陷才留毫秒级静态守卫。

| 问题 | 根因 | 解决 | 详细记录 |
|---|---|---|---|

| 原生包点「检查更新」必崩：`Record components not available for record class …` | Jackson 反序列化 `record` 要读 record components，三个 `allDeclared*` 都不覆盖；更新模块 21 个 record / enum 一条未登记 | 全量登记（两条线）+ 扫源码 ↔ 元数据文件的静态守卫 | PR #243 `#issuecomment-6216014519` |

| 我误加「原生形态不支持自更新」的门，用户看到「升级按钮永远是灰的」 | 我据「原生包不在升级通道里」下的判断**不成立**（原生线有自己的 tag 与资产，换装与重启机制同构） | 撤门 + 补正向用例 + 更正文档 / TS / TD / Issue 结论 | `TS-2610-047` §4.1、#247 |
