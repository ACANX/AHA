## 🔧 技术要点

### 关键决策

- **入口必须是「不继承 `Application`」的转发类**：JVM 启动器在 `java -jar` 下看到主类继承
  `javafx.application.Application` 就假定 JavaFX 由模块路径提供，直接报
  「JavaFX runtime components are missing」。转发而不是重写 `main`：`AhaDesktopApp.main` 里还有
  启动横幅（版本行走 stdout）、渲染诊断开关与 `launch(AhaDesktopApp.class, args)` 三步。
- **`shadedArtifactAttached=true` 是硬约定，不是可选**：默认（`false`）会让 fat jar **顶替项目主产物**，
  于是装配描述符与**原生镜像线**（`aha-desktop-native` 依赖 `aha-desktop`）拿到的都是 fat jar、
  模块化 jar 被挪成 `original-*.jar`（issue #217 就是这么来的）。
- **classpath 启动 ⇒ 两个开关与模块路径时代不同**：反射进 `com.sun.javafx.font`（issue #48 探针）
  在未命名模块里本就不受限，不需要 `--add-opens`（写 `javafx.graphics` 反而因「无此模块」失败）；
  `--enable-native-access` 只能写 `ALL-UNNAMED`（写具名模块同样失败）。
- **「JavaFX 原生库能不能从 jar 里出来」是查过才敢做的**：反编译
  `com.sun.glass.utils.NativeLibLoader` 确认走 `loadLibraryFromResource` ⇒
  `Class.getResourceAsStream` ⇒ `cacheLibrary`，即**本来就支持从 classpath / jar 取原生库并缓存**；
  原生库也确实躺在 `javafx-graphics-<版本>-<分类器>.jar` **根部**（实测 Maven 仓库里的
  `javafx-graphics-25-win.jar` / `-linux.jar`）。因此「去 `lib/`」不是赌。
- **自证要落在「解包后的实际内容」上**：包体形态已经回归过一次（#217），只看「构建成功」防不住；
  工作流与两个 Python 脚本的正/反用例（旧形态包会被点名拒绝）都据此写。
