## 📋 背景与转折

上一轮（`20261016`）的结论是「conhost 上直接粘贴改不了」：JLine 的 Windows 终端逐条读按键，
粘贴里的换行与敲的回车在字节层面完全相同。

本轮读了 JLine 4.4.6 源码后发现问题被下早了：

| 事实 | 依据 |
|---|---|
| JLine 的 Windows 后端只打开**输出**侧的 `ENABLE_VIRTUAL_TERMINAL_PROCESSING`（0x0004） | `AbstractWindowsTerminal` 常量表只有 `ENABLE_VIRTUAL_TERMINAL_PROCESSING`，**没有** `ENABLE_VIRTUAL_TERMINAL_INPUT`（0x0200） |
| JLine 已完整实现括号粘贴解析 | `LineReaderImpl.BEGIN_PASTE` 绑定 `\033[200~`；`beginPaste()` 读到 `\033[201~`，`\r`→`\n` 后整体写入缓冲区 |
| AHA 已启用 `Option.BRACKETED_PASTE`（`SlashMenuReader` 构造里 `setOpt`） | 输出侧会发 `ESC[?2004h` |

也就是说：**终端能不能让标记透传，取决于输入句柄有没有 0x0200**，而不是 conhost 天生不行。

## 🧪 POC（临时目录，未进仓库）

位置：`/tmp/aha-paste-poc/`（`PasteProbe.ps1` + `run-*.cmd` + `README.md`）。
脚本用 `ReadConsoleW` 读字符流，比较 `legacy`（不加 0x0200）与 `vt`（加 0x0200）。

真机结果（**Windows Terminal**，`WT_SESSION` 有值）：

| 模式 | 输入 mode | 读到 |
|---|---|---|
| `legacy` | `0x01E7 → 0x01E0` | `line1<CR>line2<CR>line3`，**无标记** |
| `vt` | `0x01F7 → 0x03F0` | `<ESC>[200~line1<CR>line2<CR>line3<ESC>[201~` |
| `vtline`（保留 LINE_INPUT） | `0x01E7 → 0x03E2` | 同样有标记（按行返回） |

结论：**不开 0x0200 时标记被宿主消费；开了就透传。**

注意：这轮 POC 跑在 Windows Terminal 里，**conhost 自身是否发标记仍未验证**；
0x0200 对 conhost 无害（不发标记时行为与今天一致），因此先默认开启。

## 🔍 为什么绑定 `CALLBACK_INIT`

JLine 的 `AbstractWindowsTerminal.updateConsoleMode()` 用固定组合重建输入模式：

```java
int mode = ENABLE_WINDOW_INPUT;
if (attributes.getLocalFlag(ISIG) && !nativeHandlers.isEmpty()) mode |= ENABLE_PROCESSED_INPUT;
if (attributes.getLocalFlag(ECHO)) mode |= ENABLE_ECHO_INPUT;
if (attributes.getLocalFlag(ICANON)) mode |= ENABLE_LINE_INPUT;
if (tracking != MouseTracking.Off) mode |= ENABLE_MOUSE_INPUT | ENABLE_EXTENDED_FLAGS;
setConsoleMode(inConsole, mode);
```

`mode` 里**没有 0x0200**，每次 `readLine` 进入 raw mode 都会把启动时设的标志清掉。
`LineReaderImpl.readLine` 的顺序是 `enterRawMode()`（693 行）→ `callWidget(CALLBACK_INIT)`（718 行），
所以 `CALLBACK_INIT` 是「每轮 raw mode 之后」唯一的公开钩子。

没有子类化 `NativeWinSysTerminal`：它的构造器是包私有，`com.acanx.*` 无法继承。
