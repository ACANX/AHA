## 📋 任务概述

ACANX 真机实测（2026-10-13）发现：原生桌面 exe 的 `OS Information:` 打印
`Windows 8.0 build 9200`，而机器是 Windows 10 / 11；同一台机器 **JVM 模式**打印真实版本。
驱动 / 设备信息已被 #60 修好，**只剩 OS 版本这一项**。

## 🔍 排查（四个假设，三个被推翻）

| # | 假设 | 结果 |
|---|---|---|
| 1 | 仓库里已有清单实现、只是没生效 | ❌ 全仓 **0 处**（`manifest` / `supportedOS` / `MANIFESTINPUT` / GUID）——从未实现过 |
| 2 | GraalVM 有专门的清单选项 | ❌ 扫 `svm-25.0.0.jar` 全部含 `anifest` 的选项类：无 |
| 3 | 用 `-H:NativeLinkerOption` 透传给 MSVC 链接器 | ✅ 该选项存在，且是**可累加的多值**选项 |
| 4 | 清单用相对名，链接器会按工作目录解析 | ❌ 被真跑推翻（见下「坑 A」） |

**根因**：`GetVersionEx` / `GetVersion` 家族在**没有 Windows 10 兼容清单**的可执行文件里
一律返回 `6.2.9200`——Windows 对「未声明兼容性」的进程主动说谎，与真实版本无关。
`java.exe` 自带清单 ⇒ JVM 模式正常；GraalVM 生成的 exe 默认没有。

## ✅ 完成内容

### 1. 清单本体 + Windows 专属链接器参数

| 文件 | 作用 |
|---|---|
| `aha-desktop-native/src/native/app.manifest` | 只声明 Win10 / 11 的 `supportedOS`；**纯 ASCII**；刻意不带 `assemblyIdentity`（要与链接器生成的那份合并，重复声明会冲突） |
| `.../src/native/native-image-args-windows.txt` | `-H:NativeLinkerOption=/MANIFEST:EMBED` |
| `.../src/native/native-image-args-extra.txt` | 平台专属参数的**空档**（只有注释），作为非 Windows 的默认值 |

### 2. 「平台专属」交给 Maven 表达

`native-windows-manifest` profile（按 `<os><family>windows</family>` 激活）只改**一个属性**：
`native.image.extra.argsfile`。共享参数文件保持跨平台可用——`/MANIFEST*` 是 MSVC 链接器参数，
写进共享文件会让 Linux / macOS 腿**直接链接失败**。

### 3. 清单路径用绝对路径（坑 A 的修法）

`native.manifest.input` 属性：Windows 上是
`-H:NativeLinkerOption=/MANIFESTINPUT:${project.basedir}/src/native/app.manifest`，
非 Windows 退化成无害且幂等的 `-H:+UnlockExperimentalVMOptions`（避免空参数）。
它作为**主类之前**的命令行参数传入——主类之后的参数会被 native-image 当成**应用参数**。

### 4. CI 两道门禁

| 门禁 | 抓什么 |
|---|---|
| **清单自证**（新步骤，仅 Windows 腿） | 读 zip 里的 exe，搜 Win10 GUID——「加了参数但没生效」与成功**长得一模一样** |
| **OS 版本断言**（GUI 冒烟） | `Windows version 8.0 build 9200` 出现即失败；必须命中 `Windows version 10.`；并保留「必须打印 `OS Information:`」以防空过 |

## ⚠️ 两个坑（都值得记住）

### 坑 A：链接器的工作目录**不是** Maven 的 `workingDirectory`

第一次用相对名 `app.manifest`，Windows 腿报：

```
\\?\C:\Users\RUNNER~1\AppData\Local\Temp\SVM-13403134599471227632\app.manifest :
    general error c1010070: Failed to load and parse the manifest.
    The system cannot find the file specified.
LINK : fatal error LNK1327: failure during running mt.exe
```

native-image 在**它自己的构建临时目录**（`%TEMP%\SVM-…`）里调链接器 ⇒ 相对路径被解析到那里。

### 坑 B：这次失败**没让 CI 变红**

本工作流刻意把容错放在步骤级 ⇒ `构建原生镜像` 的 `conclusion=success`、`outcome=failure`，
作业绿、运行绿，只有「产物自证」的 note 写着「构建步骤结论：failure」，
下游「清单自证」「运行冒烟」**全部 skipped**。

⇒ **「CI 绿」在这条管线里不等于「构建成功」**；排查先看步骤级：

```bash
gh api "/repos/ACANX/AHA/actions/jobs/<job-id>" --jq '.steps[] | "\(.conclusion)\t\(.name)"'
```

### 另一个流程坑：PR 被合并后追加提交会变孤儿

修复刚提交时 `PR #161` 被合并（squash）⇒ 我把修复改成从 `dev`（已含合并提交）拉新分支 +
`git cherry-pick -x`，另开一条 PR。这正是仓库既有教训的第二次复现。
