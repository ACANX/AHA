# 上游冲突排障：PR #8 永久 `dirty` 的根因是一次「假合并」

> 日期：2026-10-07
> 作者：@ACANX（与 AI 协作）
> 关联 PR：[#8](https://github.com/ACANX/AHA/pull/8)（`dependa` → `dev`，冲突已解决待推送）
> 关联记录：[ReleaseProcess.md](../DevSpec/ReleaseProcess.md) §4、[TODO.md](../TODO.md) `F-12` / `G-01`

---

## 一、背景

PR #8（`dependa` → `dev`）创建后始终是 `mergeable=false`、`mergeable_state=dirty`，
GitHub 上显示 28 个提交、40 文件 +1853/−117，但**一直合不进去**。

而本地看起来一切正常：本地就在 `dependa` 上、工作区干净、`dependa` 与 `origin/dependa`
的 SHA 一致。于是问题变成：**两边都没动，冲突从哪来。**

---

## 二、排障过程与修复链

### 2.1 第一次判断就是错的：拿本地引用当了上游

第一反应是「在 `dependa` 上合并一下 `dev` 即可」，于是一试：

```
$ git merge --no-commit --no-ff dev
Already up to date.
```

「已是最新」——**看起来根本没有分叉**。若就此下结论，就会得出「GitHub 状态是缓存的、
重新推一次就好」的错误修复。

问题在于：本地 `dev` 还停在 `4f12cef`，而远端 `dev` 早已推进到 `5d938f3`。
`git fetch --all` 之后才看到真相：

```
   4f12cef..5d938f3  dev        -> origin/dev
```

**教训**：调试远端行为时，一律用 `origin/<branch>` 显式引用，不要用可能过期的本地分支。
本地 `dev` / `main` / `feat/local` 三条引用当时都是旧的。

### 2.2 决定性证据：两棵树的逐字节比对

换个角度——不看提交，看**内容**。`5d938f3` 的形态很可疑：

```
$ git log -1 --format='%h %p %s' origin/dev
5d938f3 4f12cef Merge pull request #6 from ACANX/dependa
```

消息写着 "Merge pull request #6"，但**只有一个父提交** `4f12cef`——
它不是真合并，而是把 `dependa` 的内容**重新落了一遍**。

接着做树的比对，一句话定性：

```
$ git rev-parse origin/dev^{tree}   cea8cce^{tree}
6a594528cb5a2d67d95cabe118717b8457009366
6a594528cb5a2d67d95cabe118717b8457009366
```

**`dev` 的树与 `dependa` 的祖先提交 `cea8cce` 的树逐字节相同。**

结论闭环：`dev` 的内容是 `dependa` 的真子集，两边改的是同一批文件的不同版本，
Git 无法自动合并（实测真合并会产生 9 个冲突，含 `add/add`），于是 PR 永久 `dirty`。

### 2.3 修复：`-s ours` 补上缺失的合并关系

既然 `dev` 的内容已完整包含在 `dependa` 里，正确的修复不是「再合一次内容」，
而是**补上缺失的血缘**——把 `dev` 记为父提交，树保持不变：

```
$ git merge -s ours origin/dev -F /tmp/merge-msg.txt
Merge made by the 'ours' strategy.
$ git log -1 --format='%h %p' HEAD
06c6121 3ee32fd 5d938f3
```

合并信息里写清了「为什么可以安全丢弃 `dev` 侧的改动」：因为 `dev` 的树等于
`dependa` 的祖先 `cea8cce` 的树，不存在会被丢掉的独有内容。

> **`-s ours` 不是「忽略对方」的偷懒做法，而是一种带证明的操作。**
> 用它的前提是能证明对方内容已被包含；证明不了就不该用。

### 2.4 若 `dev` 真有独有内容怎么办

那就不能用 `-s ours`，而要真合并并把 9 个冲突逐个按语义解决（本次冲突里
`Gate.yml` 是 `add/add`：两边各自新增同名文件，内容不同）——这属于正常的内容合并，
必须先读懂两边差异再取舍，绝不能一律选一边。

| 验证 | 命令 | 结果 |
| ---- | ---- | ---- |
| 合并未改动任何内容 | `git diff --name-only HEAD~1 HEAD` | 0 个文件；树 `92e697b…` 前后**逐字节一致** |

因为树完全没变，此前那次 `./mvnw clean verify`（BUILD SUCCESS，605 用例）的结论依然成立，
**无需重跑构建**。

## 四、关键教训

1. **调试远端行为必须用 `origin/<branch>`**。本地分支引用会过期；「Already up to date」
   在当时把我引向了完全错误的结论。这是本次排障唯一一次走弯路。
2. **`mergeable_state=dirty` 是结论，不是原因**。GitHub 只告诉你「合不了」，
   真正要做的是回到本地把两边的**内容**比清楚：先比树，再比文件，最后才谈策略。
3. **合并不只是搬运内容，还要留下血缘**。把内容「重新落一遍」（`git merge --squash`
   加手工提交、或 cherry-pick 全部提交）会造出一个内容相同、血缘无关的提交——
   上游收下了内容，源分支却没有变成祖先，该分支之后的每个 PR 都会永久冲突。
4. **squash / rebase 合并之后必须删源分支**。这类合并的代价就是失去血缘，
   补不回来；源分支若还要继续用（`dependa` 这种长期集成分支就是），就只能真合并。
5. **长期集成分支不适合 squash**。`dependa` 是 Dependabot 的 `target-branch`，
   会持续被合入、又持续往上游合——它必须保留血缘。
6. **不能证明「对方内容已包含」时，不要用 `-s ours`**。它会造成静默的内容丢失，
   而且事后极难发现（历史看过去完全正常）。

## 附：自查（可粘贴）

任何「PR 合不了」的情况，按顺序跑这三条基本就能定性：

```
git fetch --all --prune
git log --oneline origin/<base> --not origin/<head>     # base 有、head 没有的提交
git log --oneline origin/<head> --not origin/<base>     # head 有、base 没有的提交
```

若两边都有、且 `git log --format=%p -1 <base>` 只显示**一个父提交**却带着
"Merge pull request" 的消息，基本就是本文这种「假合并」。此时用树来定性：

```
git rev-parse origin/<base>^{tree}
git rev-list <head> | while read c; do \
  [ "$(git rev-parse $c^{tree})" = "$(git rev-parse origin/<base>^{tree})" ] && echo "等于 $c"; done
```

能在 head 的历史里找到 base 的树（或 base 的树即是 head 某祖先的树），
才可以用 `-s ours`；找不到，就老老实实解决冲突。
