## 1. 总体方案

### 1.1 形态：内联 REPL（inline），不是全屏 TUI

AHA 的交互式对话是**内联**的：像 `git`、`python` 那样把内容一行行打进终端原生 scrollback，
不使用备用屏幕缓冲区（alternate screen）。

采用这个形态的收益：

- **保留原生 scrollback**：终端自带的搜索、复制、翻页、选中、重定向全部可用
- **历史在终端里**：不需要自己实现回滚缓冲
- **管道友好**：非 TTY 时输出纯文本，没有 ANSI 垃圾

代价：**无法任意定位光标**，因此「输入框上方放一个可原地重绘的状态行」做不到
（判断依据见 [PLAN.md](../PLAN.md) 第 1 节）。

### 1.2 原则：探测能力，不探测品牌

无论 Windows Terminal、conhost、PowerShell、WSL、iTerm2、Tabby 还是 Xshell，
对进程暴露的都只是「一个 TTY + 一组环境变量 + 一组 terminfo 能力」。
因此只探测三个维度：

| 维度 | 探测者 | 用途 |
|---|---|---|
| 是否 TTY | `Console.isTerminal()` + JLine `terminal.getType()` | 决定是否着色、是否显示状态行 |
| 色彩深度 | `TERM` / `COLORTERM` / Windows 控制台标识 | 决定色带方案与色号 |
| 终端宽度 | JLine `terminal.getWidth()` | 决定折行宽度与分隔线长度 |
| 输出编码 | `Console.charset()` / `stdout.encoding` | 决定符号是否降级 |

**不为任何终端单独适配**，也不在启动脚本里自动 `chcp 65001`
（PowerShell 5.1 会缓存 `[Console]::OutputEncoding`，子进程改代码页反而更乱）。

### 1.3 分层

```
ChatCommand（主线程 readLine + 回合线程）
   │
   ├── render/    版面与样式：StreamRenderer / MarkdownStream / ToolBlock / StatusLine / Style / TextWidth
   └── tty/       终端交互：TerminalCapabilities / OutputEncoding / AboveStream
                            / JLineStatusSurface / TerminalHandover
```

**渲染层不碰光标定位**（只用 SGR 与换行），唯一例外是状态行 —— 它走 JLine 的滚动区域机制，
是唯一支持原地重绘的位置。

### 3.1 一次典型会话的完整版面

```
AHA 交互式对话（/help 查看命令，exit / quit 退出）                                    \   |   /
  供应商   BigModelCN                                                                  \  |  /
  模型     glm-4.6                                                                  ____\ | /____
  端点     https://open.bigmodel.cn/api/paas/v4/chat/completions                   /     \|/     \
  工作目录 /home/user/proj                                                        |    .-"""-.    |
                                                                                  |   /  o o  \   |
                                                                                  |  |    ^    |  |
                                                                                  |   \  '-'  /   |
                                                                                  |    '-...-'    |
                                                                                   \             /
                                                                                    '--_______--'
                                                                                       |=====|
                                                                                       | AHA |
                                                                                       '-----'
  项目根   /home/user/proj
  全局记忆 /home/user/.aha/AHA.md
  身份来源 内置默认身份
  身份顺序 后加载者优先级更高；同一层级按候选名顺序
    1. 用户级 /home/user/.aha/AHA.md（68 字符）
    2. 项目级 /home/user/proj/AGENTS.md（4722 字符）
  会话     5F3C1A2B-...
                                                             ← 空行
──────────────────────────────────────────────────────────── ← 上分隔线（提示符）
读一下 README 并总结                                               ← 输入行（无 `>`）
──────────────────────────────────────────────────────────── ← 下分隔线（状态行边框）
⠹ 等待响应…                                                    ← 状态行内容
```

模型开始输出后（正文经 `printAbove` 打到输入行上方）：

```
────────────────────────────────────────────────────────────
读取  file-read  README.md
 ✓ 完成 · 0.1s · 24 行
     # AHA
     AHA 是一个可扩展的 Agent 编排框架。
     … 还有 21 行
                                                             ← 每次调用前的空行
README 是一份项目说明，主要内容有三点：
1. 定位：可扩展的 Agent 编排框架
```

要点：

- 正文与工具区块永远打在**输入行上方**，输入行始终留在底部可编辑
- 状态行占**底部保留区**，它的边框充当输入行的下分隔线，因此它不能真的消失
  （空闲时换成模型名，见 3.4）

### 3.2 启动信息块（顶栏并排 + 细节整宽）

实现在 `ChatCommand#mastheadRows` / `ChatCommand#detailRows`，并排组装在 `StartupBanner#compose`。

启动信息**分两块**打印：

| 块 | 内容 | 位置 |
|---|---|---|
| 顶栏 | 标题、供应商、模型、端点、工作目录 | 左侧，与右侧 ASCII 标志**并排** |
| 细节 | 项目根、全局记忆、身份来源、身份顺序、会话 | 标志下方**整宽**打印 |

| 字段 | 块 | 来源 | 缺省行为 |
|---|---|---|---|
| 供应商 / 模型 / 端点 | 顶栏 | `service.runtime().attributes()` | 空值整行跳过 |
| 工作目录 | 顶栏 | `runtime.workingDir()` | 同上 |
| 项目根 | 细节 | `SystemPromptLoader.findProjectRoot(user.dir)` | 未找到则跳过 |
| 全局记忆 | 细节 | `SystemPromptLoader.ensureUserIdentity(...)` | 同上 |
| 身份来源 | 细节 | `CliSession.Opened.promptSource()` | 见下 |
| **身份顺序** | 细节 | `SystemPromptLoader.filePaths(...)` | 逐个列出「层级 + 路径 + 字符数」，并说明内联兜底是否使用 |
| 会话 | 细节 | 会话 ID | 总是打印 |

**为什么必须分成两块**：并排要求左栏足够窄。实测带绝对路径的细节行最宽 **78 列**
（「Aha.Agent.SystemPrompt（配置内联）……」与身份文件的绝对路径），若一股脑并排，
80 列终端上会把标志整个挤出屏幕——而 80 列恰恰是最常见的终端宽度。把长行移到标志下方
整宽打印，信息一条不丢，标志也能在 80 列下站住（门槛见 5.3）。

**对齐必须按显示宽度**：字段行由 `StartupBanner#field` 生成，标签用 `TextWidth.pad` 补到
**8 列**，而不是 `printf("%-8s")` 的 8 个字符。中文标签「供应商」（3 字符 / 6 列）与
「工作目录」（4 字符 / 8 列）按字符数补位会差 1 列，取值列错开——这是曾经真实存在过的缺陷。

「身份来源」的取值：`内置默认身份` / `沿用已有会话` / `命令行 --system` / `<文件路径>（N 字符）`。

**身份顺序为什么必须打印**：身份是「多来源叠加」的，顺序决定谁覆盖谁。不列出来，用户就
无从判断自己刚写进 `~/.aha/AHA.md` 的那句偏好到底有没有生效——这块信息刻意做成每次启动
都可见，而不是埋在日志里。桌面端也必须展示（见 `GUIDesign.md`）。

**为什么打印这些**：回答不符合预期时，用户第一反应是「它到底连的哪个模型」。
靠「问模型自己是什么模型」判断并不可靠 —— 模型自述经常是错的，必须由程序告知。

### 3.3 输入行

| 项 | 实现 |
|---|---|
| 提示符 | `"\n" + rule + "\n"`（`ChatCommand#run`） |
| 上分隔线 | `─` × `(width - 1)`，降级为 `-`，**高亮紫色** |
| 下分隔线 | 状态行保留区的**第一行**，同一高亮紫（不是 JLine 的 `setBorder`） |
| 行首标记 | **无**（历史上是 `❯`，已去掉） |
| 多行粘贴 | `LineReader.Option.BRACKETED_PASTE = true` |
| **斜杠命令补全** | `SessionCommandCompleter`：Tab 出候选菜单（带用法说明），`AUTO_MENU_LIST` + `LIST_PACKED` + `COMPLETE_MATCHER_TYPO`（模糊/容错） |
| **命令实时着色** | `SessionCommandHighlighter`：命令名绿=已支持 / 红=未知，回车前即可判断 |
| 退出词 | 整行等于 `exit` / `quit` / `/exit`（且不含内嵌换行） |

宽度取 `width - 1` 而非 `width`：**满宽会触发终端自动换行**，把分隔线挤成两行。

**两条线必须同色**（高亮紫）：上边线来自提示符，下边线来自状态行保留区的第一行。
之所以不用 JLine `Status` 自带的边框（`setBorder(true)`）：它只接受布尔开关，
`borderString` 是 protected 且会在内部被重建，**无法上色**——两条线会一紫一灰。
改用保留区的第一行后，占用高度不变（仍然两行），颜色完全可控。

| 色彩深度 | 色号 | 说明 |
|---|---|---|
| 256 色 / 真彩 | `38;5;141`（`#AF87FF`） | 高亮紫 |
| 16 色 | `95` | 亮品红（16 色下最接近的紫） |
| 无色 | 无 SGR | 管道 / 重定向时不塞转义序列 |

提示符以 `\n` 开头：分隔线必须从行首开始画，否则会接在上一行正文末尾。

**为什么命令要实时着色 + 可补全**：此前只能盲敲，按下回车才知道命令对不对——
错了就变成一句「未知命令」，输入过程中毫无反馈。补全负责「有哪些命令」，
着色负责「我拼的这个对不对」，两者都不改动缓冲区内容。

**为什么去掉 `❯`**：分隔线已经把输入区框出来了，再加一个标记是噪音；而且 `❯`（U+276F）
不在 GBK 内，在中文 Windows 控制台的 936 代码页下会变成 `?` —— 这是当初做编码探测的起因。

### 3.4 状态行（底部常驻）

```
⠋ 等待响应…                     ← 等待首个 token
⠙ 等待响应…
⠸ 执行工具 shell-exec…          ← 工具执行中（第二段无输出的等待）
glm-4-plus                      ← 空闲态：换模型名，边框保留
```

| 项 | 值 |
|---|---|
| 转圈帧（Unicode） | `⠋⠙⠹⠸⠼⠴⠦⠧⠇⠏` |
| 转圈帧（降级） | `|/-\` |
| 阶段文案 | `等待响应…` / `执行工具 <工具名>… <实时秒数>` |
| 空闲文案 | 模型名 |
| 刷新间隔 | `TICK_MS = 120`（`StatusLine`） |
| 截断宽度 | `width - 1`（避免折成两行） |
| 载体 | `JLineStatusSurface` → `org.jline.utils.Status` |
| 保留区内容 | 两行：**第一行是输入框下边线**（高亮紫），第二行是状态文本 |
| 行数恒定 | 空闲时也照常输出边线行，否则底部区域收缩、下边线会突然消失 |

**只显示「转圈帧 + 阶段」**，不显示耗时、模型名、用量：

- 耗时是**这次操作**的信息，属于工具区块的末行（见 3.6），放在状态行会与「现在在干什么」混淆
- 模型名与用量在空闲态与 `[usage]` 行已有位置

**为什么空闲时不隐藏**：底部那一行兼着输入行的下分隔线，撤掉会让输入区突然失去框线。
因此 `StatusLine#idle()` 是「换成空闲文案」而不是 `hide()`。

**启用条件**（缺一即整体关闭）：

```
tty == true  &&  width > 0  &&  surface.available()
```

`surface.available()` 由 `JLineStatusSurface#create` 判定：终端类型非 `dumb`、
存在 `change_scroll_region` 能力、行数 > 0。三项都要查 —— dumb 终端下
`Status.getStatus()` 仍会返回对象，但占不住底部区域，且 `close()` 会 NPE。

| 环境 | 处理 | 理由 |
|---|---|---|
| 有色 | **丢掉** `#`，按级别配色 | 颜色与字重已经把级别说清楚了，再留一个弱化的 `#` 只是噪音 |
| 无色（`NO_COLOR`、管道） | **保留** `#` | 它是**唯一**的层级信号，丢掉就等于丢掉级别 |

**六个级别必须各不相同**：此前三级只有加粗、四级往后全是同一种青色——三级之后实际等于没渲染，
「这是几级标题」读不出来。现在从「粗 + 下划线 + 亮青」逐级递减到「弱化 + 斜体 + 青」，
并有用例（`everyHeadingLevelLooksDifferent`）钉住六种样式互不相同。

**歧义规则**（`InlineScanner`，CommonMark 侧翼思路的可解释子集）：

| 定界符 | 开定界符要求 | 闭定界符要求 |
|---|---|---|
| `*` | 后一个字符非空白 | 前一个字符非空白 |
| `_` | 后一个字符非空白，且**前一个字符非字母数字** | 前一个字符非空白，且**后一个字符非字母数字** |

因此 `2 * 3` 不会误判为斜体，`a_b_c` 也不会。

**为什么不牺牲流式**：

| 缓冲 | 上限 | 理由 |
|---|---|---|
| 行首块级判定 | 8 字符 | `#`、`- `、`1. `、`> `、三个反引号，只需这么长即可判定 |
| 行内构造 | 200 字符 | 超出即按纯文本吐出，否则一个未闭合的定界符会把后续内容一直扣住 |
| 递归深度 | 4 层 | 防止构造输入打穿栈 |

**围栏内部原样输出**：代码里的 `#`、反引号、`-`、`*` 不应被当成 Markdown，
否则读代码的人会被错误高亮误导。围栏内的 `|` 也不会被当成表格。

#### 3.5.1 表格

```
| 字段 | 说明 | 默认 |
|---|---:|---:|
| ModelWrite | 写入策略 | off |
```

渲染为：

```
┌──────────────┬──────────┬──────┐
│ 字段         │     说明 │ 默认 │
├──────────────┼──────────┼──────┤
│ ModelWrite   │ 写入策略 │ off  │
└──────────────┴──────────┴──────┘
```

| 项 | 处理 |
|---|---|
| 列宽 | 取该列所有单元格的最大显示宽度 |
| 对齐 | 从分隔行解析：`---` 左、`:--:` 居中、`--:` 右 |
| 表头 | 分隔行之前的那一行，加粗 |
| 缺列的行 | 右侧补空单元格，保证框线对齐 |
| 超出终端宽度 | **压缩列宽**，不折行——表格一旦折行，行列对应就彻底乱了 |
| 框线字符不可用 | 退化 ASCII（`+---+` / `| a |`） |
| 后的空行 | 跳过，否则会多出一整行空框 |
| **单元格内行内样式** | 解析 `` `代码` `` / `**粗体**` / `*斜体*` / 链接 |
| 单元格列宽 | 按**解析之后**的显示宽度算（链接会展开成「文本 ⟨地址⟩」，宽度会变） |
| 表头加粗 | 仅在单元格无行内样式时叠加——行内样式自带 `[0m` 复位，会把外层加粗一起清掉 |
| 内容撑宽时 | 退回纯文本再截断：以对齐为先（表格错位比丢样式难读得多） |

**单元格必须先渲染再判断放不放得下**：反过来先按列宽截断纯文本，会把 `` ` `` 或 `**`
切成两半——解析不出闭合定界符，整格退回字面量，屏幕上就出现没被渲染的星号和反引号
（这正是此前表格里样式不生效的原因）。

**这是唯一会延迟输出的构造**：不先扫一遍就不知道每列多宽，逐行输出必然参差不齐——
那还不如不渲染。因此表格在遇到第一个非表格行（或流结束时）整体输出；表格通常很短，这点延迟无感。

### 3.6 工具调用区块（重点）

#### 布局

```
执行命令  shell-exec  powershell                   ← 首行：类别 + 工具名 + 程序名（色带 + 鲜艳色 + 加粗）
E:\GitRepo\GitHub\ACANX\AHA> powershell -NoProfile -Command "Get-ChildItem
  -Recurse -Path aha-core/src/main/java -Filter *.java"   ← 命令行：目录 + 提示符 + 命令全文（高亮白）
结果                                              ← 结果区标题（常规色）
   E:\...\SqliteMemoryStore.java :: 111: String sql = "INSERT OR REPLACE
        INTO session(id, gmt_create, config_json) VALUES(?)"
   E:\...\SqliteMemoryStore.java :: 229: String sql = "INSERT INTO memory(...
 ✓ 完成 · 1.2s · 2 行                              ← 末行：状态 + 用时 + 规模（常规色）
```

**命令行刻意做成终端转录的样子**：`<目录><提示符> <命令全文>`。用户排查问题时第一个要看的就是
这一行——在哪个目录、用什么终端、跑了什么命令。提示符字符本身就是平台信号：
`E:\repo>` 是在 cmd 里跑的，`/tmp/repo$` 是在 sh 里跑的。

非命令类工具不打命令行，改为逐条列出参数：

```
读取文件  file-read
 path  Docs/PLAN.md                                ← 超长值只报规模
 ✓ 完成 · 0.1s · 412 行
 结果
   …（前 5 行）…
   … 输出共 412 行，此处显示前 5 行
```

无色时（`NO_COLOR`、管道）：首行退化为 `[读取文件] file-read`，其余结构不变。

#### 三类行的配色分工

| 行 | 配色 | 理由 |
|---|---|---|
| 首行（类别 + 工具名 + 程序名） | 暗灰底 + **加粗 + 鲜艳类型色** | 这是「谁做了什么」的主语，要第一眼抓住注意 |
| 命令行 | **高亮白**（256：`38;5;255`；16 色：`97`） | 排查时的第一现场，用最亮的白单独拎出来 |
| 结果区 / 末行 | 常规色（沿用原有样式） | 主体内容，不该与上面两行争注意力 |

类型色（256 色，比早期版本更鲜艳）：

| 类型 | 色号 | 观感 |
|---|---|---|
| 读取文件 | `117` | 亮蓝 |
| 写入文件 | `221` | 亮黄 |
| 执行命令 | `215` | 亮橙 |
| 请求网络 | `123` | 亮青 |
| 调用工具 | `255` | 白 |

#### 结构规则

| 项 | 值 | 实现 |
|---|---|---|
| 区块前空行 | 每次调用前强制一个空行 | `StreamRenderer` |
| **首行内容** | `类别 + 工具名`，命令类再补**程序名**（命令第一个词） | `ToolBlock.head` + `ToolKind#programOf` |
| 类别标签 | 4 字对齐：读取文件 / 写入文件 / 执行命令 / 请求网络 / 调用工具 | `ToolKind` |
| 命令行 | `<目录><提示符> <命令全文>`，折行、续行缩进 2 列 | `ToolBlock.command` |
| 续行缩进 | 2 列 | 同上 |
| 超长命令 | 超过 40 行时**中间**省略，保留首 20 行 + 尾 10 行 | 同上 |
| 非命令类明细 | 逐条 `键  值`，标签列宽 6，值折行且续行对齐 | `ToolBlock.details` + `TextWidth.wrap` |
| 参数值上限 | 超过 200 字符只写 `<N 字符，已省略>` | 同上 |
| 结果区标题 | 成功为 `结果`，失败为 `错误` | `StreamRenderer#print` |
| 成功正文 | 最多 5 行（折行后），超出报「输出共 N 行」 | `ToolBlock.body` |
| 失败正文 | 最多 40 行、**不弱化** | 同上 |
| 末行 | `✓ 完成 / ✗ 失败 · 耗时 · 规模`；失败时耗时同样显示 | `ToolBlock.result` |
| 耗时显示阈值 | 成功与失败均为 ≥ 100ms | `ToolBlock.detail` / `failureDetail` |
| **截断** | **任何情况都不按终端宽度硬截断** | 全部走 `TextWidth.wrap` |

**为什么命令与输出一律折行、绝不截断**：此前长命令被截到 80 字符（还常常连终端宽度都过不了），
用户完全看不到到底执行了什么，「为什么失败」也就无从判断。实测一次 Windows 上的命令失败，
屏幕上只能看到一句 `'slash' is not recognized`，连「执行了哪条命令」都无从确认。
只有几百行级别的超长命令才在**中间**省略——首尾通常才是关键信息。

**为什么失败时耗时也要给**：它本身就是排查线索——秒级失败多半是参数或环境问题，
超时才失败往往是命令本身卡住。

**错误正文不再回显命令原文**：命令行已经完整展示，再贴一遍只是重复
（早期命令不可见时才需要）。

#### 类型与配色

| 类型 | 标签 | 判定工具名 | 目标参数 | 256 色标签 | 语义 |
|---|---|---|---|---|---|
| READ | 读取 | `file-read`/`file-list`/`read` | `path` | `38;5;110`（柔蓝） | 安全 |
| WRITE | 写入 | `file-write`/`write`/`edit` | `path` | `38;5;179`（黄） | 会改数据 |
| EXEC | 执行 | `shell-exec`/`shell`/`exec`/`bash` | `command` | `38;5;209`（橙红） | 会跑命令 |
| NETWORK | 请求 | `http-get`/`http`/`fetch` | `url` | `38;5;80`（青） | 出网 |
| OTHER | 调用 | 未识别 | 首个参数 | `38;5;250`（灰） | 中性 |

**用颜色区分的是「操作的后果」而不是「工具是谁」**：读取是安全的、写入会改数据、
执行会跑命令。扫一眼颜色就知道刚才发生了什么，不必逐行读工具名。

#### 色带的实现要点

```java
// 256 / 真彩：暗灰底 + 类型色标签
"\u001B[48;5;236m" + "\u001B[38;5;110m" + 文本 + "\u001B[0m"
// 16 色：亮底 + 显式前景
"\u001B[100;97m" + "\u001B[97m"        + 文本 + "\u001B[0m"
```

两条必须遵守的规则：

1. **色带必须自己铺满整行**。只给颜色不铺底，看起来就是「一段彩色文字」而不是「区块」。
   实现见 `Style#fill`：`TextWidth.pad(body, width - 1)`。
2. **截断必须发生在上色之前**。`TextWidth` 数的是显示宽度，把含 SGR 的串交进去，
   转义序列会被当成普通字符 —— 宽度算错、色带跟着断。

**16 色为什么必须显式指定前景**：16 色下亮底配默认前景，在浅色终端上几乎不可读
（白底白字）。256 色/真彩则不需要，暗灰底 `48;5;236` 配默认前景即可。

### 3.7 工具授权问答

需要 `WRITE` / `EXECUTE` / `ADMIN` 权限时，回合线程暂停并提问：

```
需要授权：file-write 请求 WRITE 权限
  path = /home/user/proj/a.txt
  content = …
  [y] 允许本次   [n] 拒绝   [a] 本次会话内始终允许 WRITE
```

| 输入 | 语义 |
|---|---|
| `y` / `yes` | 允许本次调用 |
| `n` / 直接回车 / 其它 | 拒绝本次调用 |
| `a` / `all` | 本会话内该权限不再询问 |
| Ctrl+C / Ctrl+D / 超时 | 视为拒绝，**不中断会话** |

拒绝后打印授权指引（三行：提示处输入 y/a、Aha.yaml 的 `Tools.AutoApprove`、启动加 `--yes`），
但**回灌给模型的只有一句简洁的「未获授权」** —— 完整指引是给人看的，模型转述会变得冗长。

**问答走队列而不是直接读 reader**：授权发生在回合线程，而 `LineReader` 由主线程持有
（主线程常驻 `readLine`）。回合线程直接读会争用同一把读锁。
实现为 `ChatCommand#askForAnswer`：主线程发现 `awaitingAnswer` 为真时，
把下一行输入投进 `answers` 队列。

### 3.8 其它输出

| 输出 | 形式 | 样式 |
|---|---|---|
| 错误 | `[error] <code>` + 完整 message 正文 | 红色；正文最多 40 行不截断 |
| 用量 | `[usage] 输入 N / 输出 M tokens` | 弱化；两侧均为 0 时**不打印** |
| 中断 | `[已中断]` | 无样式（说明被打断的回合未正常结束） |
| 控制台编码告警 | `[warn] Console output encoding <name> cannot display AHA's Chinese output.` + 三行切换指引 | **纯 ASCII** |
| 读取输入失败 | `[warn] 读取输入失败，已忽略本次输入: …` + 一行建议 | 无样式 |
| 退出提示 | 空行 + `会话已保存：<id>` + `续接本次会话：aha chat --session <id>` | 无样式 |
| 工具异常堆栈 | 工具执行抛异常时，错误正文带完整堆栈 | `AgentEngine` 捕获并附加 |
| 回合异常堆栈 | 回合线程未预期失败时，摘要 + 完整堆栈 | `ChatCommand` 捕获并附加 |

**编码告警必须用纯 ASCII**：它出现的前提恰恰是「当前控制台表示不了中文」，
用中文提示等于提示本身也读不了。

**用量两侧都为 0 时不打印**：部分供应商不回 usage，打印 `[usage] 输入 0 / 输出 0 tokens`
只会误导。

## 4. 流式期间保持输入可用（核心机制）

这是 0.1 交互体验的关键，也是最容易做错的地方。

### 4.1 架构

```
主线程                          回合线程（虚拟线程 aha-turn-N）
  │                                   │
  ├─ reader.readLine(prompt)  ←永远在读 │
  │        ↑                          │
  │        │ printAbove（逐行上抛）     │
  │        └──────────────────────────┤
  │                                   ├─ service.streamChat(...)
  └─ Ctrl+C → token.cancel()          └─ 状态行刷新（另一线程）
```

| 角色 | 线程 | 说明 |
|---|---|---|
| 读输入 | **主线程** | 常驻 `readLine`，永不退出 |
| 跑回合 | 单线程虚拟线程执行器 | `Executors.newSingleThreadExecutor(Thread.ofVirtual().name("aha-turn-", 0).factory())` |
| 写正文 | 回合线程 → `Reader.printAbove` | 逐行上抛到输入行上方 |
| 刷状态行 | 全局守护调度器 | `aha-status-line`，每 120ms |

### 4.2 为什么 `readLine` 必须在主线程

最早的做法是「把 `readLine` 放到后台线程，主线程跑回合」，结果
**JLine 的 SIGINT 处理失效**：按 Ctrl+C 只输出 `^C` 然后整个 JVM 退出。
最小复现即可确认，与业务代码无关。

原因是 JLine 通过 `sun.misc.Signal` 注册信号处理器，而该处理与线程上下文绑定；
一旦读操作不在主线程，Ctrl+C 就落回默认行为。

**由此产生的一个隐蔽要求**：`aha-cli/src/main/java/module-info.java` 必须声明

```java
requires jdk.unsupported;
```

`sun.misc` 只由 `jdk.unsupported` 导出。不声明时：

- **module-path 下**：Ctrl+C 直接杀进程
- **classpath 下**（独立探针）：一切正常

因此这个问题**只在真实运行形态（module-path）下暴露**，用 classpath 探针测不出来。
如果哪天 Ctrl+C 行为退化，先查这行声明。

### 4.3 AboveStream：行缓冲

正文要经 `printAbove` 上抛，而渲染层写的是字节流，因此中间加一层行缓冲
（`tty/AboveStream`）。

两条刻意的取舍：

1. **只按 `\n` 切分，丢弃 `\r`**。该模式下不做原地重绘，`\r` 留着只会污染输出。
2. **不整行不吐**，且调用方的 `PrintStream` **必须关掉 autoFlush**。
   `PrintStream` 在「写 `byte[]`」时也会 flush，若不关就会把半行当整行推上去，
   **折行随之失效**（表现为长行不换行）。收尾由调用方在回合结束时显式 `flush()`。

顺带一提：`AboveStream` 覆写的是 `write(int b)`（收**字节**而非字符），
因为编码转换由外层 `PrintStream` 负责。

### 4.4 Ctrl+C 语义

| 场景 | 行为 |
|---|---|
| 回合生成中 | 取消本轮（已生成部分仍然落库），输出 `[已中断]` |
| 空闲（无回合） | 只清空输入行，**会话继续** |

第二行是必要的：早期实现里空闲时 Ctrl+C 会直接退出整个会话，与 shell 惯例不符。

`[已中断]` 由**回合线程**输出：此刻主线程正回到 `readLine`，
只有回合线程调 `printAbove` 才落在正确的位置。

### 4.5 非 TTY 路径

`capabilities.tty()` 为假时（管道、CI、重定向）：

- 输出直接写 `System.out`，**不经** `AboveStream`
- 不创建状态行（`StatusSurface.NONE`）
- 不着色、不折行（宽度按 0 处理）

因此 `aha chat < input.txt > output.txt` 得到的是干净纯文本。

## 5. 降级矩阵

### 5.1 能力组合

| 场景 | 颜色 | 状态行 | 折行 | 符号 |
|---|---|---|---|---|
| 256 色终端（TTY） | 256 色色带 | 显示 | 按宽度 | `•` `✓` `─` `⠋` |
| 真彩终端 | 同上（当前只用 256 色号） | 显示 | 按宽度 | 同上 |
| 16 色终端 | 亮底 + 显式前景 | 显示 | 按宽度 | 同上 |
| `NO_COLOR` / `--no-color` | 无 | 显示 | 按宽度 | 同上 |
| 编码不支持符号（如 GBK） | 按深度 | 显示 | 按宽度 | `-` `[ok]` `-` `\|/-\` |
| 终端无 `change_scroll_region` | 按深度 | **不显示** | 按宽度 | 按编码 |
| dumb 终端 | 无 | **不显示** | 按宽度 | 按编码 |
| 非 TTY（管道 / CI） | 无 | 不显示 | **不折行** | 按编码 |
| 宽度未知（`COLUMNS` 未设） | 按深度 | **不显示** | 不折行 | 按编码 |

「宽度未知则不显示状态行」是刻意的：状态行需要知道宽度才能截断，
未知宽度下它可能折成两行，反而破坏底部保留区的假设。

### 5.2 编码探测

探测的是「JVM 写 stdout 使用的字符集能否表示该字符」，用
`Charset.newEncoder().canEncode(...)` **实测**而非猜测：

```java
DECORATION = "❯✓•─│├└";   // → symbols：决定是否降级为 ASCII
CJK_SAMPLE = "中文字符";   // → cjk：决定是否提示切换 UTF-8
```

| 结果 | 影响 |
|---|---|
| `symbols == false` | 列表符号 `•` → `-`；`✓` → `[ok]`；分隔线 `─` → `-`；转圈帧降级 |
| `cjk == false` | 打印纯 ASCII 的编码切换提示（`chcp 65001` / `[Console]::OutputEncoding`） |

字符集不可得时**返回 `true`**：宁可少降级、不误降级，也不必因为无法判断去打扰用户。

### 5.3 启动标志（两种风格 + 宽度门槛）

> 像素风的画法、调色板、复现与漂移检测见 [PixelLogoDesign.md](PixelLogoDesign.md)。

标志有两种风格，**同一份几何**、不同的画法，可现场切换：

| 风格 | 画法 | 尺寸 | 依赖 |
|---|---|---|---|
| **像素风**（默认） | 半块字符 `▀`，粗像素格、硬边界、平色 | 48x48 像素 → 48 列 x 24 行；降采样档 24x24 → 24 列 x 12 行 | `▀` + 256 色 |
| 线框风 | 纯 ASCII 线框 | 23 列 x 16 行；紧凑档 17 列 x 9 行 | 无 |

切换：`aha chat --logo auto|pixel|ascii|off`（默认 `auto`）。

- `auto`：终端支持符号且着色 → 像素风；否则线框风
- `pixel` / `ascii`：强制某一种（`pixel` 在无符号终端下不显示标志）
- `off`：不显示标志

**为什么像素风要挂在能力门禁后面**：它靠颜色成形（透明像素走终端默认色 `39`/`49`，不画底卡），
控制台不支持 `▀` 时强行输出会烂成乱码——启动横幅烂成乱码比朴素更糟。

**为什么像素风不采样 `Logo.svg`**：终端里的像素艺术是<b>按格摆</b>出来的。采样会把
`AHA` 点阵糊掉、把 1 像素宽的光线抹平。因此光线走 Bresenham、灯泡用整数圆、
字样与笑脸直接贴点阵。两档尺寸取自同一份 48x48 网格，24x24 是它的 2:1 **精确降采样**，
不做二次描画，形状不会走样。

**宽度门槛**：`终端宽 − 1（右边距）− 标志宽 − 顶栏宽 ≥ 4（最小间隔）`。
按候选顺序（48x48 → 24x24 → 线框完整 → 线框紧凑）取第一个放得下的；都放不下则只有信息栏。
实测顶栏 53 列时：48x48 需要 ≥ 109 列，24x24 需要 ≥ 85 列，线框完整 ≥ 83 列，紧凑 ≥ 74 列。

---|---|---|
| 完整 | 22 列 × 14 行 | 左栏宽 + 27 |
| 紧凑 | 13 列 × 9 行 | 左栏宽 + 18 |
| 不显示 | — | 更窄 |

判定式：`终端宽 − 1（右边距）− 标志宽 − 左栏宽 ≥ 4（最小间隔）`。
实测顶栏 53 列（常见配置）时：**完整 ≥ 80 列、紧凑 ≥ 71 列**，更窄则只有信息栏。

**为什么用纯 ASCII 而不是 Unicode 方块**：`▀ ▄ █` 在非 UTF-8 代码页下会整片退化成 `?`，
而启动横幅正是用户最先看到的东西——烂成一排问号比没有标志更糟。纯 ASCII 在任何代码页下
都能显示，代价是图形细节少一些。

**为什么着色分四档**：图形取自 `Logo.svg` 的琥珀色系，按「光线 → 灯泡 → 灯座 → 字样」
四挡明度上色（`Style#logoRay` / `#logoBulb` / `#logoBase` / `#logoWord`）。纯 ASCII 图
本身没有明暗，层次只能靠色阶拉开；不着色时仍是可辨认的灯形。
