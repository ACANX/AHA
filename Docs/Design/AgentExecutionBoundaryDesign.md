## 0. 本文定位

本文定义 **Agent 执行边界（Agent Execution Boundary）**：让「Agent 不在本地跑 Maven 编译 / 测试」
从一条**文字约定**，变成 Agent 运行环境里的**能力约束**。

三件事先写清楚：

1. **这不是「反 Maven」**，也不是要限制人类开发者。人类域完整保留 JDK 与 Maven，本地构建、
   本地测试、IDE 一切照旧。
2. **这不是「防 Agent 作恶」的安全边界**，而是**工程效率边界**：把「重复劳动、与 CI 竞争、
   结论不权威」的默认路径堵死。它不承诺对抗性安全（见第 8 节）。
3. **验收标准在别处**：真正决定代码对错的仍是 CI 的 `Build.yml` / `Gate.yml` / `Compat.yml`
   （见 [BuildSpec.md](../DevSpec/BuildSpec.md) §8）。本设计只保证「本地那条路走不通」。

关联：来源 Issue #70；提示层（`AGENTS.md`、DevSpec、`.agents/skills/build|test`）已在前序工作中收紧。

## 1. 问题与背景

### 1.1 现象

在 #67（供应商五档模型）的实现过程中，Agent 反复在本地执行 `./mvnw ... test` / `clean test`。
后果：

- **慢**：本项目一次全量构建在慢文件系统上可达分钟级；
- **重复**：同一份编译 / 测试，CI 每次 push 都会跑；
- **结论不权威**：本地环境（JDK、Maven 版本、缓存、平台）与 CI 不同，本地绿不等于 CI 绿；
- **不可追溯**：本地结果没有记录，事后无从判断「到底验过没有」。

### 1.2 为什么「写进 AGENTS.md」不够

`AGENTS.md` 是**提示**（prompt），不是**机制**（enforcement）。它有效，但有三个固有上限：

1. 长上下文、赶进度时，指令权重会被稀释；
2. 不同 Agent 工具对上下文文件的读取时机、截断策略不一致；
3. 提示只能约束「知道并愿意遵守」的执行者，无法阻止「顺手跑一下」。

结论：提示层要保留（它解释了「为什么」），但不能作为**保证**。

### 1.3 约束空间：Agent 工具矩阵（本机实测）

| 工具 | 本机位置 | 原生拦截机制 | Agent 可在本机配置 |
|---|---|---|---|
| pi | WSL `~/.pi/agent/extensions/` | `tool_call` 事件可返回 `{ block: true }` | ✅ |
| Claude Code | WSL `~/.claude/settings.json` | `permissions.deny` | ✅ |
| Codex | WSL `~/.codex/rules/*.rules` | `prefix_rule(pattern=[...], decision=...)` | ⚠️（`deny` 关键字待验证） |
| OpenCode | Windows `/mnt/d` | 项目级配置 / 未知 | ❌ 家规禁止访问 `/mnt` |
| DSH | Windows `/mnt/d` | 未知 | ❌ 同上 |

这张表本身就是结论：**按工具逐个打补丁的方案不可行**——

- **数量**：新增工具、工具升级都要重配；
- **覆盖**：Windows 侧两个工具处在 Agent 无权访问的区域（见 `/data/Agent/CNXNC/AGENTS.md`
  第二节环境边界），无法配置、也无法验证；
- **一致性**：五套机制的语义、优先级、失效方式各不相同，无法证明它们等价。

### 1.4 目标与非目标

**目标**

| # | 目标 | 判据 |
|---|---|---|
| G1 | 任何 Agent 工具、任何仓库，在本地构建 / 测试上**能力为零** | 域内 `./mvnw`、`sh ./mvnw`、`mvn`、`java`、`javac` 均失败 |
| G2 | 人类开发者**零影响** | 域外 `./mvnw` 行为与今天完全一致 |
| G3 | **不改写工作区文件** | 域内 `git status` 干净，不存在误提交 |
| G4 | 保留完整「改代码 → 推送 → 看 PR checks」闭环 | 域内 `git` / `gh` / `python3 bin/Check*.py` 可用 |
| G5 | 边界自身**可自证**，失效时可被发现 | 自证脚本；故意移除隔离时必须失败 |
| G6 | 不依赖任何 Agent 工具的插件 / 配置 | 新增工具无需改配置 |

**非目标**

- 不做对抗性安全（Agent 有意绕过不在威胁模型内）；
- 不改变 CI 的构建 / 测试内容；
- 不替代 `AGENTS.md` 的说明职责；
- 不强制人类使用沙箱。

## 2. 设计原则

| # | 原则 | 说明 |
|---|---|---|
| P1 | **约束执行域，而不是约束工具** | 约束放在「Agent 在哪个域里跑」，工具只是域内的进程 |
| P2 | **能力剥离优先于规则禁止** | 「不存在 Maven/JDK」比「禁止执行 Maven」更可靠、更少误判 |
| P3 | **单一强制点** | 内核进程创建层（命名空间 / 挂载），一处配置全局生效 |
| P4 | **工作区保真** | 任何改写工作区文件的手段一律否掉（会污染 git） |
| P5 | **双域对称** | 人不降级、Agent 降级；边界是「域」的属性而非「用户」的 |
| P6 | **边界必须自证** | 隔离效果由脚本断言并进 CI，避免静默失效 |
| P7 | **可逆、最小惊讶** | 一个启动器即边界；域外行为零变化；随时可退出 |

## 3. 威胁模型与失败模式

### 3.1 威胁

| 编号 | 威胁 | 后果 |
|---|---|---|
| T1 | Agent 图省事，在本地跑构建 / 测试 | 资源浪费、与 CI 重复、结论不权威 |
| T2 | Agent 声称「本地已通过」，实际未跑或环境不同 | 误导评审 |
| T3 | Agent 在工作区留下构建副产物 | 污染 diff、误提交 |

### 3.2 失败模式清单（设计时必须逐条有对策）

| 编号 | 失败模式 | 对策 | 状态 |
|---|---|---|---|
| F1 | 改写工作区文件（如把 `mvnw` 换成桩）被 **git 视为修改** | **不改工作区**；改为剥离工具链（P4） | ✅ v3 已解决 |
| F2 | `sh ./mvnw` 绕过「去掉执行位」 | 不依赖执行位；用「无 JDK」使其必然失败 | ✅ |
| F3 | Agent 用绝对路径 JDK（`/usr/local/java/...`） | 以 `--tmpfs` 隐藏常见 JDK 根目录 | ✅ |
| F4 | Agent 自行 `curl` 下载 JDK 或 Maven | 属对抗性绕过；P3 加网络出口限制或遮蔽下载工具 | ⏳ P3 |
| F5 | 内核不允许 unprivileged userns | 启动器探测失败即明确报错；退化到容器方案（P2） | ✅ 探测 + 文档 |
| F6 | Windows 侧原生 Agent 不在命名空间内 | 域外覆盖不到；P2 用等价容器 / 受限账户，或让工具经 `wsl` 调用 | ⏳ P2 |
| F7 | 自证脚本静默失效（隔离没了却仍绿） | 自证必须包含**反向用例**：故意放开时必须失败 | ✅ 设计要求 |
| F8 | PATH 前置桩被 Agent 覆盖 | 桩只用于「给出指引」；真正的拦截靠「工具链不存在」 | ✅ |
| F9 | 误伤人类（人类在沙箱里跑） | 人类默认不进沙箱；沙箱提供 `--allow-jdk` 等显式放宽开关 | ✅ |

## 4. 候选方案与决策

### 4.1 方案 A：逐工具 hook / deny

- **做法**：pi 扩展、Claude Code `permissions.deny`、Codex `prefix_rule`、OpenCode 配置……
- **优点**：贴近各工具，可给出丰富提示。
- **否决理由**：数量不可控（见 §1.3）；Windows 侧不可达；语义不等价；G6 不满足。
- **保留价值**：作为**纵深防御的补充层**，不作为主机制。

### 4.2 方案 B：仓库级 `mvnw` 守卫

- **做法**：给 `mvnw` 加守卫，本地非 CI 时拒绝 build/test。
- **优点**：跨工具（谁都经过 `./mvnw`）；实现简单。
- **否决理由**：① 需改 Maven Wrapper 文件，`mvn wrapper:wrapper` 会覆盖；
  ② 只覆盖单个仓库；③ 人类本地构建也要被拦（或需额外开关）；④ 拦不住系统 `mvn`。
- **保留价值**：可作为单仓库的**最后一道补充**（P3 可选）。

### 4.3 方案 C：文件视图改写（`--ro-bind` 覆盖 `mvnw`）

- **做法**：在命名空间内把 `mvnw` 绑定为拒绝桩。
- **否决理由**：**F1 实测命中**——域内 `git status` 把 `mvnw` / `mvnw.cmd` 判为已修改
  （inode 与内容都变），存在被 Agent 误提交的风险；`sh ./mvnw`（F2）也能穿过。
- **教训**：这是「看起来能落地」与「能落地」的分界，已记入 §7。

### 4.4 方案 D：能力剥离 + 命名空间（**采纳**）

- **做法**：用 `bwrap` 构造受限执行域：隐藏 JDK 与 `/mnt`，`JAVA_HOME` / `PATH` 前置到拒绝桩。
- **优点**：工具无关（P1/P3）；不改工作区（P4，F1 解决）；WSL 原生零依赖；
  能给出明确指引；顺带落实「WSL 之外不可见」的家规。
- **代价**：依赖 Linux 命名空间（F5）；Windows 侧覆盖不到（F6）。

### 4.5 方案 E：容器化（devcontainer / Docker）

- **做法**：Agent 在容器内运行，镜像**不装 JDK 与 Maven**。
- **优点**：跨平台标准；Windows 侧也能用（F6）；能力剥离更彻底。
- **代价**：本机 Docker CLI 位于 Windows 侧（`/mnt/c`），Agent 无法在 WSL 内构建 / 验证镜像；
  体积与启动开销更大。
- **定位**：**P2**，与方案 D 并存（同一设计原则，不同实现载体）。

### 4.6 方案 F：内核级路径禁止（AppArmor / seccomp / LSM）

- **现状**：本机 `AppArmor: 不可用`；seccomp 需进程自我加载，不满足 P3。
- **定位**：不可用，记录备查。

### 4.7 决策矩阵

| 方案 | 工具无关 | 不改工作区 | 人类零影响 | 本机可落地 | Windows 侧 | 结论 |
|---|---|---|---|---|---|---|
| A 逐工具 hook | ✗ | ✓ | ✓ | 部分 | ✗ | 补充层 |
| B `mvnw` 守卫 | ✓（单仓库） | ✓ | 需开关 | ✓ | ✗ | 可选兜底 |
| C 文件视图改写 | ✓ | **✗** | ✓ | ✓ | ✗ | 否决（F1/F2） |
| **D 命名空间能力剥离** | **✓** | **✓** | **✓** | **✓** | ✗ | **采纳（P0/P1）** |
| E 容器化 | ✓ | ✓ | ✓ | ✗（本机） | ✓ | P2 |
| F 内核 LSM | ✓ | ✓ | ✓ | ✗ | ✗ | 不可用 |

## 5. 架构

### 5.1 三域模型

```
┌──────────────────────────────────────────────────────────────┐
│  人类域（宿主 WSL）                                            │
│  JDK / Maven / /mnt / IDE      ← 人的本地构建、本地测试        │
│                                                              │
│   ┌────────────────────────────────────────────────────┐     │
│   │  Agent 域（bwrap 命名空间）                          │     │
│   │  git / gh / python / 编辑器 / 工作区（可写）          │     │
│   │  ✗ JDK   ✗ Maven   ✗ /mnt   桩：java/mvn/mvnw       │     │
│   │  → 改代码 → 推送 → 等 PR checks                       │     │
│   └────────────────────────────────────────────────────┘     │
└──────────────────────────────────────────────────────────────┘
                              │ push
                              ▼
┌──────────────────────────────────────────────────────────────┐
│  CI 域（GitHub Actions）                                       │
│  Build.yml（编译+单测） / Gate.yml（verify+覆盖率） / Compat.yml │
│  → 唯一权威结论；失败即卡点                                     │
└──────────────────────────────────────────────────────────────┘
```

### 5.2 组件与职责

| 组件 | 职责 | 位置 |
|---|---|---|
| `AgentSandbox.sh` | 建立 Agent 域并启动目标命令 | `bin/`（P1） |
| 拒绝桩 | 命中即输出「去 CI」指引并非零退出 | 运行时临时目录 |
| shell 集成 | 让 `pi` / `claude` / `codex` 自动进域 | `~/.bashrc` 函数或 PATH shim（P1） |
| 自证脚本 | 断言隔离有效 + 反向用例 | `bin/CheckAgentBoundary.py`（P1） |
| `AGENTS.md` 声明 | 告知 Agent 所在域与正确流程 | 仓库根（P1） |
| CI 卡点 | 最终质量门禁 | `.github/workflows/`（已有） |

### 5.3 启动时序

```
用户/工具 → AgentSandbox.sh
             ├─ 探测 bwrap（无 → 明确报错退出，F5）
             ├─ 建临时桩目录（java/javac/mvn/mvnw/gradle）
             ├─ 组装命名空间：
             │    --tmpfs /mnt                     （F6 之外的 Windows 隔离）
             │    --tmpfs <每个存在的 JDK 根>       （F3）
             │    --setenv JAVA_HOME <桩 jdk>
             │    --setenv PATH <桩 bin>:$PATH
             └─ exec bwrap ... -- <目标命令>
                                    └─ Agent 在此域内工作
```

## 6. 详细设计

### 6.1 启动器接口

```
agent-sandbox [--repo <目录>] [--allow-mnt] [--allow-jdk] -- <命令...>
```

| 参数 | 默认 | 说明 |
|---|---|---|
| `--repo` | `$PWD` | 预留：后续可对指定仓库做附加约束 |
| `--allow-mnt` | 关 | 允许看到 `/mnt`（默认不可见） |
| `--allow-jdk` | 关 | 允许使用宿主 JDK（调试用；默认隐藏） |
| `--` 之后 | — | 在域内执行的命令与其参数 |

退出码约定：`0` 正常；`64` 用法错误；`69` 缺少 `bwrap`；`97` 命中拒绝桩。

### 6.2 剥离项清单

| 类别 | 处理 | 理由 |
|---|---|---|
| 宿主 JDK 目录 | `--tmpfs` 隐藏 `/usr/lib/jvm`、`/usr/local/java`、`/opt/java`、`/opt/jdk` | 使 `mvnw` / `mvn` 无 JVM 可用（F2/F3） |
| `JAVA_HOME` | 指向桩 JDK（内含 `bin/java` 桩） | 让 `mvnw` 走到桩并给出指引，而非晦涩报错 |
| `PATH` | 前置桩目录，含 `java` / `javac` / `jar` / `mvn` / `mvnw` / `mvnw.cmd` / `gradle` | 直接调用也命中桩 |
| `/mnt` | `--tmpfs` 隐藏 | Windows 盘不可见，顺带落实环境边界 |
| 工作区文件 | **不动** | P4 / F1 |

### 6.3 桩的输出契约

```
[agent-sandbox] 已拦截：Agent 执行域不提供本地 Maven / JDK 构建工具链。
                 请推送分支后看 PR 的 CI checks（Build.yml / Gate.yml），失败再按 CI 日志排查。
```

- 输出到 stderr（不污染 stdout 管道）；
- 退出码固定 `97`，便于上层识别「被边界拦截」而非「构建失败」；
- **只给指引、不做判断**，不使用 `System.exit` 之外的副作用。

### 6.4 开关与环境变量

| 名称 | 作用 |
|---|---|
| `AGENT_SANDBOX_REPO` | 未传 `--repo` 时的默认仓库 |
| `--allow-jdk` | **完全放开宿主 JDK（仅人排障）**：会使 `./mvnw` 也随之可达，即主动放弃 G1。**Agent 不得使用**。 |

### 6.5 shell 集成（待定，见开放问题）

两种备选：

| 方式 | 覆盖 | 代价 |
|---|---|---|
| `~/.bashrc` 函数包装 `pi` / `claude` / `codex` | 仅交互 shell | 轻；子进程 / 非交互启动不生效 |
| PATH shim（`~/.local/bin/pi` 等包装脚本） | 所有调用 | 硬；需维护与真实入口的映射 |

### 6.6 自证设计（P1）

`bin/CheckAgentBoundary.py` 需断言：

1. 域内 `./mvnw`、`sh ./mvnw`、`mvn`、`java`、`javac` 都返回 `97`；
2. 域内 `git status --short` 为空；
3. 域内 `/mnt` 为空；
4. 域内 `git` / `gh` / `python3 bin/Check*.py` 可用；
5. **反向用例**：带 `--allow-jdk` 时 `java` 可用——证明断言真的在起作用（防 F7）；
6. 平台为 Linux 且 `bwrap` 不存在时，脚本**跳过并明确标注**，而不是判绿。

### 6.7 CI 集成（P1）

在 `Gate.yml` 增加一条 `agent-boundary` 作业（或并入既有文档 / 脚本检查）：
运行自证脚本；由于 GitHub runner 允许 userns，可直接执行。

## 7. POC 实测证据

参考实现：`bin/AgentSandbox.sh`（本设计的 P0 产物）。实测记录：

```
$ agent-sandbox --repo <AHA> -- bash -c './mvnw -v'
[agent-sandbox] 已拦截：Agent 执行域不提供本地 Maven / JDK 构建工具链。
                 请推送分支后看 PR 的 CI checks（Build.yml / Gate.yml），失败再按 CI 日志排查。
exit=97
```

| 检查项 | 实测结果 |
|---|---|
| `./mvnw -v` | ⛔ 拦截（exit 97） |
| `sh ./mvnw -v` | ⛔ 拦截（F2 已封堵） |
| `mvn` / `java` / `javac` | ⛔ 不可用 |
| `git status --short` | ✅ 干净（F1 已封堵） |
| `ls /mnt` | ✅ 空（Windows 盘不可见） |
| `git` / `gh` / `python3 ...` | ✅ 可用 |
| `--allow-jdk` 时 `java` | ✅ 可用（反向用例：证明拦截真的在起作用） |
| `--allow-jdk` 时 `./mvnw` | ⚠️ 同样可达 —— 因为 `./mvnw` 靠 java 运行，放开 JDK 等于放弃 G1；仅供人排障 |

> **已踩的坑（必须留痕）**：第一版用 `--ro-bind /bin/false <repo>/mvnw`，
> 功能上拦住了，但域内 `git status` 把 `mvnw` / `mvnw.cmd` 判为已修改（F1），
> 且 `sh ./mvnw`（F2）可绕过。这直接导致设计原则 P4 的诞生。

## 8. 边界、残余风险与已知绕过

- **Windows 侧原生 Agent**（OpenCode / DSH）不在命名空间内：P2 用容器 / 受限账户，或让其经
  `wsl` 调用命令；其配置位于 `/mnt/d`，按环境边界不由 Agent 触碰。
- **自行下载工具链**（F4）：属对抗性绕过；P3 可加网络出口限制或遮蔽 `curl` / `wget`。
- **userns 不可用**（F5）：启动器明确报错并给出容器替代路径，不静默降级。
- **不是安全边界**：本设计的目标是「默认路径不可行」，不承诺对抗恶意绕过；
  真正不可绕过的卡点始终是 CI（分支保护的必需检查）。
- **可逆**：删除启动器 / 不使用沙箱即恢复正常，无残留状态。
