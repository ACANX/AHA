## 1. 目标

**在发布 1.0 正式版之前，AHA 必须完成自举（Self-Hosting）：**

> 项目自身的日常开发、测试、构建、发布，以及后续 AHA 功能的迭代与升级，
> 全部由 AHA 工具链（CLI + 技能体系 + 内置工具 + 记忆与会话）完成，
> 不再依赖 Claude Code、Cursor、GitHub Copilot Workspace 等其他 Agent Harness。

这是 1.0 的**硬门槛**，不是加分项。1.0 若未达成自举，不得发布正式版。

术语说明：本文的「自举」等同于业界常说的 self-hosting / bootstrapping；
「其他 Harness」指一切非 AHA 的编码 Agent 工具。

## 2. 为什么把自举设为 1.0 硬门槛

| 理由 | 说明 |
|---|---|
| 稳定性的唯一可信证明 | 1.0 声称稳定。开发者自己都不用它，稳定性无从验证 |
| 能力完备性的最严格检验 | 自举会以最短路径暴露缺口：工具不足、技能缺失、记忆检索弱、权限确认打断心流、会话无法恢复……任何一项都会立刻卡住 |
| 需求来源更可靠 | 自举过程中暴露的是**真实且高频**的需求，比闭门规划的 roadmap 更可靠 |
| 防止能力自嗨 | 没有自举约束，容易做出"看起来很全但没人用"的功能 |
| 对外可信度 | 一个 Agent Harness 若不能跑自己，很难说服他人用它跑生产项目 |
| 回归保护 | 自举成为每日强制回归：任何破坏可用性的改动会在次日被立即发现 |

## 3. 自举层级

自举不是开关，而是逐级推进。每一级既是上一级的验证，也是下一级的前提。

| 层级 | 名称 | 版本区间 | 自举范围 | 升级门禁 |
|---|---|---|---|---|
| **L0** | 手工 | 0.1（现状） | 完全依赖其他 Harness | — |
| **L1** | 可读 | 0.2 | 用 AHA 读代码、检索、解释结构、起草文档 | 单次会话内完成只读任务且无需回退 |
| **L2** | 可改 | 0.3 ~ 0.4 | 用 AHA 完成小范围代码修改并跑通测试 | 连续 10 个 PR 由 AHA 产出且 CI 通过 |
| **L3** | 可交付 | 0.5 ~ 0.7 | 用 AHA 完成一次完整功能（代码 + 测试 + 文档 + CHANGELOG） | 一个完整 minor 版本的全部提交由 AHA 产出 |
| **L4** | 全自举 | 0.8 ~ 1.0 | 用 AHA 完成 AHA 自身的迭代与发布 | 连续一个 minor 周期（≥ 4 周）零外部 Harness |

层级不可跳跃：未达成 L2 就宣称 L4，等价于没有自举。

**范围限定**：1.0 的自举仅限**本地 runtime**。远程执行（`aha-remote`）、WSL、调度、云函数等能力计划在 1.1 之后交付，因此不得作为 1.0 自举的前置依赖。

## 4. 验收标准

发布 1.0 前必须**同时**满足以下全部条件：

| 编号 | 标准 | 验证方式 |
|---|---|---|
| A1 | **工具完备**：文件读写、命令执行、HTTP、记忆写入与检索、会话恢复均可用且权限受控 | `aha tool list` 覆盖上述能力；权限策略在非交互场景可稳定放行 |
| A2 | **技能完备**：`build` / `test` / `release` 技能能驱动完整交付闭环 | 用三个技能各完成一次真实任务，无需查阅文档外知识 |
| A3 | **持续性**：连续 ≥ 4 周、≥ 30 次提交由 AHA 产出，期间不启动其他 Harness | `git log` 审计 + 会话记录 |
| A4 | **质量不降级**：自举产出的提交，CI 通过率与人工产出无显著差异（评审一次通过率 ≥ 80%） | CI 历史统计 + 评审记录 |
| A5 | **发布闭环**：至少 1 个 minor 版本的完整发布流程由 AHA 驱动（分支 → 版本号 → CHANGELOG → tag → CI） | 发布记录可追溯 |
| A6 | **可审计**：能从事后证据中区分 AHA 产出与人工产出 | 提交信息约定 + 会话日志留存 |

### 4.1 提交信息约定

为满足 A6，自举期间的提交信息须标注产出方式：

```
<type>(<scope>): <subject>

Harness: aha/<version>        # 由 AHA 产出时标注
Session: <session-id>         # 可选，便于回溯会话
```

人工提交不标注 `Harness` 行。该约定用于统计与审计，不参与 CI 门禁。

## 5. 反向指标

以下任一情况出现，即判定该层级**未达标**，需回退层级并补齐缺口：

- 某类任务必须切回其他 Harness 才能完成
- 关键任务只能在 AHA 之外手工完成（如改构建脚本、写发布说明）
- 需频繁人工介入才能维持会话（上下文丢失、记忆检索不到既往决策）
- 为绕开 AHA 的限制而降低交付标准（少写测试、跳过文档）
- 自举期间的 CI 失败率显著高于历史水平

## 6. 缺口与补齐路径

相对 0.1 现状，达成 L4 的主要缺口：

| 缺口 | 阻碍层级 | 补齐版本 | 说明 |
|---|---|---|---|
| 交互式 `chat` 未做真实 TTY 联调 | L1 | 0.1.x | 自举的入口能力，必须最先稳固 |
| 记忆检索仅 `LIKE`，无相关性排序 | L1 / L3 | 0.6（向量 + RAG） | 检索不到既往决策会导致重复劳动 |
| 扩展运行时未实现 | L2 | 0.3 | 自举过程中扩展能力的载体 |
| 权限确认在批量任务下频繁打断 | L2 | 0.5 | 需要可信目录 + 细粒度白名单 |
| 无 `aha doctor` 环境预检 | L2 | 0.8 | 环境问题应在会话开始前暴露 |
| 事件总线与生命周期钩子 | L3 | 0.4 | 支撑长链路任务的可观测性 |
| 无成本与用量可视化 | L3 | 0.8 | 自举是高频使用，需控制 token 开销 |
| 缺少长任务会话恢复 | L3 | 0.6 | 跨会话续做同一任务 |
| 发布流程未脚本化 | L4 | 0.8 ~ 1.0 | A5 的前置 |

## 7. 度量方法

自举度量的数据来源与计算方式：

| 指标 | 数据来源 | 计算方式 |
|---|---|---|
| 提交产出占比 | `git log` | 含 `Harness:` 行的提交 / 总提交 |
| 连续自举天数 | `git log` 时间戳 | 最长连续无人工提交区间 |
| CI 通过率 | CI 历史 | 首次通过的构建数 / 总构建数 |
| 评审一次通过率 | PR 记录 | 无需修改即合并的 PR / 总 PR |
| 回退次数 | 会话记录 | 切换到其他 Harness 的次数（目标 0） |
| 人工介入频次 | 会话记录 | 每千行改动的干预次数 |

度量结果按 minor 版本记录到本文件下方「自举进度」小节。

## 9. 风险

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| 自举门槛被事后放宽 | 1.0 名不副实 | 验收标准写入本文档，发布检查清单强制勾选 |
| 为达成自举而堆砌功能 | 背离用户价值 | 缺口清单以自举实践暴露为准，不预先扩张 |
| 自举期间效率显著低于其他 Harness | 项目进度受阻 | 允许过渡期并行；但 L4 要求连续零回退 |
| 记忆检索不足导致重复劳动 | 自举体验差 | 0.6 优先向量检索；过渡期用显式决策文档补偿 |
| 高频使用导致 token 成本失控 | 成本压力 | 0.8 交付用量可视化与预算告警 |
| 自举结论不可信（无法区分产出方） | 验收无据 | A6 提交信息约定 + 会话日志留存 |
