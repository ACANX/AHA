# TS-2610-025 · 原生桌面端主题不跟随系统、切换残留与暗色标题对比度

## 1. 背景

issue #44（真机，Windows 11 + 原生镜像）：原生桌面端已能正常开窗并加载界面，但暴露出四类界面问题：

1. **默认主题恒为暗黑**，与系统当前的浅色皮肤不一致；
2. **从暗黑切到亮色后，部分组件背景仍是暗色**（切换不彻底）；
3. **暗色模式下部分标题文字是深色系**，与深色背景对比度不足，肉眼难以分辨；
4. **字体清晰度 / 字体本身与 JVM（jar）模式差距明显**。

JVM 模式下的截图作为对照：同一台机器、同一份配置，JVM 模式是浅色且字体清晰。

## 2. 排障过程与修复链

### 2.1 先分清「四类问题里哪些是确定性缺陷」

第 4 类（字体）只在原生镜像里出现，属于渲染管线 / 字体枚举层面的差异；
本机（WSL，无 Windows 图形环境）无法复现，因此本次不动它，转入 `N-24` 跟踪。
其余三类都能在源码里定位到确定原因，逐条修。

### 2.2 第 1 类：默认主题恒暗

`DesktopSettings` 的默认主题本就是 `SYSTEM`，问题出在 `SystemTheme.prefersDark()`：
读不到系统配色（`getColorScheme()` 为 `null`、或系统偏好尚未就绪、或原生镜像里读取失败）
时，**一律返回暗色**。JVM 模式能读到 `LIGHT`，原生镜像读到空，于是同一台机器上
两种模式一浅一深。

修法：三级回退——

1. 配色明确为 `DARK` / `LIGHT` → 直接采用；
2. 配色未定 → 用系统**背景色**的亮度判断（同一份系统偏好数据，能兜住第一种的空白）；
3. 都取不到 → **亮色**（Windows 与主流桌面的出厂默认；旧实现猜暗色的代价已在真机上被证实）。

另加 `SystemTheme.onColorSchemeChanged(Runnable)`：订阅 `colorSchemeProperty()`，
在「跟随系统」模式下用户于系统设置里切换深色 / 浅色皮肤时实时重刷界面
（回调在界面线程触发；仅当主题仍为 `SYSTEM` 时应用，不覆盖用户手动选择）。

### 2.3 第 2 类：切换亮色后部分组件仍是暗色

两处原因：

- **硬编码颜色**：`DesktopShell` 3 处边框写死 `#3A3A3A`、`ProviderDialog` 1 处背景写死 `#1E1E1E`。
  它们虽然走了 `themed(...)` 登记，但每次重刷写回的还是暗色常量，切到亮色自然「没变」。
  改为读 `Palette.BORDER` / `Palette.BASE`。
- **未登记 / 未重刷的常驻节点**：
  - `CompletionPopup` 是常驻实例，样式在构造时一次性写入，换主题后不会重建 →
    新增 `refreshTheme()`，由 `DesktopShell.applyTheme` 调用；
  - 会话右键菜单（`ContextMenu`）有独立的场景根，不继承主窗口主题 →
    改为在 `setOnShowing` 时套上当前配色，保证每次弹出都是当前主题。

### 2.4 第 3 类：暗色下标题文字对比度不足

逐个排查后发现：右栏「本轮」标题、左右两条折叠按钮是**仅有的没有走 `themed(...)` 登记**
的裸控件，因此一直用 JavaFX 默认文字色（深色系），在深色底上几乎看不见。
现统一登记主题：标题用 `Palette.FOREGROUND` 加粗，折叠按钮改为透明底 + `Palette.MUTED`。

### 2.5 第 4 类：字体差异（本次不修）

字体清晰度 / 字体本身与 JVM 模式的差距，只在原生镜像里出现。可能的方向有三条，
但都需要真机对照才能定位：

- Prism 渲染管线是否回退到软件管线（软件管线没有次像素抗锯齿，字会明显发虚）；
- 原生镜像下的字体枚举 / 默认字体解析是否与 JVM 模式不同；
- 高分辨率缩放比的读取是否一致（窗口尺寸计算已经处理过，但字体栅格化是另一条路径）。

已另开 **issue #48** 长期跟踪（现象、背景、待排查方向与验收标准均写在该 Issue 正文里），
`Docs/TODO.md` 的 `N-24` 只作索引。

## 3. 最终验证结果

- 本次改动只涉及桌面端界面层，未触碰反射 / JNI 元数据与构建参数；
- 按 ACANX 的要求，本地不跑构建与测试，编译与全量测试交由 PR 的持续集成执行
  （`Build` 六条腿 + `CodeQL`）；
- 真机验收（下载合入后自动产出的 Windows 原生包）：
  ① 默认启动主题与系统一致；
  ② 切到亮色后三栏边框、工具卡片、候选弹层、右键菜单全部跟着变；
  ③ 深色模式下「本轮」标题与折叠按钮清晰可读；
  ④ 字体差异仍在，转 issue #48。

## 4. 关键教训

1. **「兜底值」也是一种产品决策**：`prefersDark()` 回退暗色，当初的理由是「猜错代价最小」，
   但真机上它就是「每次启动都猜错」。兜底应当选**出厂默认**，并留一条能自我纠正的订阅。
2. **内联样式 + 逐节点登记的主题方案，漏一个节点就是一个永久缺陷**：裸控件（不登记）
   与硬编码常量是同一个病的两种表现。本次把仅剩的裸控件补齐；后续新增控件必须走 `themed(...)`。
3. **弹层是独立的场景根**：`Dialog` 早已处理，但 `Popup`（候选弹层）与 `ContextMenu`（右键菜单）
   同样不会继承主窗口样式——这类「看不见的场景根」是主题缺陷的高发区。
4. **遗留问题要开 Issue，不能只写进 TODO**：`TODO.md` 是暂存区，长期条目会被后续条目淹没；
   本次字体问题已单开 issue #48 长期跟踪，并把「未闭环问题必须开 Issue」写进项目 `AGENTS.md`。

## 结论分层

### 已观测事实

- issue #44（真机，Windows 11 + 原生镜像）暴露出**四类**界面问题：
  ① 默认主题**恒为暗黑**，与系统当前的浅色皮肤不一致；
  ② 从暗黑切到亮色后，**部分组件背景仍是暗色**；
  ③ 暗色模式下**部分标题文字是深色系**，对比度不足；
  ④ **字体清晰度 / 字体本身**与 JVM（jar）模式差距明显。
- **对照样本**：同机、同配置下 JVM 模式的截图是**浅色且字体清晰**——一浅一深、一清一虚。
- 第 1 类的确定原因：`DesktopSettings` 的默认主题**本就是 `SYSTEM`**，
  问题出在 `SystemTheme.prefersDark()`——读不到系统配色（`getColorScheme()` 为 `null`、
  系统偏好尚未就绪、或原生镜像里读取失败）时**一律返回暗色**；
  JVM 模式能读到 `LIGHT`，原生镜像读到空。
- 第 2 类的两处原因：
  - **硬编码颜色**：`DesktopShell` **3 处**边框写死 `#3A3A3A`、`ProviderDialog` **1 处**背景写死 `#1E1E1E`
    ——它们虽走了 `themed(...)` 登记，但**每次重刷写回的还是暗色常量**；
  - **未登记 / 未重刷的常驻节点**：`CompletionPopup` 是常驻实例（样式在构造时一次性写入，
    换主题后不会重建）；会话右键菜单（`ContextMenu`）**有独立的场景根**，不继承主窗口主题。
- 第 3 类的确定原因：右栏「本轮」标题、左右两条折叠按钮是**仅有的没有走 `themed(...)` 登记**
  的**裸控件**，因此一直用 JavaFX 默认文字色（深色系）。
- 第 4 类（字体）**本机无法复现**（WSL 无 Windows 图形环境）⇒ 本次**不动**，
  转 `Docs/TODO.md` **N-24** 作索引，并另开 **issue #48** 长期跟踪，
  三条待排查方向写在 issue 正文里：Prism 是否回退**软件管线**（软件管线没有次像素抗锯齿）、
  原生镜像下的**字体枚举 / 默认字体解析**是否与 JVM 模式不同、**高分辨率缩放比**的读取是否一致。
- 验证口径：本次改动**只涉及桌面端界面层**，未触碰反射 / JNI 元数据与构建参数；
  **按 ACANX 的要求本地不跑构建与测试**，编译与全量测试交由 PR 的持续集成执行
  （`Build` 六条腿 + `CodeQL`）；真机验收四项（默认主题与系统一致 / 切亮色后各处跟着变 /
  暗色下标题与折叠按钮清晰可读 / 字体差异仍在并转 issue #48）。

### 机制 / 行为模型

- **「兜底值」也是一种产品决策**：`prefersDark()` 回退暗色，当初的理由是「猜错代价最小」，
  但在真机上它就是「**每次启动都猜错**」。⇒ 兜底应当选**出厂默认**（亮色），
  并留一条能**自我纠正**的订阅（本档案新增 `onColorSchemeChanged`，只在主题仍为 `SYSTEM` 时应用）。
- **内联样式 + 逐节点登记的主题方案，漏一个节点就是一个永久缺陷**：
  「裸控件（不登记）」与「硬编码常量」是**同一个病的两种表现**——两者都会在换主题后停在旧外观。
- **弹层是独立的场景根**：`Dialog` 早已处理，但 **`Popup`（候选弹层）与 `ContextMenu`（右键菜单）**
  同样不会继承主窗口样式——这类「**看不见的场景根**」是主题缺陷的高发区。
- **遗留问题要开 Issue，不能只写进 TODO**：`TODO.md` 是暂存区，长期条目会被后续条目淹没；
  本次据此把「未闭环问题必须开 Issue」写进项目 `AGENTS.md`。

### 未定位 / 未复现

- **第 4 类（字体差异）未定位**：本机 WSL **无 Windows 图形环境**，无法复现；
  三条可能方向都需要真机对照才能收敛 ⇒ 转 **issue #48** 长期跟踪。
- **真机验收当时未做**：四项验收都写在档案里，但要等「合入后自动产出的 Windows 原生包」，
  即**修复效果在写作时尚未确认**。
- **系统主题实时订阅在原生镜像下是否可靠触发**：`colorSchemeProperty()` 的回调
  （`onColorSchemeChanged`）**未在真机验证**——而原生镜像里「读不到系统配色」正是本次的根因，
  所以这条订阅在原生下的可用性本身就是个待确认项。

## 未决问题

**Q1 字体发虚的根因是什么？**

现状：**未定位**——本机无 Windows 图形环境，三条方向（Prism 软件管线回退 / 字体枚举与默认字体解析 /
高分辨率缩放比）都需真机对照。跟踪入口：**issue #48**、`TODO.md` **N-24**。
> **后续进展（2026-10-13）**：该问题已由 issue **#48** 定位到「原生镜像丢失 LCD 次像素抗锯齿」
> （彩色边缘像素 JVM 165,783 / native 9,025 = **18.4×**），成因指向 DirectWrite 渲染参数在
> closed-world 下读不到；已落地**临时缓解**（`NativeRenderDefaults`，PR #127），**根治**转 issue **#60**。

**Q2 真机四项验收做了吗？**

现状：**当时未做**（要等合入后自动产出的 Windows 原生包）。四项：默认主题与系统一致、
切亮色后三栏边框 / 工具卡片 / 候选弹层 / 右键菜单全部跟着变、暗色下标题与折叠按钮清晰可读、
字体差异仍在。

**Q3 系统主题的实时订阅在原生镜像下可靠吗？**

现状：**未验证**。而本次根因恰是「原生镜像读不到系统配色」——
若订阅依赖同一份读取路径，`onColorSchemeChanged` 在原生下也可能不触发。
阻塞点：需要真机上切换系统皮肤并观察界面是否实时跟随。

**Q4 主题「漏登记」怎么防？**

现状：本次把**仅剩的裸控件**补齐了，但没有机器检查——后续新增控件忘走 `themed(...)`
会重演同类缺陷。
阻塞点：可考虑在冒烟测试里断言「关键节点在切主题后色值确实改变」（本项目的 FXML 批次
已引入 `PaletteTest` 一类守卫），尚未系统化。
