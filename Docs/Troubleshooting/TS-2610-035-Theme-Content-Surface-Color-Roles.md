# TS-2610-035 · 暗色下内容面「亮一档」被放大感知：按角色拆分底色

> 事件日期：2026-10-13
> 作者：@cnxnc
> 关联 Issue：[#153](https://github.com/ACANX/AHA/issues/153)（暗色下日志区 / 输入框底色与其他页面、对话框不一致）

## 1. 现象

暗色模式下，**日志区（`LogPanel` 的文本域）** 与 **中间的对话输入框（`aha.composer`）** 的底色
看起来与其它页面 / 对话框「不是同一套主题色」。亮色模式下**没有**这条反馈。

## 2. 排查过程

| # | 动作 | 预期 | 实际 | 结论 |
|---|---|---|---|---|
| 1 | 梳理颜色有哪几条上色路径 | 一条 | **三条**：主题补丁 CSS 字面量（Scene 级）/ 内联样式串（`themed()` 来自 `Palette`）/ 属性 API 兜底（`ThemePaint.apply` 的 `setTextFill`·`setBackground`） | 先弄清「谁管哪一层」再动手 |
| 2 | 两份补丁表对账：选择器集合、色号归属 | 可能已漂移（本单最初就是这么写的） | 选择器 **42 / 42 完全一致**；两表用色 10 / 9 个，**全部**能在 `Palette` 里找到（0 个野生色号） | **推翻「已经漂移」的假设**：漂移**风险**在（手抄字面量），但不是本现象的原因 |
| 3 | 量化「内容面 vs 页底」的感知差（sRGB → L\*） | 暗色那对应该明显更大（否则不该只有暗色被报） | 暗色 `#1E1E1E`→`#252526` ΔL\*=**3.45**；亮色 `#F4F4F4`→`#FFFFFF` ΔL\*=**3.81** | **也推翻**：两主题的感知差几乎相同（暗色还略小） |
| 4 | 定位真正差异 | — | 两主题用的是**同一条规则**（内容面比页底亮一档），差别只在「这一档落在大片深色背景上还是大片浅色背景上」 | 根因是**深色底放大了这一档的可见度**，不是数值本身 |
| 5 | 看宿主是谁 | — | 消息滚动区 / 菜单栏 = `BASE`（`DesktopShell:1254`、`1558`）；工具卡片 / 候选弹层 = `BLOCK_BACKGROUND`；输入框 / 搜索框 / 文本域 = `CONTROL_INNER` | 三类面共用一个「亮一档」的常量 ⇒ 没有角色区分 |

## 3. 根因

一句话：**「内容面」与「抬起控件」共用同一个「比页底亮一档」的底色常量**，
于是**大块内容面**（日志区、输入框）在深色背景上也亮着一档——
按 L\* 算是与亮色主题同样的量级，但**深色底上这一档被放大感知**，看起来就像「另一套主题」。

- **触发条件**：暗色主题 + 大面积内容面（文本域 / 输入框 / 列表）；
- **机理**：`CONTROL_INNER` 一个常量同时承担两种语义——
  「输入框 / 列表 / 滚动容器」这类**内容面**，与「按钮 / 菜单 / 弹层」这类**抬起控件**。
  前者应与页底同色（它只是「可输入的地方」），后者才该亮一档（表达「可点 / 浮层」）；
- **为什么没被及早发现**：亮色下同结构（`#F4F4F4` → `#FFFFFF`）差值虽同样大，
  却落在白底语境里，观感是「白输入框」这种**熟悉**形态 ⇒ 没人觉得不对；
  而暗色下它变成「一块比周围亮的灰」，才被看出来。既有测试只锁了色值表，没锁**角色关系**。

## 4. 修复

**按角色拆开**（issue #153）：

| 角色 | 载体 | 底色 |
|---|---|---|
| **内容面** | 输入框 / 文本域 / 列表 / 滚动容器 | 与页底同色（`Palette.CONTROL_INNER`，暗色改为 `#1E1E1E` = `BASE`） |
| **抬起控件** | 按钮 / 菜单 / 下拉弹层 | 比页底亮一档（新增 `Palette.RAISED_BACKGROUND`，暗色 `#252526`） |

改动点：`Palette`（新增角色常量 + 暗色 `CONTROL_INNER` 对齐 `BASE`；**亮色不动**）、
`aha-theme-dark.css`（内容面 8 处字面量 → `#1E1E1E`；按钮 / 菜单 / 弹层保持 `#252526`）、
`PaletteTest` 新增一条锁「角色关系」的断言。

> **替代方案取舍**：也想过「把暗色的 `CONTROL_INNER` 往 `BASE` 挪一点（如 `#222222`）」——
> 但那只是把差异调小，**角色仍然混在一个常量里**，下次换个控件又会冒出来；
> 按角色拆开才是把口径定下来。另：**亮色本轮不动**（未报问题、且白底输入框是熟悉观感），
> 代价是两主题的「内容面」规则暂不对称 —— 见「未决问题 Q2」。

## 6. 教训与沉淀

- **感知差要用 L\* 算，不能凭「相对亮度比」**：`#252526` 与 `#1E1E1E` 的**比值**看着差 23%，
  换成 L\* 只有 3.45，与亮色主题的 3.81 相当——**按比值推结论会得出完全相反的方向**；
- **「写入规范而无人执行等于没写」**：`DesktopDesign.md` §11.6 早就写了「**不允许硬编码颜色**」，
  但直到 2026-10-13 才有机器守卫（`bin/CheckTheme.py`）。本次顺手把它补上——
  这也与本项目对「规范 + 检查脚本」的一贯要求一致；
- **同一个常量承担两种语义，迟早出事**：`CONTROL_INNER` 被内容面与抬起控件共用，
  是这次「只有某类控件不对」的结构性原因。定色表时**角色要分开**；
- **落地**：`Palette`（角色常量）、`bin/CheckTheme.py`（Gate 里跑）、`DesktopDesign.md` §11.6（角色表 + 守卫）、
  `PaletteTest`（角色关系断言）。

## 结论分层

### 已观测事实

- 两份补丁表：选择器**各 42 条，集合完全一致**；暗色用色 10 个、亮色 9 个，
  **全部能在 `Palette` 找到**（0 个野生色号）。
- L\* 实测：亮色 `#F4F4F4`(L\*=96.19) → `#FFFFFF`(100.00)，ΔL\*=**3.81**；
  暗色 `#1E1E1E`(11.26) → `#252526`(14.71)，ΔL\*=**3.45**。
- 宿主底色：消息滚动区 / 菜单栏 = `BASE`；工具卡片 / 候选弹层 = `BLOCK_BACKGROUND`；
  输入框 / 会话搜索框 / 文本域 = `CONTROL_INNER`（改前 = `#252526`）。
- 应用层**没有**任何拖放实现（与本条无关，但同一轮排查中被确认，见 issue #125）。

### 机制 / 行为模型

- 三条上色路径并存（CSS 字面量 / 内联样式串 / 属性 API 兜底）是**原生镜像下 CSS 传导不可靠**逼出来的设计
  （`TS-2610-029` / `031`）——它解释了为什么「同一件事要在三处各写一次」；
- 颜色本身没有漂移（事实 1），故现象只能来自**规则**而非**数值**：
  规则是「内容面比页底亮一档」，而这一档在**深色底**上被放大感知（事实 2 说明两主题的 L\* 差相当，
  所以「暗色差更大」的直觉不成立）；
- **推定**：深色底放大感知是这条反馈只出现在暗色的原因。**未做**受控的观感实验（无显示器环境）。

### 未定位 / 未复现

- **未复现（本机）**：没有能看界面的环境，无法复现「看起来不一致」这一步；只做到了逻辑与色值层面的定位。
- **未定位**：现象是否还包含其它面（例如工具卡片 `BLOCK_BACKGROUND` 与页底的关系）——
  用户只报了日志区与输入框两处，其余未逐一比对。
- **未验证**：修复后的观感（见「未决问题 Q1」）。

## 排除项

| 已排除的可能 | 依据 |
| --- | --- |
| 「两份补丁表已经漂移（色号不一致）」 | 选择器 42/42 一致；两表色号全部属于 `Palette`，0 个野生色号 |
| 「暗色的感知差比亮色大得多」 | ΔL\* 实测 3.45 vs 3.81——暗色**还略小**；按比值看才会得出反向结论 |
| 「某个控件压根没被上色（回落到 modena 白底）」 | 两份表的选择器集合一致，且 `ThemePaint.apply` 还会用属性 API 兜一层；日志区 / 输入框都在补丁覆盖内 |
| 「是主题切换没重刷导致的残留」 | 该问题（`TS-2610-025` / `028`）有独立机制与既有守卫；本次现象在**首次启动**的暗色下即可见 |
| 「改数值就行（不必拆角色）」 | 数值一改就掩盖了「一个常量两种语义」的结构问题；换个控件或加个面板还会复发 |

## 未决问题

**Q1 修复后的观感是否达到 ACANX 的预期**

现状：代码与守卫已落地，CI 只验证到「色值 / 结构」；**「看起来是否一致」需要人眼**。
阻塞点：需 ACANX 真机看一眼暗色下的日志区 + 输入框（以及对话框里的输入框）。
按 `IssueTrackingSpec.md` §4，这类人工项以 ACANX 的判断为准，不写成机器结论。

**Q2 亮色主题是否也要把内容面对齐页底（两主题规则对称）**

现状：本轮**只动暗色**（亮色未报问题，且「白输入框 + 浅灰页」是熟悉观感）。
代价是两主题的「内容面」规则暂不对称：暗色内容面 = 页底，亮色内容面比页底亮一档（ΔL\*=3.81）。
阻塞点：属产品取舍，待 ACANX 拍板（若要对称，改法是亮色 `CONTROL_INNER` → `#F4F4F4`，一处常量）。

**Q3 还有没有别的「一个常量两种语义」**

现状：本轮只处理了 `CONTROL_INNER`。`BLOCK_BACKGROUND`（工具卡片 / 候选弹层 / 按下态）是否也承担了多种语义，未逐一核对。
阻塞点：需要一次色表语义审查（把每个常量的「谁在用、表达什么」列出来），不在本轮范围。

## 后续（2026-10-14，第二轮：色源收敛）

**背景**：第一轮修掉了可见现象（按角色拆底色），但 issue #153 正文的实质要求
「收敛为一处色源」还没做——颜色仍有**两处手写来源**（`Palette.java` 与两份 CSS 里
手抄的字面色号），只是由 `bin/CheckTheme.py` 事后核对兜着。

**本轮做法**：保留 CSS 字面量机制（不能换 CSS 变量，理由见下），把「唯一色源」
挪到**生成**这一步。

| 环节 | 落点 |
| --- | --- |
| 手写色源（唯一） | `Palette.java` 的 `applyDark()` / `applyLight()` |
| 模板（带 `%角色%`） | `aha-desktop/src/theme/aha-theme-{dark,light}.template.css` |
| 生成器 | `bin/GenThemeCss.py`（`--check` 只校验） |
| 生成物（入库） | `aha-desktop/src/main/resources/.../css/aha-theme-{dark,light}.css` |
| 守卫 | `bin/CheckTheme.py` 第 4 / 5 项（逐字节重现 + 跨主题角色序列一致） |

**为什么不用 CSS 变量「只用一处」**：这是本条正文 A 方案的原写法，但被仓库既有证据否掉——
issue **#49 第四轮**：原生镜像下**自定义 color 查表不可靠**，查不到值时 CSS 会
**丢掉整条声明**，文字色回落成 modena 默认黑（`Palette.buildThemeStyle()` 与两份 CSS
头部都记着这条结论）。所以字面量必须保留，只能靠生成来收敛；
`bin/GenLogoPng.py`（生成器入库、产物入库）是同一模式。

**验证**：

| 项 | 命令 / 做法 | 结果 |
| --- | --- | --- |
| 纯搬运（色值零变化） | 生成物 vs `git HEAD` 版本，去注释后取色号序列 | dark **58/58**、light **58/58** 逐值一致 |
| 逐字节重现 | `python3 bin/GenThemeCss.py --check` | ✅ 通过 |
| 跨主题角色序列 | 同上（内部比对） | dark 58 = light 58，一致 |
| 反向验证 A：手改生成物 | 把某处 `-fx-background-color` 改成 `#1E1E1F` | ❌ 报「不能由模板 + Palette 重现」并给出 diff |
| 反向验证 B：模板里塞字面色号 / 未定义角色 | 插入 `#FF0000` / 改 `%NOT_A_ROLE%` | ❌ 两条分别被点名 |
| 反向验证 C：只改暗色模板的某个角色 | `%HOVER_BACKGROUND%` → `%BLOCK_BACKGROUND%` | ❌ 报「两份模板的角色序列不一致，第 12 个角色…」 |

**仍未做 / 未验证**：

- 正文验收标准 4 的**截图对照**（暗色与亮色各一张）与 Q1 的观感确认：需 ACANX 真机；
- 正文验收标准 3 的**运行期**守卫（逐个断言 `Region#getBackground()`）**未做**：

- Q2（亮色是否也要对齐页底）、Q3（还有没有别的「一个常量两种语义」）不变。
