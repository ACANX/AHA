## 1. 背景

按用户要求把「供应商配置」从「弹窗挑一个」改成**能查看、能修改、能新增**，
并把侧边导航与对话功能做成最小可用客户端。改造过程中连出四个问题，
其中两个是我自己引入的、一个是**我的自动化脚本污染了用户的真实配置**。

## 2. 排障过程与修复链

### 2.1 非启用项发灰、费眼（主题没铺到对话框）

**现象**：供应商列表里未被启用的项是灰色低透明度，看不清。

**根因**：暗色主题只加在**主窗口的根节点**上，而 `Dialog` / `Alert` 有自己的场景根，
**不会继承**主窗口样式 → 对话框是 JavaFX 默认**白底**；而我又给列表文字设了
`Palette.FOREGROUND`（`#E4E4E4`，近白）→ **白底白字**。

**修复**：把主题抽成 `Palette.theme()`，应用到**每一个顶层容器**
（主窗口、供应商对话框、工具列表、授权弹窗、删除确认）；
列表未启用项一律用正常前景色，只有启用项用绿色加粗 + 模型名。

**教训**：主题/样式必须覆盖每个顶层容器。对话框不是主窗口的子节点。

### 2.2 点「新增」没反应（三个原因叠加）

**根因 A**：模型字段用了**可编辑 `ComboBox`**。这类控件的「编辑器文本」与 `value`
是**两份状态**，输入内容不会自动提交到 value，且**失焦时可能被清空**——
点「新增」按钮恰好让模型框失焦，于是读到空字符串，校验失败。

**根因 B**：校验失败的提示只写在对话框**左上角**的状态行里，按钮旁边没有任何反馈。

**根因 C**：对话框内容高度超过屏幕，「新增」按钮被**切在屏幕外**（真机截图可见只露一半）。

**修复**：
- 模型改成**纯输入框 + 候选下拉菜单**（读取永远可靠）；
- 错误/成功信息**就地显示在按钮旁边**（新增区多一行「结果」）；
- 对话框**限高 720 + 内容可滚动**，按钮不会再跑到屏幕外；
- 落盘逻辑抽成 `ProviderForm.save(...)`：校验 → 写入 → **读回自检**，
  并补了 3 例测试（含「写完能被 core 的 `ConfigLoader.loadModel` 读回」）。

**教训**：「点了没反应」几乎总是**缺反馈**，而不是没执行。
反馈必须贴着动作；能用普通输入框就别用双份状态的可编辑 ComboBox。

### 2.3 「打开供应商」直接抛异常（配置坏 → 界面崩）

**现象**：用户打开供应商对话框即报错，控制台刷出多屏异常。

**根因**：`Model.yml` 里有一个 **`qqqqq`** 键（非大驼峰），而 core 按 YAML 字段规范
**拒绝加载整份配置**；对话框直接 `store.load()`，没有兜住异常 → 界面当场崩，
且用户看不到「哪一行坏了」。

**修复**：新增 `ProviderForm.loadSafely(...)`（返回配置或错误说明），
对话框全部改用它：坏配置时**照常打开**，并把 core 的原始错误（含出错字段名）
显示在状态行里，同时指出修正方向。补 2 例测试复现该场景。

**教训**：严格校验是 core 的设计（好事），但**调用方必须能承受校验失败**。
「打开就崩」比「打不开但说清原因」差得多。

### 2.4 我引入的口径不一致：界面允许的 ID，core 不认

**根因**：我在 GUI 里把 ID 校验写成「字母数字下划线点减号」，而 core 要求**大驼峰**
（`^[A-Z][a-zA-Z0-9]*$`，`ConfigLoader.validateFieldNames`）。
于是界面能写出**连自己都读不回来**的配置——上面那个 `qqqqq` 就是这么来的。

**修复**：GUI 校验改为与 core **同一个正则**，错误文案写明原因；
补测试钉住（小写 ID、带下划线 ID 均被拒）。

**教训**：界面校验必须与核心校验**同源**，不能各写一套。

### 2.5 我的自动化脚本污染了用户的真实配置

**现象**：用户的 `C:\Users\ACANX\.aha\Model.yml` 里多出 `NewProvider` 与 `qqqqq` 两条测试数据。

**原因**：我用 PowerShell 模拟鼠标点击「供应商」按钮来截图时，**鼠标抬起事件落在了
刚弹出的对话框控件上**（新增按钮 / 输入框），把测试数据真写进了用户的配置。

**处置**：先备份（`Model.yml.bak-aha-20261008`）→ 用正则逐块移除非法键 →
用 PyYAML 解析校验「恰好 6 家 + 默认 DeepSeek」 → 再用项目自己的 CLI
（`aha provider list`，与应用同一条读取路径）复核通过。

**教训（最重要的一条）**：自动化不得对用户的真实数据做点击/输入。
要在界面上验证写入，就用**测试**（临时目录 + `ModelConfigStore`），
而不是对着真实配置模拟操作。

## 4. 关键教训

1. **主题/样式要覆盖每个顶层容器**：`Dialog` / `Alert` 不继承主窗口样式，白底白字就是这么来的。
2. **可编辑 `ComboBox` 是双份状态**：编辑器文本与 value 不同步，失焦还会被清空——
   读值是不可靠的，能用普通输入框就别用。
3. **「点了没反应」= 缺反馈**：错误要显示在动作旁边；对话框要限高可滚动，
   否则按钮会被切在屏幕外。
4. **界面校验与核心校验必须同源**，否则界面能写出自己都读不回来的配置。
5. **调用方必须承受严格校验的失败**：坏配置要能打开界面并说清原因，不是崩掉。
6. **自动化不得碰用户的真实数据**：验证写入用临时目录的测试，不要模拟点击真实配置。
7. 我在这轮里**连续三次在同一类问题上返工**（读取不可靠 / 反馈缺失 / 校验不同源），
   说明写界面代码时应当先问「这条信息从哪来、失败时用户看到什么」。
