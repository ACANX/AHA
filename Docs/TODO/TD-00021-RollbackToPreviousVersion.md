## 来源

- 2026-10-16 **第二轮**代码审查（PR #243）P3-⑤：备份目录里留着上一版的全部文件
  （`~/.aha/update/backup/<旧版本>/`，含被新包删掉的文件），但界面没有「切回去」的入口，
  而 `Update.BackupKeep`（默认 2）会按份数把它们裁掉 —— 留着的意义就只剩排查。

## 现状

| 层 | 状态 |
|---|---|
| 备份内容 | ✅ 每次换装都把被替换的旧文件按**相对路径**搬进 `backup/<旧版本>/`（删除动作也走备份） |
| 保留份数 | ✅ `Update.BackupKeep`（0–10，默认 2）在启动收尾时生效（`StagingArea.pruneBackups`） |
| 手工回滚 | ✅ 设计文档 §4.1 有手工步骤；`SwapPlan.rollback` 有单测覆盖 |
| 界面入口 | ❌ 没有：用户看不到「我还能切回哪一版」，也不知道备份在哪 |
| 自动回滚 | ✅ 换装失败时 helper 会用备份回滚（`rolledBack` 写进回执） |

## 要做的事

1. **只列「可还原的版本」**：从 `~/.aha/update/backup/` 里解析出版本号，界面显示一份列表
   （当前版本 / 可切回的版本），并说明「切回不会动 `~/.aha/` 下的用户数据」；
2. **走同一条换装链路**：不要在界面里直接拷文件 —— 生成一份「以备份为源」的换装计划，
   交给 helper 执行（复用 `UpdatePlan` / `SwapPlan` / 回执 / 启动收尾，别再写一份换装逻辑）；
3. **降级语义要一致**：等同「降级」（二次确认 + 「用户数据不回滚」提示）；如果目标版本**不在**
   发布页（本地手工包 / 已过期），要如实说明「这是本机备份，不是发布页的包」；
4. **备份被裁掉之后**：列表里已经不存在的版本不能点，并提示「只保留最近 `Update.BackupKeep` 份」；
5. 测试：`UpdateServiceTest` 增「以备份为源的计划」用例；界面冒烟断言列表与置灰规则；
6. 文档：`DesktopAutoUpdateDesign.md`（新增一节）、`AppUpdateGuide.md`、`CHANGELOG.md`。

## 为什么值得做（而不是只留手工步骤）

- 备份**已经在磁盘上**、`SwapPlan.rollback` 也已经有单测 —— 缺的只是「让用户看得见、点得到」；
- 升级出问题时，「切回上一版」是最省事、最不需要信任新版本的补救；
- 反向风险：备份会被 `BackupKeep` 裁掉，所以入口必须**照实**说明能切回的范围，不能假装一直有。
