## 2. 推荐章节体例

| 序 | 章节 | 回答的问题 | 必要性 |
|---|---|---|---|
| 1 | 来源 | 谁在什么背景下提出？诉求要点是什么？ | 必备 |
| 2 | 需求 | 到底要什么（可核对的诉求清单） | 必备 |
| 3 | 评审结论（日期） | 定了什么（逐条、可核对） | 评审后必备 |
| 4 | 现状（实查） | 现在是什么样（**附可复核证据**） | 建议必备 |
| 5 | 方案 · 前言 | 受哪些规范约束？关键术语怎么定义？ | 建议必备 |
| 6 | 方案 · 正文 | 怎么做（流程、规则、边界、异常与退化） | 必备 |
| 7 | 实施清单 | 落地要交什么（逐项、可交付） | 建议必备 |
| 8 | 验收标准 | 怎么算完成（**优先可机器判别**） | 必备 |
| 9 | 范围外（不做） | 明确不做什么，避免范围膨胀 | 建议必备 |
| 10 | 引用参考 | 关联工作流 / 脚本 / 记录 / 规范（站内挂链接） | 建议 |
| 11 | 附录 | 备选方案与被否理由、变更历史、决议追踪、绘制约定、纯文本版图 | 视需要 |
| 12 | 状态摘要 | 状态 / 实施阶段（可用文首一行或三行状态条） | 可选 |

**顺序原则**：读者先看「这是什么、要什么、定了什么」，再看「为什么（现状）、怎么做（方案）、怎么验（验收）」；
**过程考古一律后置**（附录），不夹在正文中间。

## 3. 各部分写法要点

### 3.1 现状：必须带证据

- 写「命令 + 原始输出 / 状态码」，不写「我记得」「应该是」；
- 例（#165 实测）：匿名下载 Actions 制品 → **401**；发布页资产 → **200**；两者对照才支撑「改走发布页」的结论；
- 事实用表格列：**事实 | 证据**；证据里的本仓库文件挂链接（见 3.6）。

### 3.2 评审结论：可核对、可计数

- 每条写成「项目 | 决定」，避免大段散文；
- 若在多处出现同一数字（如「已决 23 / 未决 0」），**必须保持一致**，改动后用脚本核对所有出现位置；
- 状态类信息不要写成"两个真相"：**以 GitHub 的 label / assignee / open-closed 为准**，正文只做摘要。

### 3.3 决议追踪：保留原文，不做删除式收敛

- 形式：`- [x] ~~原问题~~ ⇒ 结论（日期）`；未决留 `- [ ]`；
- **不要删条目**：删掉之后没人知道「为什么不是另一个方案」；
- 决议追踪属于**过程考古**，放附录（与「备选方案与被否理由」「变更历史」同族），正文只留状态摘要与指针。

### 3.4 验收标准：优先机器可判别

- 首选「命令 + 期望输出」；其次「构造反例 ⇒ 守卫必须失败」（反向验证）；
- 避免「看起来对了」「观感良好」这类无法复核的表述；**必须由人判断的项**（观感、真机行为）单独标出「需人工确认」；
- 给「跳过 / 不出包 / 不触发」这类**负向行为**也写验收：跳过必须**可见**（写在 run 摘要或 PR 评论里）——「跳过不能静默」。

### 3.5 术语与约定：一次说清

- 正文用到的专有说法（例：粘性标签、变更分类、腿（leg）、兜底清扫、安全阀）在方案前言里**集中定义**；
- 每条给**可核对的锚点**（标签名、版本号格式、tag 命名、目录、保留数字），不要只写概念解释；
- 曾被弃用的旧说法也写一行（例：「未关闭的 PR」——旧文档口语写作「在飞」，已弃用），让读到旧文的人能对上号。

### 3.6 引用与链接：挂了就必须核对

- 站内条目**逐个比对** `git ls-files` 确认存在；不存在的（尚未创建的文件）**不要挂链接**，改列「本单新增（尚不存在）」；
- 外部标准给出官网链接，并用 `curl -L` 看状态码，把「核验日期」写进口径行（例：2026-10-14 逐条核验 HTTP 200）；
- **Issue 里用绝对 URL**：Issue 正文渲染在 `/owner/repo/issues/N` 之下，相对路径会被解析成 `…/issues/Docs/…` 而点不开；
  仓库内 `.md` 文件之间才用相对路径（GitHub 官方文档「Relative links」一节的适用范围）。

### 3.7 规范参考：按性质分三档

| 档 | 内容 | 备注写法 |
|---|---|---|
| 项目规范（强制） | `Docs/DevSpec/*Spec.md` | 写「本文档受它约束的**哪个方面**」，而不是只列文件名 |
| 项目参考 | 设计 / 指南 / `AGENTS.md` / 技能 / 排查记录 | 写「引用了它的哪一节」 |
| 外部标准 | SemVer、Conventional Commits、平台手册、语言规范… | 写「在本方案里起什么作用」+ 是否已被仓库采用 |

## 4. 表格与图的约定

### 4.1 表格

- **一行一实体**：一个标签一行、一个文件一行；不要把三个实体塞进一个单元格；
- **不用「同上」**：让人往回看是负担；合并性规则写成**表下约束**（例：「`OS:*` 不能单独使用」）；
- 列名用**读者能懂的文字**，不要用 `A / B / C` 这类需要图例才能看懂的代号（尤其当正文别处也用 A/B/C 表示别的东西时）。

### 4.2 流程图

- **单一起始、单一结束**（圆角 `([开始])` / `([结束])`；双圆会渲染成一个大圆圈，占地方且不美观）；
- **判定用菱形**；不通过时的回边回到**判定之前的汇聚点**，不要直接跳回某个业务节点；
- **一节点一件事**（例：三种触发方式不能塞进同一个节点）；
- **节点里不贴命令 / 文件名 / 标识符**——命令放正文表格；标识符只在「映射图」这类以标识符为内容的图里出现；
- 连线文字尽量短（编号 + 图例，或短标签）；
- Mermaid 能力边界（实测）：
  - **不能指定连线锚点**：回边一律连到「朝向对端」的那一侧；想让箭头从上方进入，只能让该节点**只有一条入边且来自上方**；
  - 连线字号可用逐条 `linkStyle N font-size:10px` 调小；用 `%%{init:%%` 主题字号会把**节点文字一起改小**，通常不是本意；
  - **渲染效果必须在页面上确认**：本地只能做语法自检（起止数量、悬挂节点、可达性、`subgraph`/`end` 配平、无反斜杠）。

### 4.3 图的载体（三档）

| 载体 | 适用 | 取舍 |
|---|---|---|
| 正文 Mermaid | 需要与人讨论、可 diff 的流程 | 依赖前端渲染：命令行 / API / 邮件里只显示源码 |
| 附录 ASCII | 纯文本场景（终端、API、通知） | 直观度差、维护成本低 |
| SVG（`Docs/Diagrams/`） | 长期存档、需要精确布局（如手工走线） | 仓库规范 **SVG 优先**；生成需工具（`mermaid-cli` 等），diff 不可读 |

## 6. 一句话总结

> **正文只放「定了什么 + 怎么做 + 怎么验」；过程考古（备选、变更历史、决议追踪）进附录；每一条结论都要能被复核。**
