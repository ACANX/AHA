## 0. 本文定位

把「Issue 怎么开、状态怎么管、什么时候能关」定下来。

| 载体 | 职责 |
|---|---|
| **本文（规范）** | **状态机、判定标准、关闭门槛**——什么算「在做」、什么算「卡住」、凭什么能关 |
| 技能 [issue-tracking](../../.agents/skills/issue-tracking/SKILL.md) | **操作**：`gh` 命令、标题与正文结构、关闭评论模板 |
| `AGENTS.md`「遗留事项一律开 Issue 跟踪」 | 强制口径的摘要与索引 |

规范与操作分离是项目约定（`DocumentationSpec.md` §1）。两者冲突时以本文为准。

## 1. 开单判定

**必须开**（任一成立）——与 `AGENTS.md` 一致：

- 本轮**未能闭环**的问题（查不动、需外部环境、需后续迭代）；
- 需要**人拍板**的取舍项（技术上无唯一正解）；
- **自动化做不到、必须由人完成**才能收口的事（推送、仓库 / 分支保护设置、平台侧配置、外部环境验收）；
- 从设计文档 / 规范里读出的、**暂时不动的已知缺口**。

**不必开**：本轮就能改完的缺陷（直接改）；一次排查的过程记录（进 `Docs/Troubleshooting/`）；
已完成事项的开发记录（进 `Docs/DevLog/`）。

> 判据：一个遗留问题如果**不适合下一轮立即动手**，就应该是一条 Issue。
> **不得只在对话里交代**——对话会滚走，事后既无闭环也无从判断「到底做过没有」。

## 2. 标题、正文、标签与里程碑

- **标题**：`模块/主题：一句话说清要解决什么`，可检索；避免「优化一下」「看看这个」。
- **正文结构**：`## 来源` / `## 现状` / `## 需求 / 待拍板` / `## 验收标准` / `## 关联`
  （逐条可判定；见技能里的骨架）。
- **标签**：只用仓库既有标签（`bug` / `enhancement` / `feature` / `documentation` /
  `docs` / `accessibility`）。
- **禁止**为了表达状态而新建标签（见 §4.2 说明）。

### 2.1 里程碑（强制）

**凡新建 Issue 与 PR —— 包括 Agent（cnxnc）自动创建的那些 —— 必须挂上里程碑**：
不得留空，也不得「先建后补」。判定按下面顺序取**第一个能确定**的：

1. **继承**：该单若属于某个父任务 / 里程碑的既有子任务（如 #165 的 S1–S8），
   直接**继承父任务的里程碑**；
2. **按目标版本**：按「这一条要到哪个版本才算完成」判定 —— 当前待发版本是 `V0.1.3`；
   已规划的后继能力按设计路线图（[AHA-Design-V1.md](../AHA/AHA-Design-V1.md)）里该能力的归属版本判定；
3. **确定不了就别猜**：**先问 ACANX**，得到答复后再建单 / 开 PR。

PR 侧的同一要求：

- 修复 / 关联某条 Issue 的 PR ⇒ **与那条 Issue 同一里程碑**；
- 无关联 Issue 的杂务 PR（纯文档修订等）⇒ 按目标版本判定；仍不确定 ⇒ 先问。

**复核（发现漏挂立即补，并在该单留一条评论说明补挂原因）**：

```bash
# 未挂里程碑的 open Issue / PR —— 应当为空
gh api "repos/ACANX/AHA/issues?state=open&per_page=100" \
  --jq '.[] | select(.milestone == null) | "#\(.number) \(.title)"'

# 现有里程碑（标题即版本号；以 GitHub 为准，不在文档里抄一份会过期的清单）
gh api "repos/ACANX/AHA/milestones?state=all&per_page=50" \
  --jq '.[] | "\(.title)  open=\(.open_issues) closed=\(.closed_issues)"'
```

> 里程碑**只建有依据的版本**（设计路线图 / 已定的发布计划），不凭空发明版本。
> 建单与开 PR 都可直接挂：`gh issue create … --milestone V0.1.3`、`gh pr create … --milestone V0.1.3`。

## 3. 状态管理

### 3.1 为什么单独定口径

GitHub 的原生状态只有 **open / closed**（闭时带一个 reason：`completed` / `not_planned`），
并没有「进行中」「待拍板」「阻塞」。不约定口径，就会退化成人人自行拿捏：
「这条到底有没有人在做」「卡在谁那里」只能靠翻评论——**状态不可读，等于没有状态**。

### 3.2 状态取值（唯一词表）

| # | 状态 | GitHub 表示 | 判定 | 谁改 |
|---|---|---|---|---|
| 1 | **待处理**（Open） | `open` | 已登记；无人认领、无待决问题 | 创建者 |
| 2 | **进行中**（In Progress） | `open` + **assignee** | 已有人在做（分支 / PR 已开） | 执行者 |
| 3 | **待拍板**（Decision） | `open` + `question` 标签 | 需 ACANX 拍板才能继续 | 执行者 |
| 4 | **阻塞**（Blocked） | `open`（评论写明阻塞点） | 依赖外部条件（平台、上游、他人） | 执行者 |
| 5 | **已解决**（Done） | `closed` + `completed` | 关闭三要素齐备（见 §4） | **须 ACANX 授权** |
| 6 | **不做**（Wontfix） | `closed` + `not_planned` | 明确不采纳，且写明依据 | **须 ACANX 授权** |
| 7 | **转跟踪**（Superseded） | `closed` + `completed` + 承接 Issue | 本体关闭，后续转到新 Issue | **须 ACANX 授权** |

两条实现约束：

- 仓库**不使用** GitHub Projects 看板（当前没有该设施）：状态只能用上面这套原生手段表达；
- **不得为状态新建标签**。「进行中」用 **assignee** 表达，「待拍板」复用既有的 `question`，
  其余状态靠**评论留痕**。理由是标签一旦为状态而生，就会与既有标签语义重叠、并随状态漂移累积。

### 3.3 状态流转

```
                   ┌──────────► 3 待拍板 ──────────┐
                   │                                 │
 1 待处理 ─────────┼──────────► 2 进行中 ──► 4 阻塞 ─┤
                   │                 │       │       │
                   └─────────────────┴───────┴───────┴──► 5 已解决
                                                         6 不做
                                                         7 转跟踪

 5 / 6 / 7 ──(reopen，需说明为何未闭环)──► 1 待处理
```

规则：

1. **只走相邻流转，不允许静默跳级**：从「待处理」直接关闭时，关闭评论里必须补齐
   验收依据与验证过程（相当于事后补上 §4 的三要素）；
2. **每次状态变化在同一处留痕**：在 Issue 里补一条评论，写「谁 / 为什么 / 下一步」——
   状态图看不出来的信息（阻塞在谁那里、拍板选项有哪几个）必须落到评论；
3. **关闭是唯一需要授权的变更**：Agent 不得自行关闭（见 §4）；
4. **reopen 要写原因**：说明「关闭时的依据为何不再成立」，并补新的验收标准。

### 3.4 与 `Docs/TODO` 看板的状态对应

同一个事项若同时登记在 Issue 与 `Docs/TODO/README.md`，两处状态**同一变更内同步**：

| 本文状态 | TD 清单 / TD 文件头的建议写法 |
|---|---|
| 待处理 | `☐ 未开始` |
| 进行中 | `▶ 进行中` |
| 待拍板 | `⏸ 待拍板` |
| 阻塞 | `⏸ 阻塞` |
| 已解决 | `✅ 已完成（YYYY-MM-DD）` |
| 不做 | `✖ 不做` |
| 转跟踪 | `➡ 转 #NNN` |

> 历史条目按原写法保留，**不回溯改名**；新增与状态变化按本表书写（`DocumentationSpec.md` §4
> 的「记录纪律」要求代码与记录同变更内完成）。

### 3.5 定期复核（防止「静默腐烂」）

- 每周或每轮工作结束时扫一遍 open 列表：**没有 assignee 又长期无评论**的条目，
  要么认领，要么明确降级为「阻塞 / 待拍板」并写明原因；
- **长期不动的条目不要关**——保持开启并在评论里记下最新判断（做到哪一步、为什么停）；
- **不允许静默丢弃**：一个 Issue 若既不关、又不更新，就等于把结论留在了某个人的记忆里。

## 4. 关闭规范（三要素，缺一不可）

**关闭须经 ACANX 授权；Agent 不自行关闭。** 关闭前**必须先补一条关闭评论**：

| # | 要素 | 要求 |
|---|---|---|
| 1 | **相关修复 PR / 提交** | 逐个列出：编号 + 标题 + 合并状态（含 commit）。若没有代码改动，写清是「结论性关闭」还是「转跟踪」 |
| 2 | **关闭理由** | 现象是否消除；是**根治**还是**缓解**。若是缓解，**必须指名根因由哪条 Issue 继续跟踪** |
| 3 | **验收依据** | 可复核的证据：命令与原始输出、测试运行编号 / 用例数、日志行、产物路径。**不得只写「已完成」** |

补充口径：

- **正文里的「验收标准 / 验收」清单必须逐条勾选并就地附证据**（`- [ ]` → `- [x]`，
  后面追加「✅ 证据：命令与原始输出 / run 编号 / 日志行」）。关闭评论是**过程留痕**，
  勾选后的正文才是**可复核的结论** —— 只写评论、不勾正文，下一个人得翻三页评论才知道验没验
  （2026-10-14 的实际教训：#169 / #170 / #171 关闭时漏了这一步，事后补齐）；
- 勾选时**顺带核对正文里的口径是否已过期**（方案改过名、接口改过形、路径改过位），
  过期就一并更正 —— 否则正文与实现各说一套，勾了也不可信；
- 依赖**人工判断**的项（真机观感、平台行为）要明说「以 ACANX 的判断为准」，
  **不要把人工结论写成机器结论**；
- 「转跟踪」时，承接的 Issue **必须先开好**再关本条（不允许「关了就没下文」）；
- 关闭评论模板与命令见技能 [issue-tracking](../../.agents/skills/issue-tracking/SKILL.md#关闭-issue规范)。

**首个执行实例**：`#48`（原生桌面端字体渲染不一致）——附 PR `#127`、写明「临时缓解、非根治」、
给出 7 个用例的 CI 依据与三种回退方式，并把代码级根因明确转给 `#60`。

## 5. 拆分与转跟踪

- **总览 Issue**（如 `#86`）只做索引，不承载结论；具体事项逐条拆成独立 Issue，
  并在总览里用任务列表引用；
- **父子关系**用 GitHub 的 sub-issue / 任务列表表达，避免只在正文里手写「见 xxx」；
- **转跟踪**的三种情形：根因被定位到另一子系统（`#48` → `#60`）、验收被移交到平台 / 外部环境、
  方案被新设计取代。三种都适用 §4 的三要素。
