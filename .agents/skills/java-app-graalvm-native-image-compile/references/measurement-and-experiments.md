# 启动速度与内存的测量与实验

原生镜像常被当成「启动快、内存小」的银弹，但**收益要靠数据说话**。
这一节把口径、实验设计与记录表固化下来，避免每次各测各的。

## 1. 先定口径（口径不定，数字没有意义）

| 指标 | 定义 | 采集方式 |
|---|---|---|
| **冷启动** | 进程启动 → 主窗口可见（GUI）/ 主流程可响应（CLI） | 应用自己在关键点打时间戳日志（推荐：可复现、可自动化）；或用外部计时工具 |
| **空闲驻留内存** | 启动完成、界面可见后**静置 60 秒**的工作集（Windows）/ RSS（Linux、macOS） | 任务管理器 / 资源监视器 / `ps`、`time -v` |
| **包体积** | 发布资产的压缩包大小，以及解压后可执行文件大小 | 构建日志或 `ls -lh` |
| **构建时长** | native-image 阶段的墙钟时间 | CI 步骤耗时 |

规则：

- 每个数字取 **5 次的中位数**（首启动往往偏慢，别用平均值掩盖离散度）；
- 记录机器（CPU、内存、是否插电、是否同时跑别的重活）；
- 对比时**一次只变一个变量**（JDK 版本 / GC / 参数 / 形态），否则结论无法归因。

## 2. 三种形态（缺一条腿，结论就不完整）

| 形态 | 说明 | 为什么要它 |
|---|---|---|
| **A：原生镜像（基线 JDK 编）** | 当前稳定 JDK 编出的原生镜像 | 原生镜像的下限与上限 |
| **B：原生镜像（新 JDK 编）** | 只换 JDK，参数尽量不动 | 观察新 JDK 对镜像的影响 |
| **C：JVM 模式 + AOT 缓存** | jar 包 + JVM 的 AOT 类装载/链接与 AOT 方法剖析（Leyden 方向） | 原生镜像已是「全量 AOT」，Leyden 的 AOT 缓存主要在 **JVM 模式**发力；只比 A/B 会漏掉这条线 |

再叠加两个可选维度：

- **JDK 轴**：如 JDK 25（LTS 基线）与 JDK 27（新特性）各编一份；
- **GC 轴**：`serial`（默认） / `G1` / `epsilon`（无回收，只适合短命进程）。

维度一多就组合爆炸：**先跑 A/B（同参数换 JDK）这条最干净的对比**，再逐个加维度。

## 3. 实验设计模板

1. **声明假设**：例如「换到新 JDK 后冷启动减少 ≥ 10%」；
2. **固定其余变量**：同一台机器、同一份代码、同一批依赖、参数只改与假设相关的那几行；
3. **两组以上数据**：基线 + 至少一个新版本；每组 5 次取中位数；
4. **记录异常**：某次特别慢或特别快都要写下来（往往原因就是下一次的线索）；
5. **写下结论与不确定处**：结论要能指导「下一个项目该不该照做」。

## 5. 容易踩的测量陷阱

1. **拿「热启动」当冷启动**：文件缓存已在，数字偏乐观 —— 明确定义并每次执行同一流程；
2. **只测一次**：单次数字受杀毒扫描、后台更新影响极大；
3. **内存口径混用**：工作集 vs 提交内存 vs RSS 是三个数，记下来是哪一个；
4. **比较不同平台**：Windows 与 Linux 的启动与内存口径不可直接对比，
   跨平台只比**同一平台内的相对变化**；
5. **忽略预热**：原生镜像没有 JIT 预热，JVM 模式有 —— 长跑场景下 JVM 可能反超，
   这正是要看形态 C 的原因。

## 6. 结论怎么用

- 若原生镜像在**冷启动**明显占优、**内存**不占优：说明收益主要在「点开就能用」，
  那么把它定位成**验证线**（而不是发行方式）就是对的取舍；
- 若新 JDK 带来的改进主要体现在 **JVM 模式的 AOT**：下一轮应优先做形态 C，
  而不是继续堆原生镜像参数；
- 把每条结论回写到这里，并同步到项目文档 —— **下次换项目直接照抄口径**。
