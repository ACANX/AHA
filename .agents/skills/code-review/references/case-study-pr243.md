# 案例：PR #243 的三轮自审（本节技能的取材）

> 场景：桌面端「应用内升级 / 降级」功能（issue #51），**作者即审查者**（Agent 自己）。
> 三轮报告全文在 PR 评论里，编号可直接 `gh api repos/ACANX/AHA/issues/comments/<id>` 取回。
> 本页只留**可复用的判据与结论变化**，不复述报告。

| 轮次 | 审查对象 | 报告 id | 结论 | 产出 |
|---|---|---|---|---|
| 第一轮（全量） | 全部 76 个文件 | [#issuecomment-6211953013](https://github.com/ACANX/AHA/pull/243#issuecomment-6211953013) | **不能合并** —— CI 两个 run 全绿，但功能实际不可用 | P0×3、P1×5、P2×5 |
| 第二轮（复核） | `5fd47c3` | [#issuecomment-6212879773](https://github.com/ACANX/AHA/pull/243#issuecomment-6212879773) | 上轮 P0×3 + P1×5 **都真的落地了**；又挖出 2 条 P1、5 条 P2、5 条 P3 | 其中 **2 条 P1 是修复本身带出来的** |
| 第三轮（复核） | `815c5b0` | [#issuecomment-6213974385](https://github.com/ACANX/AHA/pull/243#issuecomment-6213974385) | 上轮 11 条声明 + P3 全部核实为真修好；本轮 1 条真问题 + 2 条 P3，已修 | 4 条残余**明确归属**，判定**不需要下一轮全量 Review** |

结论的**风险等级变化**：`装了也用不了` → `少数路径 + 边界场景` → `真机验收 + 定向复核`。
这个「降级要给出证据」的写法，是三轮报告最值得复用的部分。

---

## 第一轮：门禁全绿而功能不可用

- **P0-1 引用的产物不在提交里**（见 [缺陷族 1](findings-taxonomy.md#1-引用的产物不在提交里-)）：
  换装 helper 的 Windows 入口被 `.gitignore` 的 `Dist/*` 吞掉 ⇒ 包里没有它 ⇒ 真实安装的升级必然在最后一步失败。
  连带的 P0-3 是**守卫缺口**：守卫只扫已跟踪文件，所以对这件事「不存在」。
- **逃逸链**是这一轮最有价值的产出：忽略规则 → 打包静默跳过 → 守卫取样范围 → 单测自造文件 → 本地预检基于工作区，
  五个环节串成一条完整通路。修法顺序因此定为「**先立守卫**（P0-3）→ 再补产物（P0-1/2）」。
- **P1-7 门挡得太晚**：平台未实现 / 形态不支持的场合，界面允许走完「检查 → 下载 → 解包」才报「包不完整」，
  **把锅甩给包**。
- **P1-5 死代码**：回执与清理只有定义与测试，没有生产调用点 ⇒ 承诺的功能静默缺席、暂存目录 50–110 MB 永不清理、
  配置项成死配置。
- **P1-6 契约冲突**：`restart` 必须是绝对路径，而「只有 jar」的兜底给裸 `java`。

## 第二轮：复核要重验，还要审「修复本身」

- **不采信任何「已修」**：逐条用 `git ls-files`、反向注入、真代码 probe、CI 运行编号重验；
  结论三档 ✅ / ◐ / ❌，◐ 当场升成新编号（P1-6「只修了一半」→ P1-①）。
- **修复带出来的问题**（两类，都在 P1 级）：
  - 上轮的修复**把不一致固化了**：为「绝对路径」写了个只断言列表形状的测试，问题仍在时它也会通过
    （[缺陷族 11](findings-taxonomy.md#11-断言只验形状不验语义-)）；
  - 上轮的「清理」修复**引入了新风险**：启动收尾无条件清暂存，而 helper 可能正在用 ⇒ 用户再启动一次 App
    就把本次升级毁掉（[缺陷族 5](findings-taxonomy.md#5-生命周期与并发-)）。
- **文档漂移**（[缺陷族 9](findings-taxonomy.md#9-文档与实现漂移)）：改了「取消后从头下载」的提示，
  但代码注释 / 用户指南 / 测试名里 4 处仍写「可续传」；设计文档的验收口径写「两个 helper 消失」而实现只删一个
  —— **真机验收会照文档判失败**。
- **计数是编出来的**：`clearOthers() + 1`。
- **守卫的洞与误报**：跳过单行 `run:`、把 `echo` 里的路径当调用、死条件。
- 该轮的 CI 证据写明「Build 7/7 ✅、DesktopNative 8/8 ✅」，
  同时指出两条 P1 属于「**CI 结构上覆盖不到**的路径」。

## 第三轮：能力门要接在所有入口 + 残余归属

- **CLI 绕过了界面上的能力门**（[缺陷族 4](findings-taxonomy.md#4-能力门只接在部分入口-)）：
  `--update-to … --yes` 直接换装 ⇒ 「只剩单体 jar」时换装成功但**没人把程序拉回来**。
  修法要求：门接在**下载之前**（失败要快，别白下几十 MB），CLI 失败返回非 0 且文案可读。
- **残余项归属表**（本轮不修的四条，各写「为什么不在本轮修」与归属）：
  ① 时间窗口是启发式（要换设计，走独立变更 + 定向复核）；② 脚本里仍有模块 cmdlet（观察）；
  ③ 某界面分支在 CI 跑不到（真机项）；④ 复用了不贴切的错误码（影响仅文案）。
- **收工判据**（不是「感觉差不多了」）：
  ① 上轮各条已逐条核实为真修好，本轮唯一实质问题已闭环且有测试；
  ② 剩下 4 点**再读一遍代码也消除不掉**（3 条只能真机 / 特定环境，1 条需要换设计）；
  ③ 下一步是真机验收，暴露结构性问题才重新过一轮。
- 并写明「**唯一会让我改口的情况**」：真机验收暴露结构性问题（如换装链路在真实文件占用 / 杀软下不成立）。

## 三轮之后再补的两条（同样是本技能的来源）

### 1. 能力门也会**拦过头**（[缺陷族 7](findings-taxonomy.md#7-门挡得太晚--理由不准-)）

- 为修「原生镜像被认成 JVM 便携包」下了错包，我顺手加了一层「原生形态不支持自更新」的门，
  理由写的是「该形态的包不在升级通道里」；
- 下一轮实测发现**该理由不成立**（通道契约里本来就有它的 tag 与资产，换装与重启机制与另一种形态同构）⇒
  那道门拦掉的正是**本来能用的功能**，表现为「升级按钮永远是灰的」，被当成 bug 报回来两次。
- 沉淀：**门的每一条理由都要能落到证据上**；复核轮必须重新问一次「这个理由现在还成立吗」；
  撤门时补**正向用例**（而不是只删代码）。

### 2. 判据（正则 / 匹配规则）要**逐条**对照真实样本

- CI 偶发红的真因是重试判据漏了「版本号带后缀」的报错形态；第一次「正向验证」之所以通过，
  是样本里**另一条**目标准确匹配掩盖了写错的那一条。
- 沉淀：判据修改要**一条一条**注入真实样本验证；「整体报绿」不能作为单条判据正确的证据。
  这与[守卫的验证](ci-blind-spots.md#三写完守卫要验它真的会红)是同一套纪律。

---

## 这个案例最该带走的三句话

1. **CI 绿不是功能可用的证据** —— 每一轮都要问「这个问题为什么没被拦住」，并落到具体环节；
2. **「改过了」不是「修好了」的证据** —— 复核要重验，且要审「修复本身带出来的问题」；
3. **报告的价值在结论之外**：逃逸链（该立哪道守卫）、残余归属（谁在哪一轮修）、
   真机验收项（CI 覆盖不到的部分），这三样缺一不可。
