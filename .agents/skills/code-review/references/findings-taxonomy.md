# 缺陷族全表：按族扫，比逐行读更容易挖到 P0/P1

每族给：**判据**（怎么认出来）→ **取证**（用什么命令确认）→ **真实例子**（摘自 [#243 三轮审查](case-study-pr243.md)）。

> 用法：第 2 步「过全量」时对着这张表逐族问一遍；第 4 步「专项深挖」只挑标了 ⚠️ 的几族做深挖。

---

## 1. 引用的产物不在提交里 ⚠️

**判据**：代码 / 打包描述符 / 工作流引用了某个文件，而它可能只存在于工作区。

**取证**：

```bash
git check-ignore -v <路径>            # 被哪条 .gitignore 规则吞掉
git cat-file -e HEAD:<路径>           # 在 HEAD 里存在吗（不存在即致命）
git ls-files <目录>/ | grep -i <关键词>  # 已跟踪清单里有没有
```

**为什么容易漏**：被忽略 ≠ untracked ⇒ `git status` 是干净的，`git add -A` 静默跳过。
三道下游门禁都会跟着失效：打包工具对**匹配不到的 include 静默跳过**、守卫只扫**已跟踪**文件、
单测在临时目录里**自己造**这个文件。

**真实例子**：`Dist/apply-update.cmd`（换装 helper 的 Windows 入口）被 `.gitignore` 的 `Dist/*` 吞掉，
包里没有它 ⇒ 任何真实安装的应用内升级都会在最后一步抛出「安装根里没有换装 helper」。
功能全废，而 CI 两个 run 都是绿的。

**防线**：加一条「**打包描述符里引用的每个手写产物必须存在且被 git 跟踪**」的守卫，并做**反向注入**验证。

## 2. 定义了但没人调用（死代码）⚠️

**判据**：新增了 public 方法 / 配置项 / 回执结构，但生产代码里没有调用点。

**取证**：

```bash
grep -rn "<方法名>" --include=*.java .          # 只看定义与测试 ⇒ 死代码
grep -rn "<配置键>" --include=*.java --include=*.ps1 .
```

**真实例子**：`consumeLastResult()`（上次换装的回执）与 `cleanupAfterSwap()`（清理暂存）全仓只有定义与测试 ⇒
① 用户**从不被告知**上次升级成功 / 失败 / 已回滚；② `<AHA_HOME>/update/<版本>/`（50–110 MB）**永不清理**；
③ 界面给出的 `Update.BackupKeep` 成了**死配置**。

**注意**：这类问题的后果往往不是报错，而是「承诺的功能静默缺席」，所以最容易被漏掉 ——
凡新增了「对外可见的行为」（提示、清理、统计、开关），都要问一句**谁调它**。

## 3. 契约冲突（写方 / 校验方 / 执行方）

**判据**：同一个字段 / 文件被三处不同代码解释，而三处没有共享的常量或测试。

**取证**：把三方代码并排读，用**真代码 probe** 跑一遍最不常见的那条取值（见 [evidence-playbook](evidence-playbook.md#probe)）。

**常见跨语言组合**：Java 写计划 ↔ PowerShell 执行计划；Java 写 JSON ↔ Python 守卫校验；
描述符的 include ↔ 脚本的实际输出名。

**真实例子**：`restart` 字段的语义是「**每个元素 = 一个可执行文件**」（执行方逐元素 `Start-Process`），
而「只有 jar」布局的兜底却往里塞 `[java, -jar, jar]` —— 参数被当成程序。
实测结果：计划创建直接失败，用户只看到一句「拉起命令必须是绝对路径：-jar」；
若校验放宽，执行方会把 `java`（无参）拉起、回执写 `ok=true` ⇒ **应用关了不回来**。

**经验**：契约不一致**通常表现为一句莫名其妙的错误信息**。看到「文案与用户预期完全不符」的报错，
优先怀疑契约，而不是怀疑文案。

## 4. 能力门只接在部分入口 ⚠️

**判据**：同一条能力判定（平台 / 形态 / 权限 / 版本）被写在多个入口，实现时只接了一处。

**取证**：列出所有能发起该动作的入口（界面按钮 / CLI 子命令 / 脚本 / 计划执行方），逐个 grep 那道门。

**真实例子**：界面早已按「只剩单体 jar ⇒ 换装后没人拉回来」拦住升级，`--update-to <版本> --yes`
却直接 `prepareSwap` + `launchHelper` ⇒ 换装成功、**没有人把程序拉回来**，用户的应用就没了。

**配套要求**：门要接在**最贵的动作之前**（失败要快，别白下几十 MB）；CLI 失败要返回非 0 且文案可读，
否则脚本只能看到英文堆栈。

## 5. 生命周期与并发 ⚠️

**判据**：存在「A 正在进行中，B 会动同一批资源」的组合（清理、迁移、备份、上传、构建）。

**取证**：对每个「启动 / 定时 / 收尾」路径，列出它会删 / 改的东西，再问「这东西此刻可能正在被谁用」。

**真实例子**：启动收尾**无条件**清掉其它版本目录，而换装 helper 可能正在等 App 退出 / 拷文件；
用户升级窗口一关、**再双击一次图标**，就会删掉 helper 正在用的新包目录 ⇒ 本次升级被自己毁掉，
回执还把锅甩给包。备份保留数为 0 时更狠：回滚会把「本来存在的文件」当本次新增删掉。

**修法方向**：以「在飞标记 / 锁」为准，而不是以时间窗口为准（时间启发式只能算兜底，命中率取决于磁盘速度）。

## 6. 静默失败与吞异常

**判据**：`catch` 之后只有日志、没有用户可见的结局；或 `catch` 的类型比实际抛出的窄。

**取证**：列出该流程可能抛出的异常类型，与 `catch` 的类型比对；看失败后**界面处于什么状态**。

**真实例子**：`startSwap` 只 `catch (UpdateException)`，`RuntimeException` 会让界面**永久 busy**（按钮永远灰）；
自证失败分支的回滚没有 `try/catch`，回滚里一次 `Copy-Item` 抛异常 ⇒ 脚本**整个崩掉**、
不写回执、**不重启** ⇒ 用户面对一个打不开的目录（与脚本自己声明的口径直接矛盾）。

**判据加一句**：**凡是「失败路径」也要写跨语言的用户可见结果**（回执、退出码、界面提示）的流程，
失败路径必须与成功路径同样被审查。

## 7. 门挡得太晚 / 理由不准 ⚠️

**判据**：能力判定发生在昂贵动作（下载 / 解压 / 构建）之后，或拦住用户的理由与真实原因不符。

**真实例子**：Linux/macOS（POSIX helper 未实现）与另外的部分形态，界面允许走完「检查 → 下载 → 解包」
才报「包不完整」—— **把锅甩给包**，用户会去查包，而真因是平台没实现。

**反向教训（同为 P1 级）**：**门也可能拦过头**。某一轮为了止血加了一层「某形态不支持自更新」，
理由写的是「该形态的包不在升级通道里」；下一轮实测发现**该理由不成立**（通道契约里本来就有它的 tag 与资产），
于是那道门拦掉的正是**本来能用的功能**，表现为「按钮永远是灰的」，被用户当成 bug 报了两次。

⇒ **能力门的每一条理由都要能落到证据上**（契约里的 tag / 资产名、代码里的调用链），
并在下一轮复核时**重新问一次「这个理由现在还成立吗」**。

## 8. 计数与承诺是编出来的

**判据**：数字 / 文案与实现无关（`x = f() + 1`、`f()` 返回 void）；文案承诺的能力实现没做。

**取证**：`grep` 该数字的赋值来源；拿文案里的关键词（「续传」「可恢复」「自动清理」）去实现里找对应逻辑。

**真实例子**：`stagingCleared = staging.clearOthers(v) + 1`（`clear()` 返回 void）⇒ 什么都没清时
用户也会看到「清理 1 个暂存目录」；面向用户的指南写着「`.part` 可续传」，实现却是 `TRUNCATE` **从头下**。

**教训**：文案改动要**回头扫全仓旧说法**（代码注释、测试名、用户指南、设计文档的验收口径）。
一次只改「提示语」而留下 4 处旧描述，下一轮真机验收会照着旧口径判失败。

## 9. 文档与实现漂移

**判据**：设计文档的**验收口径**、用户指南的描述、代码注释与实现不一致。

**取证**：用实现里的关键词反查文档，用文档里的验收项反查实现。

**真实例子**：设计文档 §8.2 的验收项写「**两个** helper 文件消失」，实现只有 `.ps1` 自删、
`.cmd` 由启动收尾删 ⇒ 真机验收会照文档判失败（实际行为无害）。

**优先级**：**面向用户的指南**与**验收口径**优先修，因为它们会直接误导下一步的真机验证。

## 10. 守卫有洞或会误报 ⚠️

**判据**：守卫的匹配方式与实际写法有系统性偏差（跳过某类行、只看某一类文件、拿子串当调用）。

**取证**：**正向 + 反向注入各一次**：

```bash
# 正向：构造一个应被抓住的违规，守卫必须红
# 反向：删掉守卫依赖的前提（如 .gitignore 例外 / 某行断言），守卫必须红且指名准确
```

**真实例子**：守卫直接跳过以 `run:` 开头的行 ⇒ **单行** `run: python3 …` 抓不到；
反过来 `echo "… python3 bin/CheckDocs.py …"` 被误报成调用；还有一处 `or "\n" in line` 是死条件。
另有守卫只扫**已跟踪**文件，于是「文件没进提交」这件事对它不存在。

**判据加一句**：守卫的修复也要**逐条对照真实样本**验证 —— 多行样本会掩盖写错的那一条
（例：一条正则写错，但样本里另一条目标准确匹配，于是「验证通过」）。

## 11. 断言只验形状不验语义 ⚠️

**判据**：测试断言列表长度 / 类型 / 是否存在，却不断言内容与语义。

**真实例子**：为「拉起命令必须是绝对路径」写了个**只断言列表形状**的测试就宣布修好 ——
它把这个不一致**固化**成了「正确」，下一轮才靠真代码 probe 挖出来。

**判据加一句**：修完一个问题，问「**我这条测试会不会在问题仍然存在时也通过？**」
会通过 ⇒ 测试没有覆盖这个问题的语义。

## 12. 平台与形态差异（JVM ↔ 原生镜像）⚠️

**判据**：功能只在原生镜像 / 特定平台 / 特定文件系统上失败，而 CI 只跑 JVM 与 ubuntu。

**取证**：拿日志里的 `Caused by` 去反查哪些机制在原生镜像里不同（反射、资源、运行期初始化、模块系统）。

**真实例子**（两个真机崩溃，CI 全绿）：

- FXML 里唯一一处**大写枚举值**属性 ⇒ 原生镜像里 `BeanAdapter` 的反射强转（`TabPane$TabClosingPolicy`）
  找不到元数据 ⇒ **设置面板打不开**（JVM 上永远不会复现）；
- Jackson 反序列化 `record` 需要 **record components**，而更新模块的 21 个 record / enum
  **一个都没登记** ⇒ 原生包一点「检查更新」必崩。

**沉淀方式**：这类问题**不要**靠单测挡（测不到），要靠
① 静态守卫（如「FXML 里不许出现大写枚举值属性」「更新模块的 record / enum 必须登记」）；
② 原生镜像规范与元数据技能（[graalvm-reachability-metadata](../../graalvm-reachability-metadata/SKILL.md)）；
③ **真机验收项**。

## 13. 文件属性与权限

**判据**：复制 / 移动文件时带着属性、时间戳、只读位；跨平台文本文件的行尾 / BOM / 编码。

**真实例子**：`COPY_ATTRIBUTES` 把源文件属性带到落地文件，源被标记只读时，
Windows 上**下一次**升级同一个文件会失败；另一个：批处理文件里写中文注释（666 个非 ASCII 字节），
一旦被跟踪就违反它自己声明的「纯 ASCII + CRLF」规约。

**判据加一句**：这类问题**首次**运行看不出来，要在审查时问「第二次、第三次还会成功吗」。

## 14. 资源不回收

**判据**：新增了暂存 / 缓存 / 备份 / 解压目录，但没有对应的清理路径（或清理是死代码，见第 2 族）。

**取证**：`grep` 创建目录的地方，看谁负责删；把「保留数 / 保留期」配置的**每个取值**（含 0）走一遍。

**真实例子**：暂存目录每次升级留一份包（50–110 MB）且永不清理；清理逻辑存在但没人调用。

---

## 15. 安全边界

**判据**：网络重定向、路径拼接、外部输入解析、解密与校验等边界只做了一半校验。

**真实例子**：重定向逐跳查白名单，但**只校验 host、不校验协议**（`https → http` 降级可通过）；
执行脚本只把 JSON 里的路径当字符串拼接，没有「必须落在安装根内」的二次校验（Java 侧有，
脚本侧读的是 JSON、不经过 Java）——同权限下不构成提权，但文档把「防注入」列为契约，两边都校验更稳。

**判据加一句**：**文档里声明的安全契约，在每一处解析该输入的代码里都要有对应实现**。
