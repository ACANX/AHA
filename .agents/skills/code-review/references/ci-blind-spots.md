# 逃逸链：为什么「CI 全绿」而功能不可用

审查里最值钱的产出不是「发现一个 bug」，而是**说清这个 bug 是怎么从三道门禁下溜过去的** ——
它决定了要立哪道守卫，而不是「下次小心点」。

**用法**：对每条 P0/P1 追问一句「**为什么 CI 没红**」，把答案填进下表（逃逸环节 → 为什么没拦住）。
若某条 P0 的逃逸链里有多个环节，**优先修能同时挡住多个环节的那一个**（通常是守卫）。

---

## 一、典型逃逸通路

| # | 逃逸环节 | 为什么没拦住 | 堵法 |
|---|---|---|---|
| 1 | 文件被 `.gitignore` 吞掉 | 被忽略 ≠ untracked ⇒ `git status` 干净、`git add -A` 静默跳过 | 守卫断言「产物已跟踪」；反向注入（`git rm --cached`）验证 |
| 2 | 打包描述符引用不存在的产物 | 打包工具对**匹配不到的 include 静默跳过**，不报错 | 守卫对照「描述符 include ↔ `git ls-files`」 |
| 3 | 守卫只扫**已跟踪**文件 | 被忽略的文件对守卫**不存在**（连「编码不合规」都没机会说） | 守卫的取样范围与「提交内容」对齐 |
| 4 | 单测在 `@TempDir` 里**自己造**被依赖的文件 | 测的是「逻辑对」，不是「真包里有」 | 断言「真产物存在」的守卫，而非再造一份 |
| 5 | 本地预检基于**工作区**文件 | 工作区有、提交里没有 ⇒ 预检通过 | 预检也要 `git ls-files` / `cat-file -e` 核对 |
| 6 | 测试跑在 **JVM**，功能在**原生镜像** | 反射 / 资源 / 运行期初始化在两者不同（原生里直接崩） | 静态守卫（如「record / enum 必须登记反射」「FXML 不许出现大写枚举值属性」）+ 真机项 |
| 7 | 测试跑在 **ubuntu**，功能在 **Windows** | 平台分支 / 批处理交接根本没执行到 | Windows 腿加一条「真跑那个脚本」的步骤 + 真机项 |
| 8 | 界面分支在 CI **跑不到** | 例如平台门先命中，那棵「只剩单体 jar」的界面分支永远不执行 | 真机验收项（写清第几项） |
| 9 | 新增的是**死代码**（没有调用点） | 没有任何测试或流程会走到它 | 守卫/审查动作：grep 调用点 |
| 10 | **生命周期 / 并发**场景 | CI 不会「换装进行中再启动一次」 | 单测覆盖并发入口（可行时）+ 真机项 |
| 11 | **时间启发式**判据（如「10 分钟窗口」） | CI 跑得飞快，永远落在窗口内 | 换成持锁文件 / 显式标记；时间窗口只作兜底 |
| 12 | **计数 / 文案**类问题 | 没有断言，也不报错 | 用例断言「计数只算真的删掉的」；文案与实现同变更 |
| 13 | 依赖**外部服务**（发布页资产 / 下载） | CI 用伪造数据或跳过网络步骤 | 真机项 + 网络异常的降级路径单测 |

## 二、守卫守则（该不该立守卫）

立守卫要按「**是否必然复发且复发时静默**」判，不是「凡是出过的问题都立一道」：

| 情况 | 处置 |
|---|---|
| 必然复发 **且** 复发时静默（无报错、无测试变红） | ✅ 立**毫秒级静态守卫**（扫文件 / 扫元数据 / 扫描述符），并在规范里写明判据 |
| 只能靠真机 / 真实环境触发（文件占用、杀软、原生 exe 替换） | ❌ 不立守卫 → 列成**真机验收项**（一次确认） |
| 一次性验证（这次跑通即可） | ❌ **绝不**做成每次构建都跑的自测 / 门禁 |
| 影响仅文案 / 计数 | ⚪ 用例断言即可（若已有测试），不必新增守卫 |

> 这条来自真实教训：一次「换装 helper 自测」被做成每次构建都跑的门禁，属**一次性验证常驻化**，
> 已按 ACANX 判定移除。**留守卫的唯一理由是「以后必然复发且复发时静默」**。
