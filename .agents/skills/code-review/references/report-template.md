# 审查报告模板

报告发在 **PR 评论**（`gh pr comment <n> --body-file <文件>`），标题带轮次与审查对象（提交号）。
正文中文、全角标点、结论先行；`文件:行` 给位置；命令与输出用围栏代码块逐字照抄。

---

## 一、首次全量审查

```markdown
## 代码审查报告（PR #<n> 全量 · <日期>）

审查范围：本 PR 全部 <N> 个文件，重点看 <换装 / 下载 / 配置 / 打包 / 守卫>。

**结论：<不能合并 / 可以合并 / 修掉 P0 后可合并>。** <一句话说清最致命的那条与它的后果>

### 为什么 CI 全绿：一条完整的「逃逸链」

| 逃逸环节 | 为什么没拦住 |
| --- | --- |
| <文件> 被 `.gitignore:<行>` 忽略 | `git add -A` 静默跳过，`git status` 也干净（被忽略 ≠ untracked） |
| CI 出包（描述符里有 include） | 打包工具对匹配不到的 include **静默跳过** |
| `bin/Check<X>.py` | 只扫 git 跟踪的文件 ⇒ 被忽略的文件对守卫不存在 |
| 单元测试 | 在 `@TempDir` 里**自己造**该文件，测不到「真包里有不有」 |

复现证据：

```bash
$ <命令>
<输出>
```

---

## P0 · 合并前必修

| # | 问题 | 位置 | 影响 / 修法 |
| --- | --- | --- | --- |
| **P0-1** | <一句话：现象 + 后果> | `文件:行` | <影响；修法要具体到加什么> |

## P1 · 应修，别留给下一轮

| # | 问题 | 位置 | 说明 |
| --- | --- | --- | --- |
| **P1-4** | … | `文件:行` | … |

## P2 · 可后置，但要进 TODO

| # | 问题 | 位置 |
| --- | --- | --- |
| P2-9 | … | `文件:行` |

## P3 · 顺手修

列出即可。

---

## 这轮做得对的地方（保留，别退化）

- <逐条：某处实现与注释一致、某处先备份再替换、某处路径校验三处都有…>

## 建议顺序

**P0-1 → P0-3（先立守卫）→ P0-2 → P1-…**。<说明为什么某个顺序更优：例如「先立守卫能把整类错误永久挡在 CI，而不是靠人眼」>

> 本报告由 Agent 自查产出（PR 作者即 Agent）。<如实说明自己此前哪些结论不成立>
```

**要点**

- **结论先行**，别把最致命的放在表格中间；
- 每条 P0 都给出**「修法」**，不是只描述现象；
- P2 要明确写「进 TODO」（否则等于丢弃）；
- 一定写「做得对的地方」：下一轮优化时才不会把对的改坏；
- 自审时**主动声明**哪些此前的「验证通过」实际不成立。

## 二、复核轮（第二轮及以后）

```markdown
## 第 <k> 轮代码审查（对象：`<sha>`，基线 `<sha>`）

> <自审 / 他审>，且刻意**不采信上一轮的任何「已修」结论**：每条都用命令 / 反向注入 / 真代码 probe 重新验一遍。

**结论：<上一轮的 P0×3、P1×5 都真的落地了 / 还有 N 条没修好>**；本轮另发现 <N 条 P1 / N 条 P2>，
其中 <N> 条是**修复本身带出来的**。风险等级已从「<装了也用不了>」降到「<少数路径 + 边界场景>」，
**<仍不建议 / 可以 > 合并**。

### 一、上一轮问题复核（逐条自己验过）

| 上轮问题 | 复核 | 我的证据 |
|---|---|---|
| **P0-1** <一句话> | ✅ 真修好 | `git ls-files` 有它；**反向注入**（`git rm --cached`）→ 守卫变红并指名 |
| **P1-5** <一句话> | ◐ 接上了，但<缺什么> → **P1-②** | <命令输出 / 用例名 / CI 运行编号> |
| **P1-6** <一句话> | ◐ **只修了一半** → **P1-①** | 真代码 probe（下方） |

### 二、新发现

#### P1-① <问题一句话> —— <我上轮说的「已修」是错的>

- 位置：`A.java:137-161`、`B.java:255-257`、`C.ps1:<行>`
- 契约冲突 / 实测（跑真代码，不是推演）：

```
<命令 + 输出>
```

- 后果：<用户会看到什么 / 数据会怎样>
- **我上轮的错**：<写了个只断言形状的测试就宣布修好 —— 它把这个不一致固化了>
- 修法（二选一）：<…>

…

### 三、CI 证据（`<sha>`）

```
Build <7/7 ✅>｜DesktopNative <8/8 ✅>｜… ｜单测 <N> 项 0 失败
```

⇒ <说明 CI 覆盖到了哪些、哪些路径「CI 结构上覆盖不到」>

### 四、剩余残余（本轮不修，明确归属）

| # | 残余 | 为什么不在本轮修 | 归属 |
|---|---|---|---|
| 1 | <时间窗口是启发式> | 要根治得换成持锁文件，属**换设计的小改动**，应作独立变更 + 定向复核 | 待安排（TD-…） |
| 2 | <界面分支在 CI 跑不到> | 只能真机覆盖 | 真机第 <k> 项 |

### 五、结论：<不需要 / 需要>下一轮全量 Review

三条具体理由（不是「感觉差不多了」）：

1. <上一轮各条已逐条核实为真修好，本轮唯一实质问题已闭环且有测试>；
2. <剩下 N 点再读一遍代码也消除不掉：X 条只能靠真机 / Windows 环境，Y 条需要换设计>；
3. <因此下一步：真机验收 → 若暴露问题只做定向复核 → 新功能开工时再走常规 Review>。

**唯一会让我改口的情况**：<真机验收暴露结构性问题（例如换装链路在真实文件占用 / 杀毒软件下不成立）——那就重新过一轮>。
```

**要点**

- 复核表**必须**有「我的证据」一列，且证据是**命令输出 / 注入结果 / CI 运行编号**；
- 复核结论只允许 ✅ / ◐ / ❌ 三档，◐ 必须当场给出新编号；
- 「修复本身带出来的问题」单独点出（这是复核轮最常见的收获）；
- 残余项写**为什么这轮不修**与**归属**，不能只写「待办」；
- 结尾写清「什么情况下我会改口」，避免「无限轮次」也避免过早收工。

## 三、措辞纪律

| 不要写 | 要写 |
|---|---|
| 「可能有风险」 | 「在 <条件> 下必然发生，证据：<命令输出>」 |
| 「已确认修复」 | 「`git ls-files` 里有它；反向注入后守卫变红（输出见上）」 |
| 「建议加强测试」 | 「补一条断言 <语义> 的用例：现有形状断言在问题仍存在时也会通过」 |
| 「这里好像不太对」 | 要么取证 → 成 finding；要么删掉 |
| 把推断混进事实 | 标注成色：已观测 / 机制模型 / 未复现（见 [evidence-playbook](evidence-playbook.md)） |

**自己的错要显式写出来**：例如「我上轮的『已修』是错的」「此前几轮『本地验证通过』的说法不覆盖
『这个文件是否真的在提交里』，在这点上不成立」。悄悄改口会让下一轮无法信任任何历史结论。
