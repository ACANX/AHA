# 代码审查：用命令取证，不用印象判分

> 本技能的取材：一次真实的多轮审查（[#243 三轮](references/case-study-pr243.md)）——
> 第一轮在 **CI 两个 run 全绿** 的情况下判出「功能实际不可用」，并补齐了「装了也用不了」的逃逸链。
> 结论只有一句：**CI 绿不是功能可用的证据；「改过了」不是「修好了」的证据。**

## 何时使用

| 场景 | 用法 |
|---|---|
| 被要求审查一个 PR / 分支 / 提交（含开放前自查） | 走「完整审查」六步 |
| 上一轮审查的问题已修，被要求复核 | 走「复核轮」：**不采信任何「已修」声明**，逐条重验，并审查修复本身 |
| 判断「这个能不能合」 | 给判级结论 + 残余归属 + 真机验收项，三者缺一不可 |
| 真机 / CI 暴露了问题，要定位 | 先按本文取证，再转 [doc-recording](../doc-recording/SKILL.md) 写排查记录 |

**不适用**：纯格式 / 文案的改动（跑 `bin/Check*.py` 即可）；改完就删的临时脚本。

## 四条硬规则

1. **不采信任何「已修」声明 —— 包括自己上一轮的。** 每条都用命令重验。前两轮的教训正是
   「门禁全绿、声明都写完了，功能还是不行」。
2. **结论必须能被命令复现，并区分三种成色**：**已观测事实**（有命令输出）／**机制行为模型**
   （读代码推出的必然结果，写明推导链）／**未定位未复现**（如实标出，不猜）。禁止把第三种写成第一种。
3. **审查对象包括「修复本身」和「上一轮新加的约束」。** 修复带出新问题很常见（某轮 2 条 P1 都是修复带出来的）；
   上一轮加的守卫 / 能力门也要问一句「它的理由现在还成立吗」——不成立的限制会把能用的功能关掉。
4. **每轮必须给出三样东西**：① 判级结论；② **残余项归属**（谁能修、为什么这轮不修）；
   ③ **CI 覆盖不到的真机验收项**（列成可逐条打勾的清单，交给能做真机的人）。

## 完整审查六步

| 步 | 动作 | 产出 |
|---|---|---|
| 0 | **定范围**：`gh pr view <n> --json files` 列出改动文件，声明本轮覆盖哪些、明确不看哪些 | 范围声明（写进报告头） |
| 1 | **先读契约再读实现**：设计文档 / 规范 / 接口注释里对该行为的承诺 | 「要求 vs 实际」的对照起点 |
| 2 | **过一遍全量，按缺陷族扫**（[findings-taxonomy](references/findings-taxonomy.md)）出候选清单 | 候选清单（不急着判级） |
| 3 | **逐条取证**（[evidence-playbook](references/evidence-playbook.md)）：每条候选都要有命令 / 运行时证据，取不到证据的降级为「推断」或删掉 | 判级后的 findings 表 |
| 4 | **专项深挖**：① 逃逸链（[ci-blind-spots](references/ci-blind-spots.md)）；② 每条能力门是否接在**所有**入口；③ 生命周期与并发；④ 死代码（定义无调用） | P0/P1 的实质来源 |
| 5 | **判级 + 残余归属**：[P0–P3 判级表](#judge) + 每条残余写明归属与理由 | 结论 |
| 6 | **写报告**（[report-template](references/report-template.md)）：结论先行，按级列表，附「做得对的地方」，给修复顺序 | PR 评论 |

> 顺序上的经验：**先立守卫的修复要排在最前**，因为它能把整类错误永久挡在 CI，而不是靠下一次人眼。
> 例：某轮的修复顺序定为 `P0-1 → P0-3（先立守卫）→ P0-2`，而不是按编号顺序。

## 复核轮（第二轮及以后）

- 逐条列「上轮问题 → 复核结论 → 我的证据」三列表；**证据是命令输出、反向注入结果或 CI 运行编号**，
  不写「已确认」这种结论词；
- 结论只允许三档：✅ 真修好 / ◐ 部分修好（同一行里直接给出新编号）/ ❌ 没修好或修反了；
- 主动找**修复带出来的新问题**（改了 A 破坏 B、守卫误报、门挡太晚）；
- 结尾给「**是否还需要下一轮全量审查**」的**具体理由**（不是「感觉差不多了」），
  并写明「**唯一会让我改口的情况**」。

## 判级<a id="judge"></a>

| 级别 | 判据 | 处理 |
|---|---|---|
| **P0** | 功能在真实环境**不可用**，或数据 / 安装会损坏，或安全边界被破 | 合并前必修；通常需要同时补一道守卫 |
| **P1** | 少数路径 / 边界场景会坏；契约不一致；承诺的能力没接上 | 应在本轮修，别留给下一轮 |
| **P2** | 影响有限（文案、计数、清理、属性），或需要换设计的中等改动 | 可后置，但**必须进 TODO / Issue**，不能只写评论 |
| **P3** | 顺手能改的小问题 | 列出即可，改不改都行 |

判级只看**后果**，不看修复难度。**修复难度高不降级**（写进残余并说明归属）；
**「只在某个平台/形态才触发」也不降级**——那正是真机验收项。

## 缺陷族速查

按族扫比逐行读代码更容易挖到 P0/P1。各族的手法与真实例子见
[findings-taxonomy](references/findings-taxonomy.md)。

| 族 | 一句话 |
|---|---|
| 引用的产物不在提交里 | 被 `.gitignore` 吞、assembly 静默跳过、只在工作区 |
| 定义了但没人调用 | 回执 / 清理 / 配置项成死代码（`grep` 调用点） |
| 契约冲突 | 写方 / 校验方 / 执行方对同一字段理解不同（常跨 Java ↔ 脚本） |
| 能力门只接在部分入口 | 界面拦住了，CLI 绕过去了 |
| 生命周期与并发 | 换装 / 上传 / 迁移**进行中**时另一条路径把资源清掉 |
| 静默失败 | 吞异常、`catch` 范围过窄 ⇒ 界面永久 busy；失败要**写得出来** |
| 门挡得太晚 | 白下几十 MB 才报「包不完整」——失败要快，且理由要准 |
| 计数与承诺编出来的 | `x = f() + 1`；文案承诺「可续传」而实现每次重下 |
| 文档与实现漂移 | 改了行为没回头改注释 / 指南 / 测试名里的旧说法 |
| 守卫有洞或会误报 | 只扫已跟踪文件、跳过单行 `run:`、把 `echo` 当调用 |
| 断言只验形状不验语义 | 测试把实现的不一致**固化**成「正确」 |
| 平台与形态差异 | JVM 能过、原生镜像崩（反射 / 资源 / 初始化） |
| 文件属性与权限 | 复制属性把只读带过去，**下一次**同文件升级失败；批处理编码 |
| 资源不回收 | 暂存 / 缓存 / 备份目录永不清理，磁盘只涨不落 |

## 收尾自检

- [ ] 范围声明写了（覆盖哪些文件 / 哪些明确不看）；
- [ ] 每条 finding 都有**命令可复现**的证据或明确标注为推断；行号用 `文件:行` 格式；
- [ ] 检查了「修复本身」与「上一轮加的约束」；
- [ ] 每条能力门都对着**所有入口**（界面 / CLI / 脚本）核过；
- [ ] 逃逸链问过：这轮没被拦住的问题，**为什么 CI 没红**？
- [ ] 死代码问过：新增的回执 / 清理 / 配置项，**调用点在哪**？
- [ ] 写了「这轮做得对的地方（保留，别退化）」；
- [ ] 残余项有归属，需要跟踪的已登记 TODO / Issue（见 [issue-tracking](../issue-tracking/SKILL.md)）；
- [ ] 真机验收项列成可打勾清单，并说明每项**为什么只能真机验**；
- [ ] 自己的错（含被推翻的上一轮结论）**明确写出来**，不悄悄改口。

## 常见错误

| 错误 | 后果 | 正确做法 |
|---|---|---|
| 拿 CI 绿当通过 | 「装着用不了」的功能被放行 | 门禁覆盖不到的路径，一律按未验证处理 |
| 只读 diff 不跑命令 | 结论无法复现，等于印象 | 每条结论配一条能重跑的命令 |
| 采信「已修」 | 上一轮的洞原样留在原地 | 逐条重验，用注入 / probe / CI 编号作证 |
| 只看新增行 | 漏掉「旧代码被新行为破坏」 | 顺新行为反查所有受影响的调用方与入口 |
| 只报问题不报好的 | 下一轮优化时把对的改坏 | 附「做得对的地方」清单 |
| 残余项只写评论 | 下一轮无人接手，重复劳动 | 归属明确，需要跟踪的进 TODO / Issue |
| 推断写成结论 | 真机验证按错的方向走 | 标注成色：已观测 / 机制模型 / 未复现 |
| 按修复难度降级 | 真问题被降成「以后再说」 | 判级只看后果 |
