# 文档记录：待办 / 开发日志 / 排查记录

仓库有三类**过程记录**，各自有独立目录与命名规则。本技能说明**什么时候写哪一类、写什么、
怎么命名、写完要登记什么**。它们不是可选项：不记录等于没发生——下一轮没人知道做过什么。

## 何时使用

| 触发 | 记录动作 |
|---|---|
| 完成一个功能 / 改动 / 修复 | 写一篇**开发日志**（`Docs/DevLog/`） |
| 排查并解决一个问题（含事故复盘） | 写一篇**排查记录**（`Docs/Troubleshooting/`）；解决过程中若牵出遗留项，另开 Issue |
| 产生一个本轮不做的待办 | 建一个 **TD 文件**（`Docs/TODO/`）+ 登记清单 + 需要长期跟踪的**开 Issue** |
| 认定某件事「做不到」或「决定暂缓」 | 在 `Docs/PLAN.md` 追加**结论与依据**（不追加待办） |
| 某个文档 / 设计稿 / 脚本不再维护 | 用 `git mv` 移入 `Archive/`，文件头注明「已废弃」 |

## 分流表（写哪里 / 什么命名 / 依据）

| 场景 | 目录 | 命名 | 规范与模板 |
|---|---|---|---|
| 待办清单与进度 | `Docs/TODO/` | `README.md`（固定名） | [README](../../../Docs/TODO/README.md) |
| 单个待办详情 | `Docs/TODO/` | `TD-PPPPP-大驼峰英文标题.md`（五位从 `00001` 全局自增） | 同上；内容参考对应 Issue |
| 已完成事项 | `Docs/DevLog/` | `yyyyMMdd-HH.md` | [README](../../../Docs/DevLog/README.md)（含完整模板） |
| 问题排查 / 事故复盘 | `Docs/Troubleshooting/` | `TS-yyyyMM-大驼峰英文标题.md` | [README](../../../Docs/Troubleshooting/README.md) + [TS-Template.md](../../../Docs/Troubleshooting/TS-Template.md) |
| 做不到 / 已暂缓的结论 | `Docs/PLAN.md` | 追加小节 | `DocumentationSpec.md` §4 |
| 已废弃资料 | `Archive/` | 保持原名 + 头注「已废弃（YYYY-MM-DD）」 | [README](../../../Archive/README.md) |

**硬性**：不得写进 `Docs/TODO.md`（已冻结）；不要把待办只留在对话里。

## 通用纪律

1. **同一变更内完成**：代码改动与对应记录在同一次提交 / PR 内更新，不要「下次补」；
2. **命名即契约**：命名不符 `DocumentationSpec.md` §1 会被 `bin/CheckDocs.py` 判失败；
3. **先取证再下结论**：记录里写「要求 vs 实际」的对照，不写「感觉」「大概」；
4. **排查与完成分开写**：排查过程属 Troubleshooting，DevLog 只引用，不搬过程；
5. **收尾前跑一次** `python3 bin/CheckDocs.py`。

## 三类记录的必备内容

### 待办（TD 文件）

- 头部引用块：待办编号 / 标题 / **状态** / 跟踪 Issue / 创建日期 / 最后更新；
- 正文建议：**来源 → 现状（含取证）→ 需求或待拍板 → 验收标准 → 关联**（可直接参考 Issue 正文）；
- 状态变化时**同时**更新 TD 文件头部与 `Docs/TODO/README.md` 清单该行；
- 完成后在备注里写**依据**（CI 运行编号 / PR / 实测），不要只写「完成」。

### 开发日志（DevLog）

必备小节（详见该目录 README 的模板）：任务概述 / 完成内容 / 技术要点 / 修改文件清单 /
验证 / 遇到的问题（只写结论）/ 待办事项 / 工时统计。

- **只写已完成的事**；未完成项指向 `Docs/TODO/` 或 Issue；
- **不写排查过程**，遇到问题只给「现象 / 根因 / 解决」并引用 TS 文件名；
- 验证一栏写 **CI 结果**（本地不跑 Maven，见 `AGENTS.md`）。

### 排查记录（TS 文件）

必备小节（见 `TS-Template.md`）：现象 / 排查过程（含取证对照表）/ 根因 / 修复 / 验证 /
教训与沉淀 / 涉及文件。

- 给出**原始报错或日志**（逐字照抄）；
- 被排除的假设也要写，并说明为什么能排除；
- 已落到哪条规范 / 检查脚本 / 技能里要写明；没有就写「未落规范」；
- 牵出的遗留事项**另开 Issue**，记录里只引用编号。

## 命名速查

| 类型 | 正则 |
|---|---|
| 待办详情 | `TD-\d{5}-[A-Za-z0-9]+\.md` |
| 排查记录 | `TS-\d{6}-[A-Za-z0-9]+\.md` |
| 开发日志 | `\d{8}-\d{2}\.md` |

`bin/CheckDocs.py` 会校验上表（含 `TD-` 编号重复），`Archive/` 不检查。

## 收尾自检

- [ ] 触发场景对应的记录**已创建 / 已更新**，且与代码在同一提交；
- [ ] 文件名符合命名速查表；
- [ ] 待办已登记进 `Docs/TODO/README.md` 清单，需要长期跟踪的已开 Issue；
- [ ] 排查记录与开发日志**互不混用**（过程在 TS、完成在 DevLog）；
- [ ] `python3 bin/CheckDocs.py` 通过。

## 常见错误

| 错误 | 后果 | 正确做法 |
|---|---|---|
| 把排查过程写进 DevLog | 开发日志变成流水账，检索不到结论 | 过程进 `Docs/Troubleshooting/`，DevLog 只给结论 + 引用 |
| 待办只写在对话里 | 对话滚走即丢失，无人知道做过没有 | 建 TD 文件 + 登记清单 + 开 Issue |
| 完成后不更新状态 | 清单与实际不符，重复劳动 | 同一变更内更新 TD 头部与清单行 |
| 文件名随意起 | 排序与检索失效，CI 判失败 | 按命名速查表；模板文件是唯一例外 |
| 用 `Archive/` 当回收站 | 归档里混入仍在维护的内容 | 只有**确定不再维护**的才移入 |
