# 遗留事项用 Issue 跟踪

> **规范**（状态机、开单与关闭判定、状态与 TD 看板对应）：`Docs/DevSpec/IssueTrackingSpec.md`；
> 本文只保留**操作**（判定速查、命令、正文骨架、关闭评论模板）。两者冲突以规范为准。

## 何时使用

出现下列任一情况时：

- 本轮**未能闭环**的问题（查不动、需外部环境、需后续迭代）；
- 需要**人拍板**的取舍项（技术上无唯一正解）；
- **自动化做不到、必须由人完成**才能收口的事（推送、仓库 / 分支保护设置、平台侧配置、外部环境验收）；
- 从设计文档 / 规范里读出的、暂时不动的已知缺口。

**判定标准**：一个遗留问题如果**不适合下一轮立即动手**，就应该是一条 Issue。

## 硬性约定

1. **不得写进已删除的暂存区文件**（`Docs/TODO.md` / `Docs/PLAN.md` / `Docs/Dbsx.txt`，2026-10-17 删除）；
   待办一律登记到 **`Docs/TODO/`**：
   建一个 `TD-PPPPP-大驼峰英文标题.md`（五位编号从 `00001` 全局自增），
   并在 [`Docs/TODO/README.md`](../../../Docs/TODO/README.md) 的清单里加一行（状态 + Issue 编号）。
2. **不得只在对话里交代**。对话会滚走：漏掉之后既没有闭环，也无从判断「到底做过没有」。
3. 开 Issue 前先**搜索是否已有同类 Issue**（`gh issue list --search`），避免重复；已有则补充评论而不是新开。
4. 关闭 Issue **需要 ACANX 授权**；Agent 不自行关闭，除非用户明确要求。

## 何时不用

| 场景 | 去处 |
|---|---|
| 本轮就能改完的缺陷 | 直接改，不必开 Issue |
| 待办清单登记 | `Docs/TODO/`：`TD-PPPPP-*.md`（详情）+ `README.md`（清单与进度） |
| 排障 / 事故复盘 | `Docs/Troubleshooting/`（`TS-yyMM-NNN-英文词序.md`），必要时再开 Issue 长期跟踪 |
| 已完成事项的记录 | `Docs/DevLog/`（`yyyyMMdd-HH.md`，规范与模板见该目录 `README.md`） |
| 「做不到 / 已暂缓」的**结论**及其依据 | 对应 `Docs/TODO/TD-*` 的「结论 / 已排除方案」小节（不追加待办） |
| 已废弃的历史资料 | `Archive/`（保持原名，头部注明「已废弃」） |
| 已定方案的详细设计 | `Docs/Design/` 对应文档 |

> 三类记录（待办 / 开发日志 / 排查记录）的**写法、时机与验收自检**见技能
> [doc-recording](../doc-recording/SKILL.md)。

## 写法

### 标题

`模块/主题：一句话说清要解决什么`。例：

- `CLI：Windows 终端多行粘贴兼容性（conhost 下仍会逐行提交）`
- `原生镜像：扩展系统与 native-image 的根本冲突与降级策略（E-01）`

避免「优化一下」「看看这个」这类无法检索的标题。

### 正文结构

```markdown
## 来源
（设计文档 / 规范 / TODO 编号 / 对话结论——可追溯）

## 现状
（实测到的现象与证据，尽量给命令与输出，不给「感觉」）

## 需求 / 待拍板
（要做成什么样；若需拍板，列出可选项与各自代价）

## 验收标准
- [ ] 可判定的条件，逐条列出

## 关联
（相关文档、Issue、PR、依赖项）
```

### 标签

用仓库既有标签：`bug` / `enhancement` / `feature` / `documentation` / `docs` / `accessibility`。
**不要为了贴标签新建标签。**

## 命令

```bash
# 先查重
gh issue list --repo ACANX/AHA --state all --search "关键词"

# 新建（正文用文件，避免 shell 转义问题）
gh issue create --repo ACANX/AHA \
  --title "模块：一句话" \
  --body-file /tmp/issue.md \
  --label "enhancement,feature"

# 补一条进展评论
gh issue comment <编号> --repo ACANX/AHA --body-file /tmp/comment.md
```

## 关闭 Issue（规范）

**关闭须经 ACANX 授权**；Agent 不自行关闭。

关闭前**必须先补一条关闭评论**，下面三要素**缺一不可**：

| # | 要素 | 要求 |
|---|---|---|
| 1 | **相关修复 PR / 提交** | 逐个列表：编号 + 标题 + 合并状态（含 commit）。若没有代码改动，要写清是「结论性关闭」还是「**转其他 issue**」 |
| 2 | **关闭理由** | 为什么可以关：现象是否消除；是**根治**还是**缓解**。若是缓解，必须指名根因由**哪条 issue 继续跟踪** |
| 3 | **验收依据** | 可复核的证据：命令与原始输出、测试运行编号 / 用例数、日志行、产物路径。**不得只写「已完成」**。若某项依赖人工判断（真机观感、平台行为），明说「以 ACANX 的判断为准」，**不要把人工结论写成机器结论** |

### 关闭评论模板

```markdown
## 关闭：<一句话结论>

### 相关修复 PR
| PR | 内容 | 状态 |
|---|---|---|
| #NNN | <标题> | 已合并（<sha>） |

### 关闭理由
<现象是否消除；是根治还是缓解；根因（若有）由哪条 issue 继续跟踪>

### 验收依据
| 依据 | 位置 |
|---|---|
| <命令 / 测试 / 日志 / 产物> | <路径或运行编号> |

<若有人工判断项，写明「以 ACANX 的判断为准」>
```

### 命令

```bash
# ① 先补关闭评论（正文用文件，避免 shell 转义问题）
gh issue comment <编号> --repo ACANX/AHA --body-file /tmp/close-comment.md

# ② 再关闭；reason 取 completed（已解决）/ not_planned（不做了）
gh issue close <编号> --repo ACANX/AHA --reason completed
```

### 三条硬性约束

1. **不允许「关了就没下文」**：若仍有未闭合的根因或后续项，必须在关闭评论里**指名转到哪条 issue**，
   或先把那条 issue 开好再关（实例：#48 关闭时把根因明确转给 #60）；
2. **不允许「只写已完成」**：没有可复核依据的关闭等于没闭环；
3. **长期不动的不关**：某项若暂时无进展，保持开启并在评论里记最新判断——**不要静默丢弃**。

> 出处：2026-10-13 ACANX 要求「关闭时须附上相关修复 PR 及关闭理由」，本条据此固化。
